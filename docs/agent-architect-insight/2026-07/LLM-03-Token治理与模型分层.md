# LLM-Token治理与模型分层

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。


Token治理不是财务问题，而是系统容量问题。只要Token管理失控，质量、时延、成本一定同时失控。

## 一、为什么Token是核心指标

LLM请求成本与Token直接相关，且长尾请求会放大总成本和排队延迟。平均值看起来健康，不代表系统稳定。

## 二、治理框架

建议三层预算同时存在：
1. 请求级上限：防止单次爆量。
2. 会话级上限：防止多轮累计失控。
3. 场景级配额：按业务价值分配资源。

## 三、模型分层策略

把模型分三层通常最稳：
- 基础层：低成本高并发
- 增强层：平衡质量与速度
- 专家层：高复杂高风险任务

关键是路由规则明确，不要让所有请求默认走专家层。

## 四、治理闭环

每周输出“高成本低收益”请求清单，定位根因：
- 上下文冗余
- 工具链膨胀
- 模型误路由
- 重试策略过宽

## 五、常见失败模式

1. 没有P95/P99监控，只看平均token。
2. 工具调用链无限扩展，隐性成本持续上涨。
3. 降级策略缺失，峰值时系统雪崩。

## 六、建议指标

- 平均token、P95 token、P99 token
- 请求成本分位数
- 降级触发率与降级成功率
- 模型层级路由占比
- 每千次请求总成本趋势

## 七、结论

Token治理的终点不是压到最低，而是让每个Token都花在有效信息上。做到“可预算、可观测、可回退”，系统才可持续。
