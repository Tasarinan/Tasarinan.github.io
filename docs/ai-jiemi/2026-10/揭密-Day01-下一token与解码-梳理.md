## 一、生成器是条件分布的展开器

初级说法是「模型读懂问题后写出答案」。拆开之后，服务在做的是：

| | 看起来像 | 实际在跑 |
|---|---|---|
| 一次调用 | 提交一个问题，收回一段话 | 循环：前向 → 抽样 → 拼接，直到 EOS 或长度上限 |
| 模型的产出 | 一个判断 | 词表上的 logits |
| 提示词的作用 | 下达命令 | 改变条件，从而改变下一步分布 |
| 温度 | 聪明或有创意 | 同一分布的锐度 |

**关键洞察：文本是路径，不是一次决策。** 路径上任何一个 token 都会改写后面的条件。所以「几乎对了」和「第一个实体就错了」是两种成本：前者可能只是采样抖动，后者会把后文全部条件在错误实体上。

这和本周后面几天是同一条链：

```text
Day01  分布里有什么、解码怎么挑
Day02  挑出来的内容偏离提示，还是偏离世界
Day03  用检索把证据放进条件
Day04  用提示词和 ReAct 改变条件的形状
Day05  把「行动」放到模型外面，再把观察写回条件
```

## 二、参数要按作用点分类，不能按名字分类

笔记把几十个 GenerationConfig 字段平铺，读起来像每个字段都在「控制文风」。作用点其实只有三处：

```text
改 logits     temperature、repetition_penalty
改候选集合    top_k、top_p、bad_words、no_repeat_ngram、suppress_tokens
改序列分      beam 的 length_penalty、num_beams、num_beam_groups
```

**三条使用纪律**：

1. 事实错误先别动这三处。三处都不增加证据。
2. 要稳定格式，优先约束候选集合（JSON 语法、禁词），而不是把温度调到 0 碰运气。
3. 要多条不同回答，用采样或分组 beam；分组 beam 是多样性搜索，预算按束宽乘上去。

**同构**：编译器的优化开关也分「改中间表示」「改指令选择」「改调度评分」。名字都叫优化，作用点不同，不能串着调。

## 三、缓存、窗口、滑动注意力，都是「能看见的条件」的账

三笔账经常被说成模型变强了：

| 机制 | 实际节省或限制的是什么 | 不改变的是什么 |
|---|---|---|
| 提示词缓存 | 稳定前缀不必重算，费用按缓存价 | 前缀内容本身；换一个字就失效 |
| 标称上下文长度 | 这次最多能放进条件的 token 数 | 中间位置的证据是否还能影响分布 |
| 滑动窗口注意力 | 每个 token 能回看的过去有多远 | 窗口外的 token 等于没进这次注意力 |

Day03 会看到同一笔账的检索版本：金段落直接放进条件，和把整份 PDF 放进条件，不是同一实验。

## 四、本日核心认知

1. **回答是下一个 token 的链。** 每一步的输入比上一步多一个自己写下的 token。
2. **单次请求不更新权重。** 提示、检索、缓存、工具结果都只改条件。
3. **temperature 是 logits 除法。** top_p 是概率质量，不是词表百分比。
4. **early_stopping 收的是 beam。** 句子结束看 EOS。
5. **repetition_penalty 以 1 为不变。** 惩罚项压的是重复，不是虚构。
6. **解码选路径。** 路径的事实上限由权重和当前上下文共同决定。
