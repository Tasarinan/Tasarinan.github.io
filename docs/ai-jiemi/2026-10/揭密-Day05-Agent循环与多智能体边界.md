## 背景

`36_Agent` 的架构笔记把智能体写成规划、记忆、工具、行动四件，又写「智能体 = 大模型 + 自主规划 + 使用工具 + 记忆」。同一批笔记里还有一句更有用的区分：固定每次都去搜索，是工作流；由模型先判断要不要搜索，才是它们所说的智能体模式。`00_Agent常见模式.md` 把自主规划和工作流预编排对成灵活性和可控性。`03_多智能体有效性探讨.md` 并置了三篇：Anthropic 的研究型多智能体、Cognition 的「先别建多智能体」、LangChain 对两者的折中。`06_记忆/01_记忆设计.md` 把记忆分成六类，并承认分类落到存储上还有一段距离。

今天核对的是：哪些能力在模型里，哪些能力在运行时里；什么时候多一个代理只是多一条缺少共享上下文的生成。

## 题目一：三个系统被叫成了同一个名字

### 作答区

#### 1. 用三个问题分类，不用宣传语分类

| | 聊天 | 工作流 | 自主循环 |
|---|---|---|---|
| 谁决定下一步 | 用户的下一句话 | 人事先画好的边 | 模型生成的 Action，运行时执行后把观察交回 |
| 工具 | 无，或由界面强制调用 | 每步绑定死 | 模型从已注册工具里选，也可以不选 |
| 失败后 | 用户重说 | 走到失败节点，按边上的处理走 | 取决于观察是否写回，以及是否允许从这一步再试 |
| 笔记里的例子 | 角色扮演被误叫成智能体 | 百炼、LangGraph 的预编排；联网的手动模式 | Manus 一类自行规划再观察；联网的自动模式 |

5 大关键技术笔记用元宝联网做了这个对照：手动模式每次都搜；自动模式先判断要不要搜。两者都「用了工具」。差别在于下一步是不是被模型的文本决定。

自主循环的可控性低，笔记写得很明确：它适合任务本身还没有标准步骤的探索。步骤已经标准、必须按顺序做、做错的代价高，笔记建议走预编排。灵活性和可控性在这里是同一条设计的两端，不是两个可以同时拉满的指标。

#### 2. 四件套各自落在哪里

简介笔记的四件套，映射到已经核对过的机制上：

| 组件 | 笔记中的定义 | 核对后的位置 |
|---|---|---|
| 规划 | 把任务拆开，用 ReAct、思维链实现 | 仍是模型生成的文本。拆分结果是 token，不是一张被执行引擎保证的计划 |
| 记忆 | 短期存会话，长期存向量库 | 短期是当前上下文；长期是模型外面的存储。权重不因为叫了记忆就更新 |
| 工具 | API、插件 | 模型输出调用文本；运行时发请求 |
| 行动 | 把规划和记忆变成输出或调用 | 若指对世界的副作用，发生在运行时；若指下一句回复，就是 Day01 的生成 |

「面向目标而不是面向过程」是架构愿望。实现上，目标句也是提示里的 token，过程仍是生成、暂停、执行、写回。

#### 3. Function Calling 训练进去的是格式

笔记把工具使用的时间线写清楚了：早期靠提示词给出工具说明、调用规范和示例，模型返回一段 JSON，程序解析并执行。后来 Function Calling 把这种格式做进模型，调用方用 tools 字段声明有哪些工具。

格式进了权重，意味着少写一段「请输出这种 JSON」的提示。请求仍然是：

```text
工具清单进入上下文
→ 模型生成调用参数
→ 运行时执行
→ 结果进入上下文
→ 模型生成下一步
```

模型不持有网络栈。工具描述写错时，模型会稳定地生成错误参数，因为描述是条件的一部分。笔记里 Anthropic 的经验也落在这里：工具说明要能被测试，说明含糊时，智能体会选错工具。测试的是说明文本，不是再训练一个「更会用工具的灵魂」。

## 题目二：多智能体何时共享上下文，何时制造冲突

### 作答区

#### 1. 四种接法

常见模式笔记列了四种：

| 接法 | 控制怎么走 | 上下文怎么走 |
|---|---|---|
| 转交 | A 做完交给 B | B 默认只看见交给它的那段，除非显式带上历史 |
| 嵌套 | A 调 B，B 调 C，再返回 | 像调用栈。内层看不见外层没传下来的决策 |
| 主从 | 主代理对用户说话，按需调子代理 | 子代理看见的是任务书，不是主代理的全部推理 |
| 群聊 | 多个代理都发言再汇总 | 每个人看见群消息，写入若并行，仍会冲突 |

接法不决定对错。决定对错的是：子代理拿到的是任务的一句话，还是导致这个任务的决策链。

#### 2. 研究检索：并行读，主代理收口

Anthropic 笔记里的结构是主代理规划，子代理在各自上下文里并行搜索，引用代理负责把主张对回来源。他们报告在内部研究评测上，Opus 主代理加 Sonnet 子代理比单个 Opus 高 90.2%。同一篇也写了成本：单体大约是普通对话的 4 倍 token，多智能体大约 15 倍。

这些数字是他们的内部任务，不是代理个数的物理常数。笔记里同时写明的边界更值得留下：需要所有参与者共享同一份实时状态、步骤彼此紧耦合的任务，这套并行不适合。

他们列出的可执行经验，都是在压协调而不是在加角色：

1. 派任务时写清目标、输出格式、可用工具和边界。含糊的任务书导致重复劳动。
2. 按问题复杂度规定子代理数量和工具次数。模型不擅长自己判断该花多少。
3. 工具说明要包含何时使用。先宽搜再收窄，写进提示，而不是指望自发形成。
4. 轨迹要能回放。长任务中途失败，要从失败步恢复，而不是整段重来。

#### 3. 写代码：动作里夹着没说出口的决定

Cognition 笔记的原则有两条。第一，子代理要拿到完整决策链，不能只拿到一句任务。第二，每一步动作都含着隐含决定，并行写入时这些决定会冲突，而且难以自动合并。

他们的结论是：今天的多智能体更适合读多写少。写代码这类要保持一份一致工件的任务，单线程加必要时的压缩，比并行子代理可靠。压缩是用另一个模型把历史收成摘要再续写，用来对付单线程把窗口写满。摘要会丢细节，这是用信息损失换一致性。

笔记里的例子把边界说具体了：代码助手里的子代理可以回答一个局部问题，但不并行改同一批文件；让小模型执行大模型的编辑指令时，指令里没写清的决定会被小模型另做一套。

LangChain 的折中在笔记里被收成一句：两边都在谈上下文何时、以何种完整度传递。分歧是任务形态，不是口号。

#### 4. 选型就用这张表

| 任务形态 | 上下文要求 | 更贴笔记的结构 |
|---|---|---|
| 开放研究，多来源阅读，最后写一份带来源的综述 | 子代理可以各看各的材料，主代理收口 | 主从，加单独的引用步骤 |
| 对同一份代码或同一条记录做连续修改 | 每一步都要看见此前的决定 | 单线程；窗口不够就压缩，并接受压缩损失 |
| 步骤固定、每步输入输出明确 | 边上写清楚即可 | 工作流，不需要自主循环 |
| 只是回答一句事实 | 证据片段 | Day03 的检索，不需要代理 |

「成功率提升」若没有任务形态和 token 倍数，就不能当作选型理由。

## 题目三：记忆是外置存储的读写规则

### 作答区

记忆设计笔记的六类，若没有存储就停在比喻。落到组件上是：

| 笔记中的类 | 持续时间 | 实际存储 | 写入 | 读出 | 淘汰 |
|---|---|---|---|---|---|
| 短期 | 这次对话 | 消息列表，受窗口限制 | 每轮追加 | 整段或最近 N 轮进入提示 | 滑出窗口就消失 |
| 工作 | 这一步 | 当前目标和中间量，仍在上下文或状态对象里 | 规划步写下 | 下一步提示读它 | 这步结束丢弃 |
| 情节 | 跨会话的事件 | 日志：谁、何时、做了什么 | 工具轨迹、对话节点 | 按时间或实体查 | 按保留期 |
| 语义 | 可复用事实 | 文档索引、向量库、表 | 入库流程，不是聊天顺便记住 | Day03 的检索 | 源文档更新时失效 |
| 程序 | 可重复的做法 | 技能说明、工作流定义、工具描述 | 人编写或单独的更新流程 | 放进系统提示或工具清单 | 版本化，不随闲聊改写 |
| 长期 | 上面几类的统称 | 任何模型外面的库 | 看具体类 | 看具体类 | 看具体类 |

笔记希望语义记忆减少「常识性幻觉」。那要靠检索把事实放进上下文，并且事实是真的。库里的错误事实会变成 Day02 的错误材料。

短期记忆只保留最近 N 轮或只保留相关轮，是在做上下文淘汰。淘汰掉的决定，下一步就看不见。这和多智能体没把决策链传下去是同一种失败。

## 本日能力差距与补足方向

### 差距1：所有包着模型的程序都叫 Agent

- **现状**：聊天、固定流程、自主循环混用一个词。
- **核对后的水平**：用「谁决定下一步、工具谁执行、失败能否从该步恢复」三问分类。
- **补足方向**：给当前系统填三问。填完再决定要不要加第二个代理。

### 差距2：90.2% 脱离任务和成本

- **现状**：用一个内部研究数字证明所有业务都该拆代理。
- **核对后的水平**：读多写少才讨论主从；共享工件上的写入保持单线程。引用数字时带上大约 15 倍 token。
- **补足方向**：先拿十个真实任务分类，再谈框架。

### 差距3：记忆类型没有读写路径

- **现状**：六种记忆各写一段定义，系统里只有一个消息数组。
- **核对后的水平**：每类对应存储、写入点、读出点、淘汰规则。
- **补足方向**：本题的表。对不上存储的类，就不要写进架构图。
