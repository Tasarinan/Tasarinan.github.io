## 一、循环依赖是"时序问题"，不是"数据结构问题"

Day03 最重要的升维：**三级缓存只是管理半成品的机制，可解性由时序决定**——依赖需求时点晚于可暴露时点，环就能解。这个第一性原理解释了所有形态：

```
setter/字段注入：需求在 populateBean（壳已存在，工厂已注册）→ 可解
构造器注入：    需求在 createBeanInstance（工厂还没注册）    → 不可解
prototype：    连暂存点都没有（容器不缓存）                  → 不可解
@Lazy：        注入代理，需求推迟到首次调用                  → 环被剪断
```

**架构师读法**：遇到任何"鸡生蛋"问题（初始化顺序、双向依赖、启动依赖），先别找工具，先画时序图问"谁在什么时点需要谁、那个时点对方能暴露什么"。**时序分析是工具选型的前置步骤**——Day02 的"就绪四层语义"、Day01 的"两阶段设计"本质上都是同一套分析方法。

## 二、三级缓存的四件套设计：半成品的受控发布协议

把源码细节抽掉，Spring 三级缓存是一套可迁移的**对象状态受控发布协议**：

```
① 成品一次性发布不可变     —— addSingleton 后不再变（安全发布的锚点，JMM）
② 半成品条件可见           —— 只对"同样在创建中"的请求暴露（allowEarlyReference + inCreation）
③ 半成品形态延迟决策       —— ObjectFactory：要不要提前建代理，等真被需要了再定
④ 一次性升级 + 全局唯一    —— 工厂调用后升二级删三级；earlyProxyReferences 记账防二次代理
⑤ 终态一致性核对           —— 被消费过的半成品，最终发布物必须与消费物一致（否则报错）
```

**这套协议的同构家族**：Raft（未提交日志不对外服务）、MVCC（事务中数据不可见，提交一次性可见）、K8s（readiness 未过不进 endpoints）、读写锁（写中读旧快照）。共同点：**系统要么发布自洽状态，要么把"不完整"显式建模并管理其一致性**。

**问诊系统落点**：医生"签到但资料未同步完"的在线状态推送、渠道"已建连但未通过健康检查"的流量开放，都是自己的"早期暴露"问题——四件套（条件可见/延迟决策/一次性升级/一致性核对）直接套用。

## 三、"为什么是三级"的设计课：延迟决策的力量

反证法的三段论值得反复回味：

1. **两级 + 直接放壳** → B 拿到原始对象 → @Transactional 失效——正确性破损
2. **两级 + 立刻代理** → 所有 Bean 出生即代理——为极少数循环场景付全量代价，且违背"代理包装最终对象"的初始化语义
3. **三级 + 工厂** → 决策推迟到"确实有人需要提前引用我"——**零成本兼容极端场景**

一句话：**第三级缓存存的不是对象，是"还没做的决定"**。

这是"为少数场景准备的能力，不能让多数场景买单"的通用智慧，同构案例遍布往周：

| 系统 | 延迟决策机制 |
|---|---|
| JVM | 类的解析/初始化推迟到首次主动使用 |
| Netty | ChannelHandler 懒加载、ByteBuf 按需分配 |
| MySQL | 索引的锁降级、行的延迟解锁（MVCC 快照） |
| K8s | 按需调度、节点压力驱逐而非预留 |
| G1（JVM 周） | region 角色动态转换，不在分配时锁定 |

设计自查题：**我的系统里有没有"为了 1% 场景让 100% 请求买单"的逻辑？能不能把它改造成工厂/闭包/懒加载式的延迟决策？**

## 四、Boot 2.6 的闸门：框架的兼容能力 vs 平台的设计态度

"Spring 一边解决循环依赖、一边（Boot）默认禁止它"——这个表面矛盾的答案分层：

- **Framework 层**（通用库）：要兼容历史的、多样的世界——三级缓存是给"已发生的环"的生路
- **Boot 层**（ opinionated 平台）：有立场——环是模块边界不清的坏味道，默认报错是 fail-fast 在**依赖图**上的应用

**同样的分层在往周反复出现**：K8s 不阻止你写没有资源限额的 Pod（API 兼容），但生产策略（LimitRange/Admission）强制要求（平台态度）；Netty 允许你在 EventLoop 里写阻塞代码（能力），但最佳实践规约禁止（态度）。**架构师的职责就是给"通用能力"配一副"平台态度"**——问诊系统的治理清单（ArchUnit 禁环、CI 闸门、代码规约）就是自己团队的"Boot 2.6 闸门"。

治理四步路线图：**摸底（CI 试跑/ArchUnit）→ 归因（概念未抽出/双向读写/工具方法误依赖）→ 过渡（@Lazy 显式留 TODO）→ 熔断（规则+闸门防新增）**。归因三类的解法分别是抽中介者、事件解耦（ApplicationEvent 剪环）、下沉公共模块——**每类都有比 @Lazy 更对的目标解**，@Lazy 只是过渡。

## 五、锁的不变量：为什么二三级可以是 HashMap

Day01 讲了一级缓存 CHM 的 happens-before（安全发布），Day03 补全另一半：**earlySingletonObjects/singletonFactories 是 HashMap，安全性来自"锁保护的不变量"**——所有对二三级缓存的读写都发生在 `synchronized (this.singletonObjects)` 块内。

这是并发设计的经典层次：**数据结构安全（线程安全容器）与访问协议安全（锁覆盖）是两条等价路线**。选择依据：

- 一级缓存：运行期高并发读、写入集中在启动期 → CHM（读无锁）收益大
- 二三级：只在启动期、创建中的 Bean 上访问，量小且全程持锁 → HashMap 足够，CHM 反而浪费

**架构师纪律**：看到非线程安全容器不等于看到 bug——先看**访问协议是否被锁/单线程完全覆盖**（Netty 的"EventLoop 串行无锁"是同一原理的极致版：用线程归属替代锁）。反过来，看到线程安全容器也不等于安全——**复合操作（check-then-act）仍需外层协议**。

## 六、热身题的架构回响：提前暴露的经济学

TLS 0-RTT 与三级缓存的对照表（Day03 正文）浓缩了"提前暴露"设计的三条铁律：

1. **暴露的部分状态必须显式声明能力边界**（0-RTT 只许幂等请求；早期引用只作引用暂存不保证完全初始化）
2. **提前态与终态必须有一致性契约**（PSK 绑定旧配置需失效；一致性核对/报错兜底）
3. **无该场景时必须零成本**（不复用就付全握手；无循环则工厂不调用）

**同样值得带走的三条安全常识**：混合加密的理由（重武器一次轻武器全程）；前向保密的本质（临时密钥用完即弃，长期私钥泄露不伤历史）；信任锚的真相（根证书的可信来自分发渠道/供应链，不是密码学）——医疗数据合规叙事的地基。

## 八、本日核心认知

1. **可解性 = 时序问题**：依赖需求时点 vs 可暴露时点——三级缓存管半成品，改变不了时序
2. **三级缓存四件套**：条件可见 / 延迟决策（工厂）/ 一次性升级（全局唯一代理）/ 终态一致性核对——半成品受控发布协议，可迁移
3. **"为什么三级"的标准答案**：两级放壳→事务失效，两级提前代理→全量买单；工厂把"要不要提前建代理"推迟到真被需要时——**第三级存的是还没做的决定**
4. **时序灵魂**：A 提前暴露、B 正常创建；第 13 步 getSingleton(name,false) 一致性核对防"B 持有的 A ≠ 容器的 A"
5. **锁的不变量**：二三级 HashMap 安全是因为所有访问在 singletonObjects 锁内——访问协议安全可替代容器安全
6. **Boot 2.6 闸门**：兼容能力 vs 设计态度；治理四步（摸底→归因三类→@Lazy 过渡→规则熔断）
7. **@Lazy 剪环**：注入代理，创建期依赖松弛为运行期依赖——过渡手段而非目标手段
8. **提前暴露三铁律**：能力边界显式声明、提前态与终态一致性契约、无场景零成本（TLS 0-RTT 同构）
9. **前向保密**：ECDHE 临时密钥用完即弃；信任锚来自供应链不是密码学
10. **架构师自查**：系统里有没有"为 1% 场景让 100% 买单"？能否延迟决策化？
