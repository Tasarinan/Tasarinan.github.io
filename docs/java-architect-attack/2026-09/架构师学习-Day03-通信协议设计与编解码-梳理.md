## 一、架构师视角下的"协议"

### 1.1 协议是双方对字节流的"解释契约"

TCP 给你的是一根无结构的字节管道，协议的全部使命是**在这根管道上重建结构**：

```
字节流（无结构） --[分帧]--> 帧（有边界） --[解码]--> 消息（有语义） --[反序列化]--> 对象
         Day01 compact      Day03 长度字段          Day03 头字段            Day03 Protobuf
```

四层抽象每一层解决一个"结构缺失"：边界（分帧）→ 元信息（头）→ 语义（消息类型）→ 数据（对象）。**粘包拆包、字段设计、序列化选型不是三个孤立考点，是同一条"结构化流水线"的四道工序**。

### 1.2 每个字段都是一次"防御性设计"

架构师读协议设计的方法论：**问每个字段"删掉它会怎样"**——

| 字段 | 删掉的后果 | 防御的本质 |
|---|---|---|
| magic | 扫描器/异构客户端的数据涌入深层 pipeline 才报错 | **在入口用最便宜的方式识别"非我族类"** |
| version | 新旧客户端混布即解析错乱 | 给**演化**留通道 |
| length | 无从分帧 | 给**边界**立依据 |
| seqId | 丢失无感知、重发无法去重 | 给**可靠性**锚点 |
| maxFrameLength | 一个 4B 字段声明 2GB → 堆外 OOM | 给**资源消耗**封顶 |

结论：**协议字段 = 针对一类风险的预置答案**。字段冗余是浪费，字段缺失是漏洞，架构师的价值是精确匹配风险面。

### 1.3 "最便宜的拦截点"原则

安全防御的本质经济学：**数据流越深，处理它消耗的资源越多；拦截越早，成本越低**。

```
第一字节（magic 校验）     → 消耗：2 字节读取。成本 ≈ 0
头字段（length 校验）      → 消耗：半帧解析。成本：低
body 反序列化（schema）    → 消耗：完整帧 + CPU。成本：高
业务逻辑（鉴权/限流）      → 消耗：状态 + 下游调用。成本：最高
```

未认证连接的规约"只允许 AUTH/HEARTBEAT、认证超时即断、零业务开销"就是这个原则的落地——**把 99% 的恶意流量挡在消耗第 1~2 层**。这与限流周的"分层限流（网关层 > 服务层 > DB 层）"完全同构。

## 二、解码器体系：框架替你踩过的坑

### 2.1 cumulator：Day01 手写逻辑的框架化

Day01 手写的 `compact + channel.read + 边界判断` 循环，对应 ByteToMessageDecoder 的 cumulator。框架化的增益不是少写代码，是**把边界条件全部闭合**：扩容策略、半包保留、异常路径的缓冲释放（老版本 Netty 这里就出过泄漏 bug，Day07 会反推同类问题）、以及解码循环的退出条件。

**架构师认知**：手写一遍的价值在于"知道框架每行代码在救什么命"；用框架的价值在于"别在生产再踩一遍"。

### 2.2 lengthAdjustment：参数背后的世界观

五参数里只有 adjustment 难背，因为它暴露了一个设计现实：**"长度字段的值"是一个约定，不是规范**（可以只算 body、可以含头、甚至可以含长度字段自身）。decoder 必须兼容所有约定，于是有了补偿参数。

恒等式 `帧总长 = offset + fieldLength + 长度值 + adjustment` 是把约定**显式化**的工具。架构师启示：**设计自己的协议时，把约定写死并写进文档（"length 只算 body"），别让实现方猜**——Kafka/RocketMQ 的协议文档第一页都是这种约定声明。

### 2.3 帧的生命周期与所有权

```text
入站：socket → cumulation（decoder所有） → frame（decoder分配，+1引用）
     → decode 成 POJO → frame 由 decoder release（或交给下游消费）
出站：业务 POJO → encoder 写入框架分配的 out → ChannelOutboundBuffer → writev → 内核
```

**每个 ByteBuf 在每个节点都有明确的 owner**——"谁分配谁释放、谁 retain 谁 release"。Day03 只需记住两条：decoder 分出的帧读完即 release；encoder 的 out 不归你管。Day07 会看到违反这两条的完整事故链。

## 三、序列化：选型是约束匹配，不是性能竞赛

### 3.1 按约束选型

```
有浏览器/开放生态参与？ → JSON（自描述、可 curl 联调）
多端 + 流量敏感 + 演进频繁？ → Protobuf（tag 兼容 + 1/4 体积 + 多语言）
Java 内部 + 无跨语言？ → Hessian2/Kryo（够快够小，注意 Kryo 跨版本兼容风险）
极致性能 + schema 可控？ → 自研 TLV / FlatBuffers（零拷贝反序列化，游戏/高频领域）
```

### 3.2 兼容性的两种哲学

| | JSON（无 schema） | Protobuf（强 schema） |
|---|---|---|
| 容错方式 | 自然容错：未知字段忽略、缺失字段为 null | 机制容错：tag + unknown fields + 默认值 |
| 代价 | 字段拼错不报错（静默丢数据）；没有"契约"可校验 | 需要 IDL 管理与代码生成流水线 |
| 适用 | 变更随意、联调频繁 | 变更受控、多端严格对齐 |

**架构师认知**：Protobuf 的 unknown fields 机制本质是"**把兼容性做成协议的一部分**"，而 JSON 是"把兼容性交给实现的宽容度"。工业级多端系统选前者——**契约先行，演化受控**。

### 3.3 版本演进的三层架构

```
帧级：version 字段 + 服务端向后兼容窗口（≥ 一个全量发布周期）
消息级：Protobuf tag 规约（只加不改不复用）
能力级：AUTH 握手协商 feature 集合，按交集降级
```

演进的关键指标是**灰度期共存能力**：任何时刻线上同时存在 N-1 与 N 版本的客户端，协议必须让两者都能正确服务。这个思维与 K8s 周的"滚动发布兼容性"（API 版本 deprecation 窗口）同构。

## 四、心跳：长连接的"生命维持系统"

### 4.1 心跳的三重使命

| 使命 | 机制 | 量级依据 |
|---|---|---|
| 刷 NAT 表项 | 客户端周期发包（writerIdle 驱动） | NAT 超时常见 1~5 分钟 → 间隔必须显著小于它 |
| 检测对端假死 | 服务端读空闲踢连接 | 三倍容错：间隔 × 3（抖动+丢包+调度延迟） |
| 连接质量采样 | 心跳 RTT 作为网络质量信号 | 可做自适应心跳/弱网标记（进阶） |

### 4.2 踢连接是容量卫生

假死连接不是"无害的安静连接"，它是**持续计费的资源占用**（fd + 内核缓冲 + Session + 路由条目 + 推送消息在发送缓冲堆积）。读空闲踢连接的阈值（90s）本质是一个资源回收周期。**架构师看心跳：不是保活功能，是资源生命周期管理**。

## 五、本日核心认知

1. **协议 = 字节流上的结构化契约**：分帧（边界）→ 头（元信息）→ 消息（语义）→ 对象（数据），四道工序环环相扣
2. **粘包不是 TCP 的 bug**，是流式可靠传输的结构代价，边界必须应用层重建
3. **每个字段都是防御性设计**：magic 识别非我族类、length 立边界并封资源上限、version 留演化通道、seqId 锚可靠性
4. **最便宜的拦截点原则**：数据流越深处理越贵，防御前移——magic 第一字节拦截，未认证连接零业务开销
5. **lengthAdjustment 的本质是约定的显式化**：恒等式现场推，设计自己的协议时把约定写死进文档
6. **校验失败关连接**：长度异常意味着流状态错乱，跳帧解决不了信任问题
7. **帧有明确的所有权链**：谁分配谁释放、谁 retain 谁 release——decoder 帧读完即 release，encoder 的 out 不归业务管
8. **序列化选型 = 约束匹配**：多端流量敏感选 Protobuf，开放生态选 JSON；Protobuf 兼容靠 tag + unknown fields（契约先行）
9. **版本演进三层**：帧 version + 消息 tag + 握手能力协商；核心指标是灰度期新旧共存
10. **心跳三重使命**：刷 NAT（真价值大头）、测假死（三倍容错）、采质量；踢连接是容量卫生不是功能
11. **WS 帧承载自定义协议**：一套编解码两种传输，浏览器端唯一解
