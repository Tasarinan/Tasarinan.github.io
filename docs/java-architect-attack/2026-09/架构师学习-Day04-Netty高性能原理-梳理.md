## 一、性能优化的第一性原理：三个问题

Netty 的"高性能"不是一堆 trick 的堆叠。所有优化都在回答三个问题：

```
① 一次操作消耗了几次系统调用？        → writev 攒批、transferTo、epoll（系统调用是贵操作）
② 一份数据被物理拷贝了几次？          → direct 免隐性拷贝、Composite/slice、sendfile（拷贝是浪费）
③ 一个资源被几把锁竞争？              → 单 EventLoop、Mpsc、PoolThreadCache（竞争是串行点）
```

**架构师的方法论**：拿到任何性能问题先问这三个问题，再对症下药。反过来的顺序（先抄配置后想原理）是八股调优的通病。

## 二、内存池：把"分配"从成本项变成管理项

### 2.1 因果链的架构解读

```
GC 会移动堆内对象 → 内核要稳定地址 → heap IO 偷偷拷贝 → 该用 direct
→ direct 分配贵 + Cleaner 释放延迟 → 池化（预申请+切分+归还）
→ 池化内存不归 GC 管 → 引用计数（手动生命周期）→ 忘 release = 堆外泄漏
→ ResourceLeakDetector（采样的哨兵）
```

每个环节都是上一环的必然结果。**这条链的起点在 JVM 的 GC 设计，终点在 Day07 的事故复盘**——架构师的价值是能看到整条链，而不是链条上的一环。

### 2.2 池化的分层 = 锁粒度的设计课

```
一把全局锁（所有线程所有分配）         ← 假想的最差设计
 → 拆成 2×CPU 个 arena（每把锁管 1/(2N) 流量）
 → 再叠线程本地缓存（大概率根本不碰锁）
```

这与并发周的演进完全同构：synchronized 全局锁 → 分段锁（JDK7 CHM）→ CAS + 单线程粒度（JDK8 CHM bin）→ LongAdder 分散单元格。**"把一把锁拆成 N 把、再把大概率路径变成无锁"是并发设计的通用演进路径**，Netty 内存池是它在内存分配领域的实例。

### 2.3 池高水位 ≠ 泄漏（运维判断力）

池子囤备用块是**设计行为**：流量低谷 RSS 不回落，不代表泄漏。判断标准：

| 观察 | 泄漏 | 正常池行为 |
|---|---|---|
| 趋势 | 单调上涨，与流量无关 | 涨后不降，但稳定在水位带内 |
| allocator metric | usedDirectMemory 持续升 | 在 arena/cache 容量内波动 |
| LeakDetector 日志 | 有（采样暴露） | 无 |

**把"上涨"直接判死刑会误杀，把"上涨"当正常会放跑真泄漏**——区分它们需要看趋势 + 采样日志 + metric 三件证据。Day07 事故里这是第一个分叉点。

## 三、所有权：引用计数的心智模型

### 3.1 把 GC 的隐性责任显式化

JVM 堆内：分配即托管，GC 兜底。堆外池化：**生命周期 100% 手动**——retain 是"我承诺要还"，release 是"履约"。所有泄漏事故都是"承诺了没兑现"的账没对上。

**责任链速记**：

```
分配者负责第一条释放链（decoder 分帧 → 传给业务即转移责任）
传递即转移（fireChannelRead 给出去就不再是你的）
retain 者独立还债（广播 retainedDuplicate × N = N 份独立契约）
兜底：Tail（inbound 未消费）/ 解码器（半包残留）/ ChannelOutboundBuffer（写出后）
```

### 3.2 零拷贝的代价结构

```
物理拷贝：花 CPU、花带宽、但所有权简单（copy 出来就是你的）
逻辑视图（slice/Composite）：零拷贝零成本，但所有权变共享契约
```

**架构师判断**：小消息高频 → 视图省的钱有限但契约风险高，不如早解码 POJO；大缓冲低频（文件、大帧转发）→ 视图收益巨大，值得认真管理引用。**零拷贝不是默认正确，是"收益 > 所有权复杂度"时的选择**。

## 四、背压：把"慢"传导回源头

### 4.1 三级背压机制

```
L1 信号：isWritable()=false / ChannelWritabilityChanged   —— 告诉你"我满了"
L2 源头：autoRead=false                                    —— 我不读了
L3 内核：接收缓冲堆积 → TCP 通告窗口收缩                     —— 网络层自动反压对端
```

Netty 提供 L1/L2 的开关，L3 是 TCP 白送的。**架构师要做的是策略**：收到"满了"信号后——降频？丢弃低优先级？断开？这是业务决策（IM：通知可丢、消息不可丢；交易：全都不可丢只能断）。

### 4.2 与 MQ 背压的同构

| | Netty 写路径 | MQ（Kafka/RocketMQ） |
|---|---|---|
| 缓冲 | ChannelOutboundBuffer | broker 页缓存/发送缓冲 |
| 信号 | isWritable / 水位 | 消费 lag / 磁盘水位 |
| 源头反压 | autoRead=false | 生产者限流/降级 |
| 不作为的结局 | 堆外 OOM | broker OOM/磁盘爆 |

**背压是分布式系统的通用课题，Netty 给了最完整的一条物理链路（到 TCP 窗口）**——面试里从这里展开到 MQ/线程池（有界队列拒绝策略）的对照，是"网络 → 中间件 → 并发"三周知识串联的黄金话术。

## 五、监控与容量：让性能"可运营"

性能设计只解决"上线时好"，监控与预算解决"运营中一直好"：

```
四件套指标：池化堆外用量 / ChannelOutboundBuffer 深度 / EventLoop 排队延迟 / 连接与水位
一个公式：  堆外预算 = 连接数×(读缓冲+高水位) + 广播峰值×扇出 + 累积余量
一条红线：  预算 80% → 扩容/限流（不是等 OOM）
一个容器账：limit ≥ 堆 + 元空间 + 堆外 + 线程栈 + code cache + 20% 余量
```

**没有指标的调优是玄学，没有预算的容量是赌博**。Day06 的事故复盘会验证：四件套里缺任何一件，定位时间都会从分钟级变成小时级。

## 六、本日核心认知

1. **性能三问**：几次系统调用？几次拷贝？几把锁竞争？——先归因再优化
2. **池化因果链从 GC 移动对象开始**，到 ResourceLeakDetector 结束；每环是上环的必然
3. **池的锁设计**（2×CPU arena + 线程缓存无锁快路径）与 CHM/LongAdder 演进同构：拆锁 → 免锁
4. **池高水位是设计行为不是泄漏**；判泄漏看趋势 + 采样日志 + metric 三件证据
5. **引用计数 = 显式的所有权契约**：谁分配谁释放、传递即转移、retain 者独立还债、兜底四处分布
6. **零拷贝五件套省的是拷贝，付的是所有权复杂度**——收益大于复杂度才用
7. **write 只入队，flush 才发**；攒批（writev）是写吞吐第一课，与 MQ 攒批同构
8. **背压三级**：isWritable 信号 → autoRead 源头停读 → TCP 窗口收缩；策略是业务决策
9. **direct 的价值只在内核那一跳**：IO 边界 direct、尽快 POJO、立刻释放
10. **预算公式 + 80% 红线 + 容器账**：容量是算出来的，不是测出来的
11. **监控四件套**是 Day06 故障定位速度的分水岭——缺一件，定位从分钟变小时
