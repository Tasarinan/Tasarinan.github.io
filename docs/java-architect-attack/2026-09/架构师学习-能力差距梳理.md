## 一、网络编程模型演进（Day01）

### 差距1.1：长连接容量量化能力不足
> Day1发现，延续第4周简历项目差距（容量规划）

- **现状**：知道"BIO 不行、NIO 行"，但说不出每长连接 10~50KB 的构成（fd + 内核 socket buffer + Session 对象）、线程栈 1MB 默认值、上下文切换 1~10μs 的量级；面试官量化追问时只能定性回答
- **架构师水平**：30 秒内完成"峰值 50w 在线 → 单机 10w → 5 台 + 30% 余量"的内存/带宽/连接数三维容量推算
- **补足方向**：给 IM 在线客服项目做一次完整容量估算，写进简历项目的"容量规划"段落；核对 Linux 默认参数（ulimit -n / threads-max / Xss）

### 差距1.2：epoll 机制理解止步于数据结构名词
> Day1发现

- **现状**：答"epoll 快"只到"红黑树"，说不出"回调挂就绪链表"（ep_poll_callback → rdllist）这个真正机制；说不出"100% 活跃时 epoll 无优势"的反向边界；存在"epoll 用 mmap"的八股错误认知
- **架构师水平**：画得出"网卡中断 → 软中断 → 协议栈 → ep_poll_callback → 就绪链表 → epoll_wait 返回"完整链路；能按系统 IO 活跃度分布做 select/poll/epoll 选型判断
- **补足方向**：把回调链路画图讲一遍；记住"稀疏活跃用 epoll"与活跃度分布的因果关系

### 差距1.3：LT/ET 与阻塞/非阻塞两组概念混淆
> Day1发现，延续并发周 Day05 差距（虚拟线程调度）

- **现状**："ET 才要非阻塞"是对的，但"LT 语义的 JDK Selector 为什么也要求非阻塞 fd"答不出；ET 不读完丢事件的两种形态（没读到 EAGAIN 中途返回、读一半来了新数据无新跳变）说不全
- **架构师水平**：因果分离——ET 要非阻塞是为了"读完不挂死"，事件循环要非阻塞是为了"一个线程伺候多个连接不卡队"，两个理由独立成立
- **补足方向**：用 ET + 阻塞 fd 手写一次 read 循环，亲测 EventLoop 挂死现象

### 差距1.4：Buffer 状态机与半包累积的实操能力不足
> Day1发现

- **现状**：只会背"flip 翻转"，说不出不 flip 的具体症状（从 pos 写到 limit，写出空洞字节）与不 compact 的症状（半包数据被 clear 作废）；自己写解码器必错
- **架构师水平**：手写"定长头 + 变长体"协议的裸 NIO 接收循环（只用 compact + 累积缓冲）一次跑通，作为 Day03 粘包拆包的前置练习
- **补足方向**：Day03 之前完成该练习；把 flip/rewind/clear/compact 四操作的状态变化写成卡片

### 差距1.5：零拷贝只会背名词，画不出路径图
> Day1发现，延续 MQ 周差距（Kafka 高性能原理）

- **现状**：说不出"传统 4 次拷贝 4 次切换 → sendfile 2 次拷贝 2 次切换"的完整路径（DMA/CPU 拷贝分别标不清）；不知道 sendfile 只有 file→socket 方向；串不起 Kafka（sendfile）与 RocketMQ（mmap）的选型差异
- **架构师水平**：白板画两条数据流向路径图；讲清 DMA gather 从页缓存直取的机制；与 Day04 Netty 的 CompositeByteBuf/slice（应用层零拷贝）分层说清
- **补足方向**：画路径图进笔记；对照 Kafka FileRecords 与 RocketMQ MappedFile 源码入口各读一遍

### 差距1.6：heap buffer IO 隐性拷贝与 Netty 内存池因果链不熟
> Day1发现，延续 JVM 第2周 Day05 差距（堆外内存）

- **现状**：不知道 heap ByteBuffer 做 socket IO 时 JDK 会偷偷拷贝到临时 DirectByteBuffer（Util.getTemporaryDirectBuffer）；"Netty 为什么力推 direct + 池化"的因果链讲不完整；direct 内存不占堆但要占容器内存预算的账容易漏算
- **架构师水平**：背熟因果链——heap 隐性拷贝 → direct 免拷贝 → direct 分配贵（失败触发 System.gc）→ PooledByteBufAllocator → 引用计数 → ResourceLeakDetector；K8s memory limit 公式纳入 MaxDirectMemorySize
- **补足方向**：读 sun.nio.ch.IOUtil 源码；把因果链与 JVM 堆外内存周的事故案例对上

### 差距1.7：网关选型叙事缺乏结构，虚拟线程问题答成二极管
> Day1发现，延续并发周 Day05 差距（虚拟线程）

- **现状**："为什么用 Netty"讲不出三层对比（Tomcat 容器抽象错位 / WebFlux 多付响应式复杂度 / 自研痛点清单=工作量清单）；虚拟线程会不会替代 Netty 答"会"或"不会"，不会分"线程模型层"与"框架能力层"两层回答；不知道虚拟线程网络 IO 底层就是 epoll（sun.nio.ch.Poller）
- **架构师水平**：从协议、容量、生态、团队四个维度展开选型叙事；虚拟线程问题分层回答并点出 io_uring + 虚拟线程的未来组合
- **补足方向**：把 Day01 第 6 问的两张对比表内化成面试话术，结合 IM 网关项目练 STAR 叙述

## 二、Netty 核心架构与线程模型（Day02）

### 差距2.1：启动流程停留在"会写 Bootstrap"
> Day2发现

- **现状**：会写 ServerBootstrap 链式配置，但 initAndRegister → register0 → doBind0 → fireChannelActive → OP_ACCEPT 的源码链讲不全；说不出"register 为什么要投递到任务队列""interestOps 为什么先 0 后 ACCEPT"两个细节
- **架构师水平**：白板画出 bind 到第一个请求的时序图，标注每一步在哪个线程执行（main 还是 EventLoop）
- **补足方向**：对着 Netty 源码把 AbstractBootstrap.doBind 单步走一遍，重点标注线程切换点

### 差距2.2：Pipeline 传播方向混淆
> Day2发现

- **现状**：inbound/outbound 方向与"outbound 逆序"经常混；`ctx.write` 与 `channel.write` 说不出"传播起点"这个本质
- **架构师水平**：给定一条 pipeline（Decoder/Business/Encoder 顺序）秒答读写路径各经过哪些 handler；解释 Head/Tail 哨兵的兜底行为
- **补足方向**：手画双向链路图；写一个 5 handler 的 demo 打印进出顺序验证

### 差距2.3：EventLoop 三合一与调度细节空白
> Day2发现，延续并发周 Day05 差距（线程池）

- **现状**：说不出 select deadline 与 scheduledTaskQueue 联动、wakeup 成本、ioRatio 作用；"EventLoop 既是执行器又是定时器"的归纳没有
- **架构师水平**：从 run() 三层循环讲清 IO 与任务的时间片分配逻辑及任务排队延迟的监控手段
- **补足方向**：读 NioEventLoop.run 与 SingleThreadEventExecutor.execute 源码；给网关补 EventLoop 排队延迟指标

### 差距2.4：业务线程划分靠感觉
> Day2发现

- **现状**：什么 handler 挂 businessGroup 说不出判定标准（阻塞/CPU 重才移出）；不知道跨线程组的有序性保证机制与代价
- **架构师水平**：按"阻塞操作清单"逐条判定；能权衡"切线程开销 vs EventLoop 阻塞后果"
- **补足方向**：把判定清单变成代码评审 checklist；复盘简历项目 IM 网关哪些 handler 该移出 EventLoop

### 差距2.5：EventLoop 阻塞后果链没有量化敏感度
> Day2发现

- **现状**：算不出"worker 32 线程挂 10w 连接，阻塞 3s 影响多少连接"（约 3000+ 停摆 × 心跳超时 × 批量误杀的放大链）
- **架构师水平**：影响半径 = 总连接/worker 数；阻塞时长与心跳超时阈值的比值决定是否误杀
- **补足方向**：给 IM 网关做"EventLoop 阻塞→影响连接数"沙盘推演，写进项目预案

### 差距2.6：无锁化四手段与 FastThreadLocal 原理空白
> Day2发现，延续并发周差距（ThreadLocal）

- **现状**：FastThreadLocal 只知道"更快"，说不出数组下标 vs 开放寻址的实现差异；"串行化无锁"作为 Netty 核心设计哲学没有体系化认知
- **架构师水平**：从"让数据只被一个线程看见"的第一性原理出发，把四个无锁手段串成一句话
- **补足方向**：读 FastThreadLocal 与 InternalThreadLocalMap 源码；对照并发周 ThreadLocal 泄漏案例看 Netty 的 removeAll 兜底

## 三、通信协议设计与编解码（Day03）

### 差距3.1：粘包拆包讲不出根因层次
> Day3发现

- **现状**：四层根因（字节流无边界/MSS/Nagle/接收时机）讲不全；"UDP 为什么没有"答不出"数据报文有边界 vs 流无边界"的本质
- **架构师水平**：从 TCP 设计目标（流式可靠）推出"边界必须应用层重建"的必然性，而不是当 TCP 的 bug
- **补足方向**：内化"TCP 没有粘包问题，问题在你把流当消息用"的因果叙述

### 差距3.2：lengthAdjustment 靠背参数，不会现场推导
> Day3发现

- **现状**：五参数背过，换个头结构就算不准；"长度含头"场景不知道用负补偿
- **架构师水平**：用恒等式"帧总长 = offset + fieldLength + 长度值 + adjustment"现场推任意头结构
- **补足方向**：自己设计三个畸形头结构做推导练习

### 差距3.3：协议字段说不出存在理由
> Day3发现，延续 MQ 周差距（Kafka 协议）

- **现状**：帧结构画得出，但 magic 防误连、length 上限防 OOM 攻击、seqId 幂等去重的理由链条断裂——"每个字段是删掉会怎样的防御设计"这个视角没有
- **架构师水平**：每个字段一句存在理由 + 不设计的后果；能按业务裁剪字段
- **补足方向**：给 IM 协议每个字段写一行"删掉它会怎样"，作为面试话术

### 差距3.4：序列化选型缺乏量化与场景匹配
> Day3发现

- **现状**：说不出 Protobuf 比 JSON 小多少（约 1/4）、快在哪（生成代码 vs 反射）、兼容靠什么（tag + unknown fields）；Kryo 跨版本兼容风险不知道
- **架构师水平**：五维对比脱口而出，按约束（多端/流量敏感/演进频繁）匹配选型而非无脑 Protobuf
- **补足方向**：用同一消息对象实测 JSON/Protobuf 体积与耗时，拿到自己的数字

### 差距3.5：心跳参数没有"为什么"
> Day3发现

- **现状**：30s/90s 的三倍容错原则、心跳防 NAT 老化的真实价值、假死连接成本账讲不出
- **架构师水平**：从 NAT 超时（1~5 分钟）、GC 停顿、网络抖动的量级推导心跳参数；把踢连接讲成"容量卫生"
- **补足方向**：查证运营商 NAT 超时典型值；把假死连接成本账（fd+缓冲+Session+路由条目+堆积消息）写全

### 差距3.6：协议安全只想到 TLS
> Day3发现，延续限流降级周差距（分层防御）

- **现状**：漏了 magic 前置校验（防扫描）、maxFrameLength（防恶意长度 OOM）、鉴权首包+未认证零业务开销（防海量裸连接 DoS）三件更基础的
- **架构师水平**：按"资源消耗路径"设计防线——拦截点越早成本越低（第一字节最便宜）
- **补足方向**：把安全四件套与"最便宜拦截点"原则写进网关设计文档

## 四、Netty 高性能原理（Day04）

### 差距4.1：内存池只知道"有池子"
> Day4发现，延续 JVM 第2周差距（堆外内存）

- **现状**：讲不出 Arena/Chunk/Page/Subpage 分层、PoolThreadCache 无锁快路径、arena 内 synchronized 的锁粒度设计；"池高水位不回落是正常的"这个运维常识没有
- **架构师水平**：画出分配路径图（cache → arena → 新 chunk）；讲清"多 arena+线程缓存"与 LongAdder 分散热点同构
- **补足方向**：读 PooledByteBufAllocator.newDirectBuffer 调用链；Day07 深挖前记住骨架

### 差距4.2：引用计数规则没成肌肉记忆
> Day4发现

- **现状**：入站消息释放责任链（谁分配谁释放/传递即转移责任/Tail 兜底）讲不系统；广播 retainedDuplicate 的 N 份释放义务讲不清
- **架构师水平**：任意 handler 场景秒答"这条 ByteBuf 谁释放"
- **补足方向**：把责任链表抄进笔记；对照 Day03 解码器代码走一遍帧的生命周期

### 差距4.3：泄漏检测原理停留在"配个参数"
> Day4发现

- **现状**：说不出弱引用+引用队列+采样机制；"SIMPLE 下一条日志 = 至少 128 次泄漏"的量化含义没有
- **架构师水平**：讲清 DefaultResourceLeak 生命周期与"为什么生产只能采样"的开销账
- **补足方向**：读 DefaultResourceLeak 源码入口；把"采样日志→ADVANCED→PARANOID 压测"排查流程写进预案

### 差距4.4：slice/retain 系列所有权会算错
> Day4发现

- **现状**：slice 与 retainedSlice 的区别、slice 后原 buf 释放的悬空风险、release 归属，三题混在一起就错
- **架构师水平**："slice 是免费视图但不持有引用；retainedSlice 持有就必须还"一句话定型
- **补足方向**：写单测验证 slice 悬空（IllegalReferenceCountException）与 retainedSlice 泄漏（PARANOID 触发日志）

### 差距4.5：背压链路画不到 TCP 窗口
> Day4发现，延续限流降级周差距（流量治理）

- **现状**："autoRead=false → 接收缓冲堆积 → 通告窗口收缩 → 对端减速"的完整传导画不全；水位线按什么定没有方法论
- **架构师水平**：从对端慢到源头减速的六步链路白板画出；水位线按"单连接可容忍驻留内存 × 连接数 = 堆外预算"反推
- **补足方向**：抓一次 tcpdump 看通告窗口收缩；把链路图写进网关设计文档

### 差距4.6：堆外内存预算与容器账串不起来
> Day4发现，延续 K8s 周差距（OOMKilled）

- **现状**：被问"10w 连接网关堆外要留多少"给不出公式，说不清与 K8s memory limit、MaxDirectMemorySize 的关系
- **架构师水平**：预算公式 + 80% 红线 + allocator metric 三件套张口就来
- **补足方向**：给 IM 在线客服按公式算一遍预算，写进简历项目容量规划段（补 Day01 差距1.1 的作业）

## 五、IM 长连接网关实战（Day05）

### 差距5.1：架构分层靠"抄别家"，说不出决策依据
> Day5发现

- **现状**：画得出"网关+MQ+逻辑层"，但"为什么走 MQ 不直连""无状态化的判定测试是什么"答不深
- **架构师水平**：每个分层决策给出两个备选方案对比与取舍理由；"kill 任意网关只损连接不损数据"张口就来
- **补足方向**：把选型对比表内化成叙事；给简历项目补一页架构决策记录（ADR）

### 差距5.2：消息可靠性机制散装
> Day5发现，延续支付周差距（幂等三防闭环）

- **现状**：不丢/不重/不乱各自机制知道一些，但"推拉结合""缺口检测"收口动作讲不出；与支付幂等/MQ 最终一致性的同构没建立
- **架构师水平**：三句话框架——"唯一标识+确认重试+对账补偿"，跨 IM/MQ/支付三域举证
- **补足方向**：默画 2.1 流程图；对照支付周三防闭环整理同构对照表

### 差距5.3：下线路由清理的竞态没意识到
> Day5发现，延续 MQ 周差距（分布式锁）

- **现状**：闪断重连与踢除并发时"旧网关删掉新网关的路由记录"竞态九成人答不出；条件删除通则没沉淀
- **架构师水平**：所有分布式删除操作都校验"归属/版本"——与分布式锁释放校验持有者同构
- **补足方向**：把竞态写进"分布式删除通则"笔记，面试主动讲是强区分点

### 差距5.4：没做过连接迁移
> Day5发现，延续 K8s 周差距（发布工程）

- **现状**：摘流量→停新连→错峰重连→drain→条件清理的完整流程没实操；terminationGracePeriodSeconds 默认 30s 的坑不知道
- **架构师水平**：把 Day02 优雅关闭三段式放大到 10w 连接规模并指出每步兜底
- **补足方向**：给简历项目补写"发布工程"段落；测试环境演练一次连接迁移

### 差距5.5：容量叙事仍是"背账本"，没做过压测闭环
> Day5发现，延续 Day01 差距1.1
