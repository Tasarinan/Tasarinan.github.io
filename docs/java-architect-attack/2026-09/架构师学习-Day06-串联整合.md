## 场景选择：为什么选"重连风暴全链路复盘"

### 为什么选这个场景

全链路场景一次性用到本周全部知识点：

```text
Day01 模型与epoll   → 现象1：重连洪峰 12w/s 打爆 accept 队列（SO_BACKLOG）、fd 与容量账
                      重连风暴的本质 = C10K 的"瞬时反向问题"：不是稳态连接多，是建连速率爆炸
Day02 线程模型      → 现象2：鉴权同步 RPC 阻塞 EventLoop → 同 Loop 全部连接停摆
                      → 90s 后心跳误杀 → 二次断连雪崩（后果链完整现形）
Day03 协议与心跳    → 现象3：心跳三倍容错被 EventLoop 阻塞击穿（90s 读空闲误判）；
                      重连风暴中的异常帧（半包/超长）与 magic 前置校验的价值
Day04 性能与背压    → 现象4：离线消息推送风暴 × 弱网客服端 → ChannelOutboundBuffer 堆积
                      → 堆外内存暴涨 → 容器 OOMKilled（预算公式没落地的直接后果）
Day05 网关架构      → 现象5：全量拉离线（无增量 seq）打爆逻辑层；路由表在二次断连中
                      写入/删除交错；缺少错峰重连与降级开关的代价
```

单点故障（比如只看 OOM）看不到"重连风暴如何把五个独立缺陷串成雪崩"。本案例的多米诺结构：

```
网络抖动（外部诱因，28s，不可控）
   → 客户端重连风暴（缺陷A：无退避无抖动）
      → 鉴权洪峰（缺陷B：鉴权依赖远程 RPC）
         → EventLoop 阻塞 → 心跳误杀（缺陷C：阻塞混入 IO 线程的放大链）
            → 二次断连 → 重连风暴自持续
      → 离线消息洪峰（缺陷D：全量拉取+推送不分级）
         → ChannelOutboundBuffer 堆积 → 堆外 OOMKilled（缺陷E：容器账漏算堆外）
            → 网关减容 → 雪崩再放大
```

**每根多米诺骨牌都是本周某一天的"差距"**。这正是串联复盘的价值。

### 这个场景与用户的贴合度

1. **用户当前公司业务**：啄木鸟云健康 IM 在线客服是简历核心项目，本周 Day05 刚完成它的完整设计——用一次故障检验自己的设计是最高效的复习
2. **与 Day05 的关系**：Day05 的设计是"应该怎么做"，Day06 的复盘是"不这么做会发生什么"——正反对照，双向巩固
3. **真实事件原型**：2015 年 Slack 停机、微信/钉钉历史上多次因网络抖动引发的重连风暴是公开案例（AWS/机房故障后的 reconnect storm），面试官大概率听说过，叙事可信度高
4. **为 Day07 埋钩子**：现象4 的堆外内存暴涨在 Day06 用"水位+预算"止损，Day07 将深挖"如果它不是堆积而是泄漏"的另一个故事

## 业务背景

```text
啄木鸟云健康 2026年09月08日（周二）上午 10:20 - 11:05（总影响 45 分钟）：

故障范围：IM 在线客服长连接网关集群（自建 Netty 网关）
故障等级：P0（客服通道整体不可用）
业务影响：
  - 在线连接从 38.2w 跌至 4.1w，持续 25 分钟低于 50%
  - 消息端到端延迟 P99 从 800ms 涨到 31s
  - 2 台网关 Pod OOMKilled 重启
  - 客服会话中断 9200 路，客诉 137 起（患者等不到回复）
  - 鉴权服务（下游）被打挂 6 分钟，连带 App 其他功能登录异常

系统现状（事发前）：
  - im-gateway：Netty 4.1 + NIO transport（未上 Epoll 原生），K8s 4 副本，4C8G
    （-Xmx4g，未显式设置 MaxDirectMemorySize，容器 limit 8G）
  - 鉴权：AUTH 首包 → EventLoop 内同步调 auth-service（HTTP，超时 200ms）
    （无本地 token 缓存——"过渡方案，等鉴权服务加缓存接口"）
  - 客户端：固定 3s 间隔无限重连（无退避、无抖动）；重连成功后全量拉离线消息
  - 离线消息：无分页无合并，一次性推送（"先跑起来再优化"）
  - SO_BACKLOG：1024（默认参考值没人动过）
  - 监控：有在线数、连接速率大盘，无告警阈值（"看板有了就行"）

故障前一周变更：无（本次故障与变更无关，纯外部诱因 + 存量缺陷引爆）
流量背景：工作日上午高峰，客服会话 1.2w 路，在线连接 38.2w
```

**为什么五个缺陷平时没暴露**：

| 隐患 | 平时表现 | 风暴引爆条件 |
|------|---------|---------------|
| 客户端固定 3s 重连 | 单个用户偶发断线，重连 1~2 次成功，无感知 | 38w 客户端同时断线 → 12w/s 建连洪峰 |
| 鉴权同步 RPC 在 EventLoop | 鉴权服务 P99 5ms，阻塞可忽略 | 全量重连 = 鉴权 QPS 万级 → 鉴权服务过载 → 200ms 超时 → EventLoop 大面积阻塞 |
| EventLoop 阻塞 | 从未发生（鉴权快） | 一旦发生即心跳误杀 → 二次断连 |
| 全量拉离线 | 单用户离线消息几条 | 风暴后人均 20+ 条 → 逻辑层/DB 洪峰 |
| 容器账漏算堆外 | 堆外用量 2G 左右稳定 | 推送堆积 → 堆外涨破 limit → OOMKilled |

## 第一部分：故障时间线（全链路视角）

### 1.1 时间线总览

```text
10:20:00  机房核心交换机主备切换，抖动 28 秒（事后网络组确认）
10:20:28  网络恢复。38.2w 客户端 TCP 断链感知（RST/超时），进入重连
10:20:31  ★重连洪峰形成：固定 3s 间隔 + 无抖动 → 第一波约 12w/s 建连
10:20:33  现象1：网关 accept 队列溢出（BACKLOG 1024），大量 SYN 被丢弃重试
          客户端表现为"连接超时"→ 3s 后再试 → 洪峰自持续
10:20:40  现象2：建连成功的连接涌入 AUTH → auth-service QPS 8w+ → 过载
          EventLoop 内同步调用大面积 200ms 超时 → 单个 EventLoop 每秒
          最多处理 5 个鉴权 → 已建连的会话读停摆
10:21:15  auth-service 被打挂（线程池耗尽），鉴权全部超时
10:22:10  现象3：停摆累计超过 90s 的连接被 IdleStateHandler 误杀
          （第一批已建立连接二次断开 → 加入重连洪峰 → 风暴自增强）
10:22:30  现象4：部分鉴权成功（缓存恢复前少量通过）+ 老连接存活部分：
          离线消息一次性推送 + 弱网客服端收不动
          → ChannelOutboundBuffer 单连接堆积数 MB → 堆外用量爬升
10:24:05  值班发现：在线数曲线断崖（38w→11w）+ 同事口头报告"App 客服进不去"
10:24:30  现象5：gateway-2、gateway-4 堆外涨破容器 limit → OOMKilled
          → 其上连接全部断开 → 洪峰再 +20% → 剩余 2 台更艰难
10:25-10:37  止血阶段（见 1.3）
10:37  连接数止跌回升（错峰重连配置生效 + 集群恢复）
11:05  在线数回到 37w+，消息 P99 恢复 900ms，故障关闭
```

### 1.2 阶段 1：发生与发现——监控缺位的代价

**发现路径复盘**（这部分最刺痛）：

| 指标 | 实际可用性 | 本应触发 |
|------|-----------|---------|
| 在线连接数骤降 30% | 大盘有图、无告警 | 10:21 即告警（提前 3 分钟） |
| 新建连接速率 10 倍 | 有图、无告警 | **10:20:35 即告警（提前 4 分钟）** |
| EventLoop 任务排队延迟 | **根本没有这个指标** | 10:20:40（阻塞开始即发现） |
| isWritable=false 连接数 | 没有指标 | 10:22:30（堆积开始即发现） |
| 堆外内存用量 | 没有指标（OOMKilled 才知道） | 10:23（提前 90 秒，够扩容） |

Day05 的"监控八指标"在本案例中：有图的 2 个没配告警，其余 6 个不存在。**发现故障靠人肉，定位故障靠猜**。

### 1.3 阶段 2：12 分钟止血——决策优先级

```text
10:25  拉群，网关/鉴权/逻辑层 owner 到位。第一判断：不是发布（无变更），排除回滚选项
10:26  决策1【扩容】：网关 4 → 8 台（HPA 手动设 min）
       依据：accept 洪峰是容量问题——Day01 账本：建连速率 ÷ 单机 accept/鉴权能力
10:28  决策2【切断放大器】：鉴权降级开关——EventLoop 跳过 RPC，
       用本地 JWT 验签（无状态 token 事先支持，只是没启用）
       依据：EventLoop 阻塞是最大放大器，先断它
10:31  决策3【降需求】：关闭离线消息推送（功能降级），改为客户端按需拉取
       依据：推送风暴是下游洪峰源头 + 堆外堆积源头
10:34  决策4【错峰】：通过配置中心下发客户端重连配置（min=5s, max=120s, 抖动±50%）
       限制：只对"已连上的客户端"生效——风暴中大多数客户端根本连不上，
       配置下发只对后续恢复有效 → 这一步的教训写进防线（重连参数必须内置默认值）
10:37  洪峰衰减：扩容节点开始分担 + 已连接客户端错峰 → 连接数回升
```

**止血决策的模式**（与并发周 Day06 相同的优先级框架）：

```
① 先断放大器（EventLoop 阻塞链、推送洪峰）——不然扩容填不满黑洞
② 再扩容量（accept/鉴权洪峰）
③ 同时降需求（可丢功能降级：离线推送）
④ 最后改行为（错峰配置）——生效最慢、对存量风暴作用有限
```

### 1.4 阶段 3：30 分钟定位——四路并行的取证

```bash
# 路1：网关侧（10:26-10:33）
$ kubectl top pods -n im | grep gateway      # CPU 正常（40%）——不是算力问题
$ jstack <pid> | grep -A 5 "nioEventLoopGroup"   # EventLoop 线程栈：
    #   at java.net.SocketInputStream.socketRead0   ← ★阻塞在鉴权 HTTP 调用
    #   16 个 worker 线程中 14 个同栈 → EventLoop 大面积阻塞实锤
$ ss -lnt | grep 8080   # Recv-Q 满（accept 队列溢出实锤）：backlog 1024，实际堆积 1024+

# 路2：鉴权服务（10:28-10:31）
$ arthas dashboard / thread   # 线程池耗尽，全部 WAITING 在 DB 连接池
    # 根因链：鉴权 QPS 8w（平时 500）→ DB 连接池 50 打满 → 排队超时

# 路3：资源侧（10:30-10:36，OOMKilled 之后）
$ kubectl describe pod gateway-2 | grep -A 3 "Last State"
    # Reason: OOMKilled  Exit Code: 137
$ 事发前监控回看（heap 有图）：heap 4G 中只用了 1.3G ← 不是堆内 → 堆外
    # 推算：38w/4 台连接均摊 + 推送堆积 → 堆外 > 3.5G，limit 8G - heap 4G - meta/栈 ≈ 3.2G 余量 → 撞墙

# 路4：客户端行为（10:33-10:37）
$ 网关接入日志聚合：建连来源 IP 无差别 3s 周期重试 → 固定间隔重连实锤
$ AUTH 后离线拉取量：人均 22 条 × 全量 → 下游洪峰实锤
```

**四路结论在 10:37 汇合**，得到完整因果链（1.1 已画）。定位耗时 13 分钟——如果有 Day05 的八指标，四路取证中的两路（EventLoop 延迟、堆外用量）本来就是实时告警，预计可压缩到 5 分钟。

### 1.5 阶段 4：根因——现象 → 知识点 → 缺陷映射

| 现象 | 本周知识点 | 代码/配置级根因 |
|------|-----------|----------------|
| accept 队列溢出、建连超时 | Day01 容量账 / SO_BACKLOG | backlog=1024 从未按"重连风暴速率"评估；无错峰设计（客户端缺陷） |
| EventLoop 阻塞、会话停摆 | Day02 线程模型 | EventLoop 内同步 HTTP 鉴权（200ms 超时）；无本地 token 缓存 |
| 心跳误杀、二次断连 | Day02/Day03 心跳三倍容错 | 90s 读空闲被"停摆"击穿——容错设计没错，错的是让阻塞混入 IO 线程 |
| 推送堆积 → 堆外 OOMKilled | Day04 水位背压 / 堆外预算 | 无 WritabilityChanged 处置策略；堆外没进容器 limit 账（Day04 公式未落地） |
| 离线全量拉取打爆下游 | Day05 推拉结合/分级 | 无分页无合并；通知类与消息类未分级，全部走不可丢推送 |
| 风暴自持续 45 分钟 | Day05 错峰重连 | 客户端固定 3s 重连无退避无抖动，重连参数硬编码不可配置 |

**根因分类（四类）**：

```
A 客户端行为缺陷：重连无退避无抖动；重连参数硬编码
B 网关代码缺陷：EventLoop 阻塞；无背压策略；NIO 未上 Epoll（本次非根因但列入整改）
C 容量与资源缺陷：BACKLOG 未评估；堆外未入容器账；无扩容预案
D 体系缺陷：告警缺失（八指标只覆盖 2 个且无阈值）；无降级开关设计
```

### 1.6 阶段 5：24 小时修复——PR 清单与验证

```text
PR1（客户端，P0）：重连指数退避 + 抖动：1s→2s→4s→…→max 120s，每次 ±50% 随机；
    参数服务端可配 + 内置兜底默认值（配置拉不到也用安全值）
PR2（网关，P0）：鉴权异步化——AUTH 处理移入 businessGroup（Day02 规约），
    EventLoop 只做解码与转发；验签结果回 EventLoop 写响应
PR3（网关，P0）：鉴权本地化——JWT 本地验签（无状态 token），
    Redis 黑名单兜底；彻底消灭"每连接一次远程调用"
PR4（网关，P1）：背压分级——WritabilityChanged 处置（通知丢弃/消息转离线/超时踢除）
PR5（网关，P1）：SO_BACKLOG 4096 + Linux 层 somaxconn 对齐；transport 切 EpollEventLoopGroup
    （SO_REUSEPORT 提升多机 accept 分摊）
PR6（逻辑层，P1）：离线消息按 seq 增量拉取 + 分页（50/页）+ 令牌桶限速 + 会话折叠摘要
PR7（SRE，P0）：容器账重算——显式 MaxDirectMemorySize、堆外预算入 limit、
    8G limit → 12G（按 Day04 公式重新推导）
```

## 第二部分：根因深度剖析（错误代码 → 正确代码对照）

### 2.1 客户端重连策略（Day01/Deny05：错峰）

```java
// ✗ 错误：固定间隔无限重连——38w 客户端的"DDoS 自愿军"
while (!connected) {
    try { connect(); break; }
    catch (Exception e) { Thread.sleep(3000); }   // 固定 3s，所有客户端同步
}

// ✓ 正确：指数退避 + 随机抖动 + 可配置 + 兜底默认值
public long nextBackoffMs(int attempt) {
    long base = Math.min(config.retryBaseMs /*1000*/,
                         config.retryMaxMs /*120000*/ >> attempt); // 指数 1s,2s,4s...
    long jitter = (long) (base * 0.5 * (ThreadLocalRandom.current().nextDouble() * 2 - 1));
    return base + jitter;   // ±50% 抖动：洪峰被摊平成窗口
}
// config 从服务端下发 + 本地兜底：配置拉不到时用编译期默认值（PR1 的教训）
```

**量化效果**：38w 客户端、指数退避 + 抖动后，建连洪峰从 12w/s 降到约 2k/s（客户端在 1~120s 窗口内近似均匀分布）——**降 60 倍，一行抖动代码**。

### 2.2 鉴权阻塞 EventLoop（Day02：后果链）

```java
// ✗ 错误：EventLoop 内同步 RPC——平时 5ms 无感，风暴时是雪崩放大器
public class AuthHandler extends SimpleChannelInboundHandler<Packet> {
    protected void channelRead0(ChannelHandlerContext ctx, Packet p) {
        if (p.type == AUTH) {
            AuthResponse r = authService.verify(p.token);  // HTTP 同步调用，200ms 超时
            ctx.writeAndFlush(authAck(r));                 // 这期间本 EventLoop 上
        }                                                   // ~1w 连接全部停摆
    }
}

// ✓ 正确1：移出 EventLoop（治标）——businessGroup 承担阻塞调用
pipeline.addLast(businessGroup, "auth", new AuthHandler());
// ✓ 正确2：本地验签（治本）——鉴权从"每连接一次远程调用"变"每连接一次本地 CPU"
if (jwtVerifier.verify(token)) {   // HMAC 验签 <0.1ms，EventLoop 内做也不慌
    // Redis 黑名单兜底：只查"登出/踢出"集合，miss 即通过
}
```

**两层修复的关系**：businessGroup 解决"阻塞不再伤害 IO 线程"（Day02 规约），本地验签解决"风暴时鉴权洪峰本身"（Day05 鉴权本地化）。**只做前者，auth-service 仍会被 8w QPS 打挂**——两个 PR 缺一不可。

### 2.3 心跳误杀的辩证（Day03：三倍容错的边界）

90s 读空闲 + 三倍容错的设计**没有错**，但它防的是"客户端假死"，防不了"服务端自己停摆"。本案例的教训不是改心跳参数（把 90s 调到 270s 只是掩盖问题且拖延假死清理），而是**保证读空闲的"读"不被别的职责阻塞**——即 2.2。**参数调优不能替代架构修复**。

### 2.4 背压分级缺失（Day04：水位与堆外预算）

```java
// ✗ 事发时：没有 WritabilityChanged 处理——弱网客服端的推送无差别堆积
//   离线消息 22 条 × 2KB × 弱网端 3000 个 ≈ 单机数百 MB 堆外 → 撞墙

// ✓ 正确：按可丢性分级（Day05 策略的代码化）
@Override
public void channelWritabilityChanged(ChannelHandlerContext ctx) {
    if (!ctx.channel().isWritable()) {
        Session s = session(ctx.channel());
        s.setPushMode(SLOW);                       // 降级模式
        pendingNotifier.drainAndDrop(s, NOTICE);   // 通知类：丢弃（客户端拉取兜底）
        offlineInbox.transfer(s, MESSAGE);         // 消息类：转离线收件箱
        if (s.slowSince().plus(5, MINUTES).isBefore(now())) ctx.close(); // 超时踢除
    }
}

// ✓ 正确：堆外预算落地（PR7）——Day04 公式
//   堆外预算 = 连接数/单机 × (读缓冲 + 高水位 64KB) + 推送峰值 × 扇出 + 余量
//   limit = -Xmx(4G) + MaxDirectMemorySize(显式 5G) + meta/栈/缓存(~1.5G) + 20% 余量 ≈ 12G
```

### 2.5 离线消息洪峰（Day05：推拉结合与分级）

```text
✗ 事发时：重连成功 → 服务端一次性推送全部离线消息（22 条均值，含通知类）
   38w 客户端 × 22 条 = 800w+ 消息洪峰，叠加扇出 → 逻辑层/DB/网关三重打击

✓ 正确：
   ① 连接建立只推"会话摘要"（未读数+最新一条，Day05 折叠策略）
   ② 客户端上报 lastSeq → 服务端按 seq 区间分页（50/页）提供拉取 API
   ③ 令牌桶限速（每连接 2 页/s）——洪峰被整形
   ④ 通知类进可丢通道，消息类才进可靠通道
   效果：推送量从 800w 降到 38w 条摘要；DB 压力从洪峰变平滑队列
```

### 4.1 3 分钟版（电话面 / 快问快答）

### 4.3 高频追问预演

1. **"为什么心跳 90s 会误杀？调大不就行了？"** → 误杀根因是 EventLoop 停摆不是心跳参数；调到 270s 只是延长雪崩且拖延假死清理。**参数优化不能替代架构修复**（2.3）
2. **"错峰为什么有效？怎么量化的？"** → 38w 客户端固定 3s = 周期性洪峰；退避+抖动把重连时间摊到 1~120s 近似均匀分布 → 峰值建连速率降 60 倍。数学本质：把 δ 函数摊成均匀分布
3. **"OOMKilled 为什么堆没事？"** → 容器 limit 管的是整个 cgroup RSS：堆 + 元空间 + **堆外**（Netty direct pool）+ 栈。事发配置只算了堆。堆外用量看 allocator metric，OOMKilled 前堆内可能很健康（K8s 周 + Day04 的交点）
4. **"如果鉴权服务永远恢复不了呢？"** → 本地验签是正解的一部分（JWT 无状态），黑名单 Redis 挂了可退化为"放行 + 事后审计"的兜底策略——按损失可控性排优先级（安全 vs 可用的权衡叙事）
5. **"扩容为什么有效？瓶颈不在鉴权吗？"** → 有效的前提是先切断放大器（PR2/PR3）：鉴权本地化后瓶颈回到 accept/CPU 这类可水平扩展的资源；否则扩容只是给黑洞填机器——**扩容前必须先定位瓶颈可扩展性**
