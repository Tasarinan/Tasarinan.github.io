## 一、架构师视角下的网络编程模型

### 1.1 不只是"BIO 慢 NIO 快"，是两次范式转移

很多工程师把网络编程模型当成"知识点排序"——BIO 过时了、NIO 先进。架构师视角下，这是一部**两次范式转移**的历史：

| 时代 | 范式 | 转移内容 | 代表 |
|------|------|---------|------|
| C10K 之前 | thread-per-connection | —— | 早期 Tomcat、传统 RPC |
| C10K（2000s） | event-loop + epoll | **绕过"线程"**：线程不再代表连接，代表一批连接上的事件 | Netty、Redis、Nginx、Node.js |
| C10M（2013+） | kernel bypass | **绕过"内核"**：用户态驱动网卡、用户态协议栈 | DPDK、F-Stack、高频交易 |
| 虚拟线程（2023+） | "回归"同步模型 | **绕过"回调地狱"**：epoll 底座不变，把事件回调翻译回同步写法 | JDK 21+、Go runtime（早已如此） |

**架构师的关键判断力**：我的系统在哪个量级、什么活跃度分布，就选哪个范式的工具。99% 的业务（包括 IM 在线客服）在 C10K~C100K 区间，event-loop 范式（Netty）就是终态；开口就 DPDK 的是背概念，能报"每连接 10~50KB"的才是做容量的人。

### 1.2 "连接模型"到"事件模型"的思维切换

这是本周（也是 Netty 学习）最重要的一次思维重置：

| 连接模型（BIO） | 事件模型（NIO/Netty） |
|----------------|----------------------|
| 一个线程拥有一个连接 | 一个线程看管一批连接 |
| 状态在**线程栈**上（局部变量、阻塞点） | 状态在**Channel/Session 对象**上（attachment、Pipeline） |
| "读消息"是顺序代码 | "读消息"是状态机的又一次转移 |
| 慢 = 线程阻塞 | 慢 = 事件循环积压（延迟） |

**推论**：事件模型下，"一个连接的处理"不再是一个函数调用栈，而是被"就绪事件"切成多段、跨多次事件循环拼接起来——所以**必须有地方存半成品状态**（原生 NIO 的 attachment、Netty 的 ChannelHandlerContext 与解码器累积缓冲）。Day03 粘包拆包的全部复杂性都源于此。

### 1.3 为什么阻塞点位置决定一切

三代模型的本质差异只有一个变量：**阻塞点在哪一层**。

```
BIO：     [accept 阻塞] + [每连接一个 read 阻塞]        → 阻塞点数 = 连接数
伪异步：  同上，只是线程数有上限                          → 没解决，只限制
NIO：     [一个 select() 阻塞，替所有连接等]             → 阻塞点数 = 1
AIO：     [无阻塞，内核完成后回调]                       → 阻塞点数 = 0（Linux 上是伪装的）
```

**架构师洞察**：伪异步 IO（线程池包 BIO）的失败告诉我们——**优化"阻塞的代价"不如消除"阻塞的必要性"**。线程池解决"创建线程贵"，不解决"线程无所事事却被占住"。这个思想在架构上反复出现：连接池缓解不了长事务、加机器缓解不了串行瓶颈。

## 二、IO 多路复用的本质：事件驱动，不是扫描驱动

### 2.1 select/poll/epell 的分水岭：谁在发现就绪

- **select/poll**：每次调用**全量扫描**——"我给你 10w 个 fd，你挨个看一遍谁就绪了"。成本与**总连接数**成正比
- **epoll**：注册一次，就绪事件**自己挂上链表**（`ep_poll_callback` 回调）——"有事件我再告诉你"。成本与**活跃连接数**成正比

```
select/poll:   每轮 = 拷贝全集 + 扫描全集 + 返回全集 + 用户再扫一遍
epoll:         注册一次(ctl) + 每轮只取就绪链表(wait)
```

### 2.2 反直觉边界：epoll 不是永远赢

| 活跃度分布 | select/poll | epoll | 谁赢 |
|-----------|-------------|-------|------|
| 10w 连接，1% 活跃（长连接网关） | 每轮扫 10w | 每轮处理 1k | **epoll 完胜** |
| 1w 连接，100% 活跃（代理转发） | 每轮扫 1w | 每轮处理 1w + 红黑树/回调常数开销 | 基本平手 |

**架构师选型依据是系统的活跃度分布**，不是"新的一定好"。IM 长连接、推送、监控上报全是稀疏活跃——这就是为什么这一代基础设施清一色 Reactor。

### 2.3 LT/ET 的工程权衡

- **LT（水平触发）**：没读完会反复提醒你——**容错高、心智低**，Redis 的选择，也是 JDK Selector 的语义
- **ET（边缘触发）**：只在状态跳变提醒一次——**性能高、纪律严**（必须非阻塞 + 一次读完），Nginx 与 Netty Epoll 原生 transport 的选择

**架构师认知**：ET 是"你保证一次做完，我保证不啰嗦"的契约——契约不履行（中途返回）就丢事件。用 ET 的系统必须把"读到 EAGAIN"做成框架级代码（Netty 的 unsafe read loop），不能依赖业务自觉。

### 2.4 与 Netty 的衔接：为什么有 Epoll 原生 transport

JDK Selector 给你的是"跨平台的最大公约数"（LT、无内核参数、有空轮询 bug）。Netty Epoll transport 的价值 = **平台红利**（ET、SO_REUSEPORT、TCP_FASTOPEN）+ **bug 免疫** + **少一层抽象**。架构师思路：跨平台抽象支付了性能税，在 Linux 单一部署环境下这笔税可以合法免掉。

## 三、内存维度：heap/direct 到内存池的因果链

### 3.1 一条必须背熟的因果链

```
JVM 堆内对象会被 GC 移动
  → 内核 write/read 要求内存地址稳定
  → JDK 对 heap buffer 做 socket IO 时偷偷拷贝到临时 DirectByteBuffer（多一次 CPU 拷贝）
  → 于是 IO 路径该用 direct buffer
  → 但 direct 分配贵（unsafe + 计数锁，失败还触发 System.gc()）
  → 于是 Netty 做了 PooledByteBufAllocator（池化复用）
  → 池化 + 引用计数 → 忘 release 就堆外泄漏 → ResourceLeakDetector
  → Day04 高性能原理 / Day07 内存管理深挖
```

每个环节都是下一个设计的原因。**面试官问"Netty 为什么有内存池"，答案起点在 JVM 的 GC 会移动对象，不在 Netty。**

### 3.2 heap vs direct 选型决策树

```
数据要过 socket/文件 IO 边界？
 ├─ 是 → direct buffer（配合池化）→ 尽快解码成 POJO 后立刻释放
 │        （direct 上做逐字段业务解析比堆内慢，价值只在内核↔缓冲区那一跳）
 └─ 否（纯业务计算/测试） → heap buffer（分配便宜、GC 管理）
```

### 3.3 容器时代的堆外内存账（衔接 K8s 周 + JVM 堆外内存周）

```
容器 memory limit = 堆(-Xmx) + 元空间 + 堆外(direct/MaxDirectMemorySize)
                  + 线程栈(N×Xss) + JVM 开销(code cache/JIT)
```

**漏算堆外是 OOMKilled 的常见根因**。Netty 网关的 direct 用量 = 活跃连接数 × 缓冲水位，必须纳入容量公式。这是"JVM 调优周的堆外内存事故"与"网络编程周的内存池"两条线在本周的交汇点。

### 3.4 零拷贝的三层含义（面试常被混为一谈）

| 层次 | 机制 | 方向限制 | 代表 |
|------|------|---------|------|
| 内核态零拷贝 | sendfile（transferTo） | **仅 file→socket** | Kafka 消费拉取、Netty FileRegion |
| 内存映射 | mmap（MappedByteBuffer） | file↔内存 | RocketMQ CommitLog |
| 应用层"零拷贝" | CompositeByteBuf / slice（逻辑组合，不物理拷贝） | 无 | Netty 协议拼装（Day04） |

**能画出"4 次拷贝 4 次切换 → 2 次拷贝 2 次切换"的路径图，并说明 DMA gather 从页缓存直取**，是这个考点的满分线。

## 四、Reactor 线程模型：串行化无锁的架构价值

### 4.1 三形态的演进逻辑

```
单线程 Reactor：一切串行 —— 无锁，但慢 Handler 卡全部、单核上限
     ↓ 把 CPU 密集业务卸载
多线程 Reactor：IO 分发单线程 + 业务线程池 —— 业务不卡 IO 了，但 IO 读写仍单点
     ↓ 把 IO 也水平扩展
主从 Reactor：boss 专 accept + N 个 worker 各管一批连接 —— accept 与 IO 隔离、多核扩展
```

每次演进都在回答同一个问题："**串行保住了无锁，但串行也限制了吞吐——哪一段该串行，哪一段该并行？**"

### 4.2 Netty 的答案：Channel 绑定 EventLoop = "按连接切分串行域"

并发周的核心结论：**减少锁竞争的最佳方式是不共享**。Netty 的落地：
- 一个 Channel **终身属于一个 EventLoop**，它的所有事件与 Pipeline 调用都在该线程串行执行
- 连接内：天然有序、无锁、handler 可写成无状态机
- 连接间：不同 EventLoop 互不干扰，多核扩展
- 需要全局共享的状态（Session 表、路由表）才回到并发工具（ConcurrentHashMap、读写锁）——**锁的粒度从"整个服务"缩小到"真正全局的那几个数据结构"**

**架构师认知**：这是"线程模型图决定并发正确性"的范例。先画图（几个 EventLoop、业务在哪个线程、什么状态被谁独占），再写代码。

### 4.3 Redis 单线程 vs Netty 多线程：瓶颈分析范式

| | Redis 6.0 前 | Netty 网关 |
|---|---|---|
| 单事件成本 | 内存操作，微秒级 | IO + 编解码 + 可能的 TLS，高一个量级 |
| 瓶颈位置 | 内存带宽/网络，非 CPU | CPU（解码/加密）与 IO |
| 结论 | 单线程是"正确的偷懒" | 必须 multi-reactor |

Redis 6.0 引入多线程 IO（read/parse/write 卸载、命令执行仍单线程）佐证了分层思想：**IO 线程与业务线程分离是普适的，但"该守住的串行域"要守住**。架构师做线程模型设计时的通用三问：单事件成本多高？CPU 还是 IO 瓶颈？哪些状态必须串行访问？

## 五、原生 NIO 陷阱 → Netty 设计：一张"痛点-解药"映射表

| 原生 NIO 陷阱（事故形态） | Netty 解药 | 背后的架构原则 |
|--------------------------|-----------|---------------|
| select() 空轮询（CPU 100%，与业务无关） | Selector 重建（阈值 512） | 绕不过的 bug 就隔离它（坏资源抛弃重建） |
| OP_WRITE 常注册（就绪风暴）| 只在写不完整时注册，写完取消 | 事件订阅要反映"真实需要"，不是"可能有用" |
| 慢消费者把发送缓冲堆爆 | ChannelOutboundBuffer + 水位（32K/64K）+ isWritable 背压 | 过载要有显式信号，不能靠内存爆掉才发现 |
| 粘包半包（消息错乱） | ByteToMessageDecoder 体系 | 字节流→消息的边界重建要框架化 |
| Selector 非线程安全 | EventLoop 串行 + 任务队列 | 把线程安全问题转化为单线程消息驱动 |
| 心跳/重连样板 | IdleStateHandler + schedule 退避 | 连接生命周期管理要组件化 |

**架构师读法**：Netty 的每个核心组件都不是"功能"，是某类生产事故的**解药**。按事故学框架，比按 API 文档学，记得牢、讲得出（面试讲"为什么"永远比"是什么"值钱）。

## 六、IM 在线客服网关的选型决策实战

### 6.1 容量推算（面试量化叙事）

```
目标：峰值 50w 在线客服会话连接
单机容量（16C32G，Netty Epoll + 池化 direct）：
  - 连接内存：10w × 10~50KB ≈ 1~5GB（direct 纳入 MaxDirectMemorySize 预算）
  - EventLoop：boss 1 + worker 32，业务线程池独立
  - fd：10w（ulimit -n 调到 100w+）
  - 带宽：峰值消息速率 × 平均包大小 × 冗余
→ 50w / 10w = 5 台 + 30% 余量 ≈ 7 台（考虑滚动发布摘流量）
```

### 6.2 技术选型三层叙事

1. **协议层**：WebSocket 主推（全双工、二进制帧、ping/pong）+ 长轮询降级（内网防火墙/老浏览器）；纯通知走 SSE
2. **框架层**：Netty 而非 Tomcat-WebSocket（长连接非容器一等公民、自定义二进制协议难）、非 WebFlux（底层就是 Netty，多付响应式复杂度）、非自研（痛点清单=工作量清单）
3. **部署层**：Linux 原生 Epoll transport + SO_REUSEPORT（惊群正解 + accept 扩展）；LB 会话保持或网关连接级路由

### 6.3 虚拟线程问题的标准答案

分两层：
- **线程模型层**：虚拟线程的网络 IO 底层就是 epoll（`sun.nio.ch.Poller`）+ 调度器，它把事件回调翻译回同步写法——**是同一底座的另一种编程模型，不是机制替代**。简单服务用虚拟线程同步写法更划算
- **框架能力层**：Netty 的 Pipeline 生态、内存池、零拷贝、transport 切换、背压水位不受影响；虚拟线程还有 pin 风险（JDK 24 JEP 491 解决）、无连接级内存控制
- **结论**：IM 网关选 Netty；关注 io_uring + 虚拟线程的组合演化，那才可能改变格局

## 七、本日核心认知

1. **阻塞点位置决定模型**：BIO 的阻塞点=连接数，NIO=1，AIO=0；优化的方向是消除阻塞的必要性，不是降低阻塞的代价
2. **epoll 的本质是"事件自己上门"**（回调挂就绪链表），成本 O(活跃数)；100% 活跃时无优势——选型看活跃度分布
3. **NIO 是同步非阻塞**；Linux AIO 是 epoll 伪装的伪异步；io_uring 才是真异步的未来
4. **flip/compact 状态机**是字节流→消息边界重建的地基，compact 是半包累积的关键
5. **heap buffer 做 IO 有隐性拷贝**（临时 DirectByteBuffer）→ direct → 池化 → 引用计数 → 泄漏检测，一条因果链通到 Day04/Day07
6. **零拷贝三层**：sendfile（仅 file→socket）/ mmap / 应用层逻辑组合（CompositeByteBuf）
7. **Reactor 三形态**的演进逻辑是"哪一段该串行、哪一段该并行"；Netty 的 Channel 终身绑定 EventLoop = 按连接切分串行域，是"减少共享"的极致应用
8. **Netty 每个组件都是某类生产事故的解药**：按事故学 Netty，按 API 学只会忘
9. **容量叙事的三个数字**：每长连接 10~50KB、线程栈 1MB、上下文切换 1~10μs——架构师与八股的分水岭
10. **虚拟线程与 Netty 共享同一个 epoll 底座**：是编程模型的竞争，不是机制的替代
