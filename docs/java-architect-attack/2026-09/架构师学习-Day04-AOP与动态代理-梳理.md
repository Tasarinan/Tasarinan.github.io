## 一、代理是"方法调用层的流量中间层"

Day04 最重要的升维：把 Spring AOP 从"框架特性"重新理解为**中间层模式在方法调用粒度的实例**。

```
横切需求 → 拦截 + 织入 —— 同一模式、四种粒度：

方法调用层：  Spring AOP 代理        → 事务 / 审计 / 缓存 / 异步
进程内请求层：Filter / Interceptor   → 鉴权 / trace / 编码
网络请求层：  反向代理 / 网关         → LB / SSL 终结 / 限流
网络报文层：  Service Mesh sidecar   → 熔断 / 重试 / mTLS
```

**架构师对横切需求的第一反应**：它应该织在哪一层？判据两条——横切逻辑需要什么粒度的上下文（方法参数 / 请求头 / 报文），以及侵入成本（改代码 / 加配置 / 加部署）。**选层错误是架构返工的常见来源**：把"按业务字段的脱敏"放在网关（上下文不够）、把"纯协议层的限流"放进业务代码（侵入过深）都是层错配。

**代理统一观**：网络代理（正向/反向）、AOP 代理、Mapper/Feign 代理——全部是"客户端不直接接触真实对象，通过中间层获得可插拔控制点"。**一句话统一：代理 = 受控的间接层**。

## 二、失效地图：从散落八股到机制推论

本周最重要的交付物是**四族失效地图**——它把历史上散落在各处的"Spring 坑"收敛为机制的推论：

| 族 | 统一根因 | 代表场景 | 统一检测 |
|---|---|---|---|
| 代理失效 | 调用没经过代理对象 | 自调用 / new / 非 public / final / BPP 连坐 | AopUtils.isAopProxy 断言 |
| 作用域失效 | 注入时点固化了作用域语义 | prototype 注入单例失活 / 无人销毁 | ObjectProvider / scoped proxy |
| 顺序失效 | 正确性建立在隐式顺序上 | BPP 提前实例化 / 赌定义顺序 / 事件多次触发 | 显式 @DependsOn/@Order |
| 循环依赖 | 依赖需求早于可暴露 | 构造器环 / prototype 环 / @Async 撞环 | Boot 2.6 闸门 / ArchUnit |

**收敛的威力**：学一族就覆盖一族框架特性（代理失效族覆盖 @Transactional/@Async/@Cacheable/@Retryable 全家）；排查时先判族再定位，把"逐个场景试"变成"按机制排除"。

**第一性原理那句**：**代理持 target 引用，目标方法体内的 this 永远是原始对象**——这是语言级事实，代理型 AOP 无法绕过（字节码织入型 AspectJ 改写类本身所以没有此问题）。失效不是 Spring 的 bug，是"外壳代理"模式的物理边界。**识别一个机制的能力边界，比学会使用它更重要**。

## 三、声明式基础设施的代价账

代理承载一切声明式能力，代价是三类**隐性成本**——架构师必须在引入时记账：

1. **内存账（Metaspace）**：每个被代理类一个动态生成类常驻。Pointcut 收敛（注解切）既是行为洁癖也是内存账——**几千个 Bean × 宽表达式切面 = Metaspace 隐性大头**（Day01 伏笔的落点）
2. **时序账（CPU）**：拦截链匹配昂贵所以按 Method 缓存（解析一次执行多次——与注入元数据、ASM 扫描同款手法）；但链上每个 Advisor 的运行时开销是每次调用的固定税——**切面自身可能成为性能劣化源**，必须埋耗时观测
3. **认知账（失效面）**：每加一个代理织入的声明式能力，就扩大一整族失效面——**能力的成本不只是运行时，还有使用者的心智模型负担**（自调用地雷的存在本身就是认知税）

**设计推论**：自研框架/平台时，"声明式 + 代理"是强力的模式，但要问三个问题：元信息够不够（只依赖方法签名与注解的逻辑才适合）、失效面可不可以被检测（提供断言/日志）、心智模型能不能一张图讲清（失效地图）。

## 四、拦截链的两种形态：方向双链 vs 洋葱单链

责任链模式在两个框架里的对照（Netty 周与本日的汇合点）：

| | Netty Pipeline | Spring 拦截链 |
|---|---|---|
| 结构 | 入站正序 + 出站逆序（方向感知双链） | 单向递归嵌套（洋葱模型） |
| 推进 | ctx.fireChannelRead(next) 显式传递 | proceed() 递归推进索引 |
| 断链 | 不 fire 即中断 | @Around 不调 proceed 即吞链 |
| 顺序语义 | 方向决定先后 | @Order 决定嵌套内外 |

**洋葱模型的心智关键**：@Around 前半段是"进入方向"、proceed 之后是"返回方向"——**一个 Advisor 占两个语义位**，所以"事务在外、脱敏在内"意味着：脱敏的 proceed 前逻辑发生在事务开启之后、proceed 后逻辑发生在事务提交之前。顺序错了（脱敏在外），行为就变成"脱敏后数据进事务"——**落库原文还是脱敏文，是合规问题**（问诊系统脱敏切面的顺序纪律由此而来）。

## 五、HTTP 演进主线的架构启示：找到最深的全局锁

热身题把 HTTP 二十年演进收敛成一句话：**把"串行的隐式约束"一层层显式化并拆除**。

```
串行请求（1.0）→ 复用连接仍串行（1.1 keep-alive）
  → 管线化试图并行，被"响应按序"卡死（1.1 HOL，工程性死亡）
  → 帧交错解除 HTTP 层按序（H2），但 TCP 字节流仍全局按序（HOL 搬家到 TCP）
  → 传输层 stream 独立（QUIC），终解
```

**与往周主线的同构**：G1 拆 CMS 的整堆停顿（JVM 周）、拆全局锁换细粒度（并发周）、集群限流拆单点（限流周）——**性能台阶的本质都是"找到当前最深的全局串行点并拆掉它"**。方法论：画依赖/顺序图 → 找最长串行段（critical section / bottleneck） → 评估拆除代价（协议换血 vs 渐进优化）。

**QUIC 连接迁移的启示**：把连接标识从"传输四元组"抽象成"Connection ID"，身份与路径解耦——**迁移能力来自身份与载体的分离**（用户态协议才能做，内核 TCP 做不到——想在内核改 TCP 二十年改不动，QUIC 直接绕过——**渐进无望时换地基，而不是在旧地基上加层**）。

## 七、本日核心认知

1. **代理 = 受控的间接层**：网络代理 / AOP / Mapper / Feign 统一到"拦截 + 织入"；横切需求第一问是"织在哪一层"
2. **Spring AOP 链路**：@Enable 注解 → 注册 AbstractAutoProxyCreator（BPP）→ after 阶段 wrapIfNecessary（找 Advisor → Pointcut 匹配 → ProxyFactory）→ 拦截链按 Method 缓存
3. **JDK vs CGLIB**：反射 vs FastClass 索引；Boot 2.x 默认 CGLIB；final 是天敌；代理类进 Metaspace——Pointcut 收敛是内存账
4. **失效第一性原理**：this 永远是原始对象——外壳代理的物理边界；AspectJ 织入类本身所以免疫
5. **四族失效地图**：代理绕过 × 作用域固化 × 隐式顺序 × 依赖环——每族统一根因 + 统一检测，散落八股收敛为机制推论
6. **@Async 三坑**：返回值吞异常 / 默认线程池不池化 / 撞循环依赖报 "raw version" 异常（@Transactional 免疫的分歧点在 getEarlyBeanReference）
7. **洋葱模型**：一个 @Around 占两个语义位（进入/返回）——事务与脱敏的相对顺序是合规问题不只是行为问题
8. **声明式的三笔账**：内存（Metaspace）+ 时序（链上固定税）+ 认知（失效面）——引入声明式能力时记账
9. **HTTP 演进主线**：找到最深的全局串行点并拆掉它（串行→分帧→独立流）；HOL 两次搬家是"约束下沉"的完整标本
10. **QUIC 启示**：身份与载体分离才有迁移；渐进无望时换地基而非加层
