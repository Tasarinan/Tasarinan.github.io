## 题目一（架构设计题）：IM 网关整体架构与连接治理

请设计 IM 在线客服长连接网关的整体架构，回答：

1. **分层架构**：接入层（gateway 集群）、路由层（uid → gateway 的寻址）、业务层（会话/消息服务）、存储层各自的职责？为什么网关要"无状态化"、无状态化的真正含义是什么（连接状态在哪、会话状态在哪）？
2. **连接生命周期**：从 TCP/WebSocket 建立到可收发消息的完整握手流程（建链 → TLS → 协议升级 → 首包鉴权 → 会话绑定）？鉴权为什么放网关本地缓存而不是每次 RPC？单设备/多端登录的互踢策略？
3. **心跳与假死治理**：心跳参数（Day03 的 30s/90s）在 10w 连接下的综合账（带宽、CPU、误杀率）？假死连接的清理闭环（IdleState 踢除 → Session 摘除 → 路由表删除的顺序与一致性）？
4. **连接路由设计**：路由表（uid → gatewayId）存 Redis 还是本地？写入时机与 TTL？跨网关消息投递的两条路径（网关间直连 RPC vs 经 MQ 中转）的选型？

### 作答区

#### 1.1 分层架构

```
患者App / 客服工作台
     │ WebSocket(主) + 长轮询(降级)          ← Day01 选型
     ▼
┌─────────────────────────────────────────────┐
│ 接入层 im-gateway ×N（Netty, 无状态）          │
│  · 连接管理 / 心跳 / 鉴权(本地token缓存)        │
│  · 协议编解码（Day03 帧 + Protobuf）           │
│  · 背压（Day04 水位 + autoRead）               │
│  · 在线状态上报（连接/断开事件）                 │
└──────────────┬──────────────────────────────┘
               │ 发布：MQ(im-push-topic，按会话分区保序)
               ▼
┌─────────────────────────────────────────────┐
│ 业务层 im-logic                              │
│  · 会话管理（患者↔客服配对、排队）               │
│  · 消息处理（seqId 生成、落库、扇出）            │
│  · 离线消息 / 历史消息                         │
└──────┬──────────────────┬───────────────────┘
       ▼                  ▼
   MySQL(消息/会话)     Redis(路由表/在线状态/去重)
```

**"网关无状态"的真正含义**：网关持有**连接**（物理资源，天然有状态、不可迁移），但不持有**业务会话状态**（会话归属、消息历史、未读数全在业务层/存储层）。判定测试：**kill 任意一台网关，业务是否只损失"重连"而不损失"数据"**——重连后路由表刷新，消息照发。这就是"状态分离"：**把可丢的（连接）和不可丢的（会话）放在不同的层**。

**为什么网关不直接调业务、而走 MQ 扇出**：消息扇出（一条消息 → 会话双方 + 多端）与推送解耦；网关宕机时消息在 MQ 积压等重连后消费，不丢；削峰（群发场景，Day04 广播扇出的流量放大被 MQ 缓冲）。

#### 1.2 连接生命周期（握手五步）

```text
① TCP 建链（三次握手，SO_BACKLOG 2048）
② TLS 握手（SNI + 证书；内网可降级）
③ WebSocket 升级（GET + Upgrade 头；长轮询降级路径同入口）
④ 首包鉴权（AUTH 帧：token + deviceId + 支持的协议版本/能力集 —— Day03 能力协商）
   网关本地校验：Redis token 缓存（鉴权服务写入，TTL 5min，命中即免 RPC）
   失败/超时 10s 未 AUTH → 断开（Day03"未认证零业务开销"）
⑤ 会话绑定：channel.attr(UID) 绑定 + 本地 ChannelManager 注册 + 路由表写入（uid → 本机）
```

**鉴权放本地缓存的原因**：每条连接一次鉴权（非每条消息），10w 连接 × 重连风暴时鉴权 QPS 可能到 10w+——每次 RPC 会打挂鉴权服务（Day06 的雷）。token 校验是纯 CPU（JWT 验签）或一次 Redis GET，网关本地做 = **把鉴权从"每连接一次远程调用"降为"每连接一次本地操作"**。

**互踢策略（单端登录场景）**：新连接 AUTH 成功后，业务层查路由表发现旧连接在别的网关 → 通知该网关踢旧连接（KICK 帧：带新设备信息，客户端可提示"已在别处登录"）。**踢旧必须在路由表覆盖之后**，否则新旧并存且路由指向已死连接。

#### 1.3 心跳的综合账（10w 连接）

| 项 | 计算 | 结果 |
|---|---|---|
| 带宽 | 10w × (20B帧/30s) 双向 | ≈ 0.1Mbps 量级——可忽略 |
| CPU | 10w/30s ≈ 3300 帧/s，纯编解码+EventLoop 分发 | 单机几毫秒级/秒——可忽略 |
| 误杀 | 90s 读空闲 = 客户端 3 个心跳周期全丢 | 正常网络下概率 ≈ 0；Gc/调度抖动由三倍容错吸收 |
| 收益 | NAT 保活 + 假死检测 + 慢消费者尽早暴露 | 核心生命线 |

**踢除的清理闭环（顺序一致性考点）**：

```java
// IdleState 触发（EventLoop 线程内串行，天然无竞态）：
1. channelInactive/主动close 前摘本地 ChannelManager
2. 发"下线事件"到 MQ（业务层异步删路由表：只删"指向本机"的条目——防止删掉新连接的记录 ★）
   伪代码：redis删除前 compare gatewayId == 本机id，不等则跳过
3. 业务层收到下线事件 → 判定"最后一条连接" → 状态置离线 → 推给关心在线状态的订阅方
```

**★ 关键竞态**：客户端闪断重连（新连接在网关 B）与旧连接的踢除（网关 A）并发——A 的删除路由操作必须带条件（只删指向自己的），否则删掉 B 刚写的记录，消息推送找不到人。**分布式下线清理的通则：删除必须携带"版本/归属"校验**（与分布式锁释放必须校验持有者同一个道理——MQ 周的教训）。

#### 1.4 连接路由

**路由表结构（Redis）**：

```
key: route:{uid}          value: {gatewayId, connId, deviceId, timestamp}   TTL 10min（心跳续期）
辅助: online-set           按业务需要的在线集合
```

**两条跨网关投递路径的选型**：

| 方案 | 路径 | 优劣 |
|---|---|---|
| MQ 中转（主选） | im-logic → MQ(分区键=uid) → 各网关订阅消费 → 命中本地则推 | 解耦、削峰、网关宕机消息不丢（offset 未确认）；延迟多一跳（P99 +5~20ms） |
| 网关直连 RPC | im-logic 查路由 → 直连目标网关 RPC 推送 | 延迟低一跳；但扇出风暴直击网关、网关需暴露内部端口、耦合拓扑 |

实践结论：**推送走 MQ（可靠性优先），高频低延迟通道（已读回执、正在输入）可直连 RPC（可丢场景）**。按消息类型分级——又是"按可丢性分级"的老原则（MQ 周的核心思想）。

## 题目二（核心机制设计题）：消息可靠性、顺序与背压

1. **消息可靠性闭环**：IM 消息"不丢、不重、不乱"分别靠什么机制（客户端生成 msgId + 服务端 seqId + ACK + 重发 + 去重幂等 + 拉取补偿）？完整的上行/下行可靠性流程？为什么"推拉结合"（推送通知 + 客户端按 seq 拉取）是最终兜底？
2. **消息顺序**：连接内 seq 单调递增 vs 会话内全局有序的区别？为什么按会话分区（MQ 分区键选择）能保序？跨连接重连后顺序怎么续（seq 续传 + 缺口检测）？
3. **慢消费者与背压（集成 Day04）**：客服端弱网导致推送堆积的完整处置策略（水位监听 → 降级路径：转离线/丢弃低优先级通知/断开）？群发/通知类扇出优化（一次编码 + retainedDuplicate）？
4. **离线消息**：离线消息的存储模型（收件箱写扩散）与拉取协议（按 seq 区间分页拉取 + 限速）？离线消息过多时的合并策略（通知合并、会话折叠）？

### 作答区

#### 2.1 可靠性闭环：不丢、不重、不乱

**三个保证的三套机制**：

```
不丢：客户端 msgId + 服务端持久化成功才 ACK + 超时重发 + 推拉结合兜底
不重：服务端按 msgId 幂等去重（消费侧）；客户端按 seqId 去重（接收侧）
不乱：会话内 seq 递增 + 按分区保序 + 客户端缺口检测（收到 seq=8 但上次是 6 → 拉取 7）
```

**上行消息流程（患者发消息）**：

```text
客户端生成 msgId(uuid) → 发送并本地 pending → 网关收包 → MQ → im-logic:
  ① 幂等检查：msgId 已处理过？→ 直接回 ACK（重发场景）
  ② 分配会话内 seqId → 落库（消息表）
  ③ ACK 沿原路回（经网关 → 客户端删 pending）
  ④ 扇出：对端连接在线 → 推送；离线 → 写离线收件箱
客户端 5s 未收 ACK → 重发（同 msgId）→ ① 幂等吸收
```

**下行消息流程 + 推拉结合**：

```text
im-logic 推送（带 seqId）→ 网关 → 客户端
  客户端收到 seq=101，本地最大 99 → 缺 100 → 主动拉取 API 补齐
  推送丢了不可怕：客户端每次连接建立/收到缺口检测时按 seq 区间拉取
结论：推送只是加速器，拉取才是可靠性的地板 —— "推拉结合"
```

**架构师认知**：这套机制与 MQ 周的消息最终一致性、支付周的幂等三防闭环**完全同构**：业务侧幂等键（msgId ≈ 支付幂等单号）、ACK-重发（≈ MQ producer retry）、对账补偿（缺口检测拉取 ≈ 支付对账差错处理）。**可靠性的本质永远是三件：唯一标识 + 确认重试 + 对账补偿**。

#### 2.2 顺序

**两级 seq 的区别**：

| | 连接内 seq | 会话内 seq |
|---|---|---|
| 生成者 | 网关（连接建立起自增） | im-logic（会话维度分配，DB/Redis 自增） |
| 作用 | 连接层去重、请求响应关联（Day03 seqId） | 端到端消息顺序的标尺 |

**为什么按会话分区保序**：im-logic 消费 MQ 时分区键 = 会话 ID（conversationId）→ 同一会话的消息进同一分区 → 单消费者按序处理 → seq 单调。**分区键选错（如按发送者）会话内就乱序**——这是 MQ 周"局部有序"的直接应用：全局有序代价高（单分区），按业务聚合键分区是标准解。

**重连续序**：重连后客户端上报"本地最大 seq" → 服务端从该点推送/允许拉取（增量同步）。配合缺口检测，丢消息窗口收敛到一个心跳周期内。

#### 2.3 慢消费者与背压（Day04 落地）

**客服端弱网堆积的分级处置**（isWritable=false 触发时）：

```java
public void channelWritabilityChanged(ChannelHandlerContext ctx) {
    if (!ctx.channel().isWritable()) {
        ChannelSession s = session(ctx);
        s.markSlowConsumer();                       // ① 标记：降级推送
        // ② 策略按消息类型分级（Day04 背压 + MQ 周按可丢性分级）：
        //    通知类（排队提醒/在线状态）→ 直接丢弃或转离线
        //    会话消息 → 转入离线收件箱（用户下次拉取），从发送缓冲清除
        //    已超阈值（如 5 分钟不可写）→ 判定假死，踢除走重连流程
        // ③ 保留 autoRead=false 手段应对极端全局内存压力
    }
}
```

**为什么"转入离线"比"硬扛"好**：发送缓冲堆积占用堆外预算（Day04 公式），转入离线收件箱把内存成本转为存储成本，且客户端重连后走拉取路径补齐——**用可靠性的地板（拉取）换内存的安全**，两套机制互补。

**通知类扇出优化（广播场景）**：

```java
// 反例：循环逐条编码
for (Channel ch : targets) { ch.write(encode(msg)); }       // N 次编码 N 份内存
// 正例：一次编码 + retainedDuplicate（Day04 零拷贝扇出）
ByteBuf body = encode(msg);                                  // 编码一次
try {
    for (Channel ch : targets) {
        ch.write(body.retainedDuplicate());                   // 视图 +1 引用，写出后自动释放
    }
} finally { body.release(); }
// 扇出 1w 连接 = 1 次编码 + 1w 个轻量视图，CPU 与内存双省
// ★ 每份的释放由 ChannelOutboundBuffer 写完成自动完成；异常路径若绕过写出 → 泄漏（Day07 伏笔）
```

#### 2.4 离线消息

**存储模型（单聊写扩散收件箱）**：

```
inbox:{uid} → 消息 seq 有序集合（按 seq 范围存）
上限（如 7 天/2000 条）+ 溢出转冷存储（历史消息走 DB 分页接口）
```

**拉取协议**：连接建立 → 客户端上报 lastSeq → 服务端从 lastSeq+1 分页返回（每页 50 条）+ **限速**（令牌桶，Day06 的雷之一：重连风暴时全量拉取会打爆 DB/Redis）。

**合并策略**：同会话多条离线消息折叠为"会话未读摘要 + 最新一条"，客户端进会话再拉详情——**把 N 条推送合并为 1 条摘要，重连风暴下流量降一个量级**。

## 题目三（治理与叙事题）：容量、发布与面试 STAR

1. **容量规划（Day01 账本的落地）**：单机连接上限怎么定（内存/fd/带宽三维）？10w+ 峰值需要几台网关（含余量与滚动发布）？
2. **发布与连接迁移（Day02 优雅关闭的放大版）**：网关滚动发布时 10w 连接怎么办——完整连接迁移流程（摘注册 → 停新连 → drain → 通知重连 → 关闭）？K8s 的配合（preStop + terminationGracePeriodSeconds）？
3. **监控告警体系（Day04 四件套的落地）**：网关必须上的指标与告警阈值？
4. **面试 STAR 叙事**：把 IM 在线客服网关组织成 2 分钟项目介绍 + 预演 5 个高频追问。

### 作答区

#### 3.1 容量规划

```
目标：峰值在线 10w 长连接
单机（16C32G 容器 limit 24G）：
  连接内存：10w × 10~50KB（Day01 账） ≈ 1~5GB（堆外预算入 Day04 公式）
  堆（Session/编解码对象）-Xmx 8G；堆外预算 6G（含水位余量）；其余元空间/栈/缓存
  fd：ulimit -n 100w，SO_BACKLOG 2048
  EventLoop：boss 1 + worker 16~32（≈CPU×2）+ 业务组 32
  带宽：峰值消息 1w/s × 2KB × 扇出系数 ≈ 40Mbps+ → 万兆内网无压力
保守单机上限：10w 连接
→ 10w 峰值 = 1 台满载：不可接受（发布即全断）
→ 生产：3 台常备（每台 1/3 负载，单机故障/发布时其余 2 台扛 5w/台——仍在安全线内）
       + HPA 按连接数扩容到 4~5 台应对大促
```

**架构师认知**：容量不是"能扛多少"而是"**扛 N 时还能不能扛故障和发布**"。N+2 冗余是这个逻辑的最小配置（1 台故障 + 1 台发布）。

#### 3.2 发布与连接迁移（滚动发布的优雅下线）

```
① 摘流量：从注册中心/LB 摘除本节点（新连接不再来）
② 停新连：accept 后直接关闭或重定向（配合 LB 停转发，双保险）
③ 通知重连：向存量连接下发 RECONNECT 帧（带建议重连时间=random(1~30s) ★错峰）
④ drain：等待客户端主动断开重连（或超时 5 分钟），期间消息照常收发
⑤ 兜底关闭：close 全部连接 → 路由表由"下线事件"清理（1.3 的条件删除）
⑥ shutdownGracefully(quietPeriod) → 进程退出
```

**★ 错峰重连**：所有连接同刻断开会造成自我 DDoS（Day06 的事故核心）。下发的重连时间加随机抖动，把 10w 重连摊到 30s+ 的窗口——**与限流周的"打散突发"同一思想**。

**K8s 配合**：preStop 执行摘注册 + sleep（等 LB 生效）→ SIGTERM 触发 ①~⑤ → terminationGracePeriodSeconds 覆盖 drain 时长（如 300s，默认 30s 不够！）。**默认值坑**：K8s 默认 30s 宽限期会强杀还没 drain 完的网关。

#### 3.3 监控告警

| 指标 | 告警阈值（示例） | 对应风险 |
|---|---|---|
| 在线连接数 | 同环比骤降 30% | 断连事故（Day06 第一个信号） |
| 新建连接速率 | > 平时 10 倍 | 重连风暴 |
| isWritable=false 连接数 | > 在线 5% | 慢消费者/弱网群体 |
| 单连接 ChannelOutboundBuffer 深度 topN | 单连接 > 1MB | 慢消费者定位 |
| 池化堆外用量 | 预算 80% | OOMKilled 前兆（Day04 红线） |
| EventLoop 任务排队延迟 | P99 > 100ms | EventLoop 被阻塞（Day02 规约执法） |
| IdleState 踢除率 | 突增 | 网络问题/客户端 bug/误杀 |
| 鉴权失败率 | 突增 | 攻击/证书过期/客户端 bug |

#### 3.4 面试 STAR 叙事

**2 分钟项目介绍（模板）**：

> "我负责在线问诊系统的 IM 网关。业务形态是患者 App 与客服工作台的单聊加系统通知，峰值 10w+ 长连接。接入层用 Netty 自研网关：Epoll transport + 主从 Reactor（boss 1 / worker 2×CPU），协议是 WebSocket 承载自定义二进制帧（16B 定长头 + Protobuf body），心跳 30s/90s 三倍容错。可靠性上做了推拉结合：客户端 msgId 幂等 + 服务端会话内 seq 顺序 + 缺口检测拉取，推送只是加速器、拉取是可靠性的地板。性能上重点治理了两个：一是广播扇出用一次编码加 retainedDuplicate 扇出；二是慢消费者背压，isWritable 触发后按消息类型分级降级，把堆外内存压力转成离线存储。发布上做了连接迁移：摘流量、下发带随机抖动的重连指令、drain 后再退出，滚动发布不掉消息。上线后 P99 端到端延迟 800ms 内，单机 10w 连接稳定运行。"

**5 个高频追问预演**：

1. **"为什么自己写网关而不用开源（如 Openfire/goim）？"** → 协议与业务耦合（医疗消息合规审计、医保对接通知）+ 团队 Java 栈 + Netty 生态（Dubbo/gRPC 同栈）+ 自研可控性；诚实补充边界：如果只是通用 IM，成熟方案优先，我们是业务特化
2. **"10w 连接怎么压测验证的？"** → 容量压测：自研连接机器人（协议仿真客户端）阶梯加压 5w/8w/10w/12w，观测四件套指标；长稳测试 24h 看内存曲线（池高水位 vs 泄漏——Day04 的判断）
3. **"连接数能到 100w 吗？"** → 回到账本：连接内存 1~5GB×10、fd、单机 EventLoop 处理上限——技术上 50w 可达（调大预算），但 3×10w 集群在可用性（爆炸半径/发布/故障转移）上优于 1×100w 单机——**容量决策是可用性权衡不是技术炫技**
4. **"最难的一个线上问题？"** → 留给 Day06/Day07 的故事（重连风暴/堆外泄漏），先埋钩子："有一次机房网络抖动 30 秒引发重连风暴，这个复盘比较完整，要不要展开讲？"——**主动引导面试官进入自己准备最充分的领域**
5. **"如果让你重新设计会改什么？"** → 诚实答改进点（如鉴权缓存预热、连接迁移自动化、双机房容灾），展示反思能力而非完美叙事

### 差距1：架构分层靠"抄别家"，说不出决策依据

- **现状**：画得出"网关+MQ+逻辑层"，但"为什么走 MQ 不直连""无状态化的判定测试是什么"答不深

### 差距2：消息可靠性机制散装，没有体系化话术

- **现状**：不丢/不重/不乱各自的机制知道一些，但"推拉结合""缺口检测"这些收口动作讲不出；与支付幂等/MQ 最终一致性的同构关系没建立

### 差距3：下线路由清理的竞态没意识到

- **现状**：闪断重连与踢除并发时"旧网关删掉新网关的路由记录"这个竞态九成人答不出；条件删除（校验归属）的通则没沉淀

### 差距4：发布只做过"滚动重启"，没做过连接迁移

- **现状**：知道 K8s 滚动发布，但摘流量→停新连→错峰重连→drain→条件清理的完整流程没实操过；terminationGracePeriodSeconds 默认 30s 的坑不知道

- **补足方向**：给简历项目补写"发布工程"段落；在测试环境演练一次连接迁移

### 差距5：容量叙事仍是"背账本"，没做过压测闭环

- **现状**：能背"每连接 10~50KB"，但"3 台常备 N+2 的冗余逻辑""压测阶梯怎么设""长稳 24 小时看什么曲线"没实操
- **架构师水平**：容量 = 账本推导 + 压测验证 + 红线告警的闭环；解释为什么 3×10w 优于 1×100w 是可用性权衡
- **补足方向**：做一个简化版连接压测机器人（哪怕只到 1w 连接），拿到自己的实测曲线

## 附录：本日关键认知速查

| 认知点 | 关键结论 |
|---|---|
| 无状态化判定 | kill 任意网关只损"重连"不损"数据"；可丢（连接）与不可丢（会话）分层 |
| 握手五步 | 建链 → TLS → WS 升级 → 首包鉴权（本地缓存+10s超时）→ 会话绑定+路由写入 |
| 鉴权本地化 | 每连接一次本地操作替代一次远程调用；重连风暴下的保命设计 |

| 下线清理竞态 | 删除路由必须校验归属（gatewayId）——分布式删除通则 |
| 路由表 | route:{uid} → gatewayId，TTL 心跳续期；投递走 MQ（可靠）或直连 RPC（低延迟可丢） |

| 推拉结合 | 推送是加速器，拉取是可靠性的地板 |
| 保序 | 分区键=会话 ID 局部有序；重连接上报 lastSeq 增量续传 |
