## 一、IoC 容器启动流程（Day01）

### 差距1.1：容器体系"组合而非重写"的结构答不出
> Day1发现

- **现状**：知道 ApplicationContext 功能更多，但说不出它内部持有 DefaultListableBeanFactory、"内核与周边设施分离"的分层设计；FactoryBean 只会背"getObject 拿对象"，串不起 MyBatis Mapper 从接口到 JDK 动态代理的完整链路
- **架构师水平**：白板画出 ApplicationContext 组合 BeanFactory 的结构图；用"内核+插件+适配器"讲清 FactoryBean 是"任意对象工厂接入 IoC 的统一适配器"
- **补足方向**：读 AbstractApplicationContext.obtainFreshBeanFactory 与 AnnotationConfigUtils.registerAnnotationConfigProcessors 各一遍

### 差距1.2：refresh() 12 步讲不全，三大重点步骤职责边界模糊
> Day1发现

- **现状**：能背出几个方法名但顺序记不全；不知道扫描发生在第 5 步 invokeBeanFactoryPostProcessors（高频误区是"构造器里就扫了"）；Boot 的 WebServer 在第 9 步创建、第 12 步启动的时序空白
- **架构师水平**：白板默写 12 步并标出三个★步骤内部细节（BDRPP 先行三批执行 / BPP 提前实例化 / 冻结配置+预实例化+SmartInitializingSingleton）
- **补足方向**：对照 AbstractApplicationContext.refresh 源码抄写一遍，标注每步产出物；12 步做成记忆卡片

### 差距1.3：BFPP/BPP 分层执行与"提前实例化陷阱"没掌握
> Day1发现

- **现状**：两类后置处理器只会背定义；PriorityOrdered → Ordered → 无序三批、"RegistryPostProcessor 先行"、`not eligible for getting processed by all BeanPostProcessors` 日志的生产含义全部空白
- **架构师水平**：看到该日志立刻定位"有 Bean 错过了部分 BPP → 事务/切面可能失效"；说得出 BPP 及其依赖 Bean 的编码纪律（构造器注入/BeanFactoryAware）
- **补足方向**：把 Day01 第 4 问对比表与两条 Aware 回调路径抄进笔记；在自己项目日志里搜一遍这条警告

### 差距1.4："ASM 扫描 + className 字符串"的延迟类加载设计不知道
> Day1发现，延续 JVM 第1周差距（类加载）

- **现状**：以为扫描就是反射加载类；不知道 BeanDefinition 存字符串、实例化才 loadClass；与 CGLIB 增强类进 Metaspace 的内存账（启动内存 = 注册的类延迟加载 + 动态生成类必然加载）断了因果
- **架构师水平**：讲清"扫描不加载、实例化才加载"两级延迟设计，并把动态生成类（@Configuration 增强、AOP 代理）算进 Metaspace 预算
- **补足方向**：读 ClassPathScanningCandidateComponentProvider.findCandidateComponents 与 SimpleMetadataReader；与 JVM 周类加载笔记对照

### 差距1.5：启动耗时治理没有方法论
> Day1发现，延续 K8s 周差距（发布工程）、简历项目差距（容量规划）

- **现状**：没用过 BufferingApplicationStartup / /actuator/startup；优化停留在"加 @Lazy"一招；全局 lazy-initialization 的风险（首请求慢、错误延迟暴露、@Scheduled/Listener 失效）说不全；外部依赖没有 fail-fast vs 降级启动的分级决策
- **架构师水平**：度量先行 → 三类大头定位 → 分层施策（范围/并行/外部连接/JVM/AOT）；能按依赖分级（医保结算通道 fail-fast、非核心异步重试）写出启动语义 ADR
- **补足方向**：给问诊系统配 /actuator/startup 跑一次启动画像；按 Day01 第 5 问分层表产出启动优化清单

### 差距1.6：发布窗口账不会算
> Day1发现，延续 K8s 周差距（发布工程）

- **现状**：算不出"启动 8min × 5 台逐台替换"的全量发布窗口；讲不出"窗口=新旧共存=兼容暴露面、回滚=两次窗口、启动抖动=探针误杀（startupProbe 防护）"三笔账
- **架构师水平**：30 秒报出窗口公式并给出探针配置建议——把 JVM/Spring 层优化翻译成发布工程收益，是面试高区分度叙事
- **补足方向**：按 Day01 第 5 问公式算一遍问诊系统真实发布窗口；与 K8s 周 Day02 发布工程笔记合并

### 差距1.7：单例 Bean 的"安全发布"机制说不出，JMM 与 Spring 悬空
> Day1发现，延续并发周 Day01 差距（JMM）

- **现状**：只会答"有状态不安全"；用 JMM 语言（singletonObjects 是 ConcurrentHashMap、put/get 建 happens-before）解释"构造期间的写为什么对请求线程可见"答不出——并发周 JMM 理论与 Spring 实现之间的连接点缺失
- **架构师水平**：分"安全发布（容器保证）"与"线程安全（自己负责）"两层作答；对有状态单例按决策树（无状态化/并发容器/ThreadLocal）秒开处方，并把"单例新增非 final 字段三问"变成 code review checklist
- **补足方向**：读 DefaultSingletonBeanRegistry.getSingleton（懒创建的 synchronized 双检）；把第 6 问决策树内化

### 差距1.8：prototype 失活陷阱不知道
> Day1发现

- **现状**：没意识到单例注入 prototype 只注入一次、多例语义失效；不知道 ObjectProvider/@Lookup 解法；与 @Transactional/@Async 自调用失效（Day04）同属"作用域与代理"失效家族的全景图缺失
- **架构师水平**：本周 Day04 收官时产出"Spring 失效地图"（作用域失效 × 代理失效 × 处理器顺序失效），面试主动讲述
- **补足方向**：写一个单例注入 ObjectProvider\&lt;PrototypeBean\> 的 demo 验证多例语义；Day04 与代理失效合并梳理

## 二、Bean 生命周期与扩展点（Day02）

### 差距2.1：doCreateBean 三大步讲不出源码级顺序与介入者
> Day2发现

- **现状**：生命周期只会背"实例化→填充→初始化"，说不出 createBeanInstance/applyMergedBeanDefinitionPostProcessors/populateBean/initializeBean 的源码顺序、每步谁能介入、注入元数据缓存在哪
- **架构师水平**：白板默写总装线，标出 addSingletonFactory（Day03 入口）和 BPP after（Day04 代理入口）在全线的位置
- **补足方向**：精读 AbstractAutowireCapableBeanFactory.doCreateBean 一遍，抄写三大步与注释

### 差距2.2：三类 init 回调顺序知道结果，说不出设计理由
> Day2发现

- **现状**：背得出 @PostConstruct → afterPropertiesSet → init-method，但"标准优先于实现、契约优先于配置、代理必须最后"三层理由讲不出
- **架构师水平**：用"生态互操作 / 确定性优先 / 代理包装最终对象"三句话讲清顺序的必然性
- **补足方向**：把三层理由内化，给自己讲一遍直到不看笔记

### 差距2.3："就绪四层语义"分不清，预热代码放错位置
> Day2发现

- **现状**：@PostConstruct / SmartInitializingSingleton / ContextRefreshedEvent / ApplicationRunner 的时机差别说不全；不知道 SmartLifecycle.start 在 ContextRefreshedEvent 之前（端口已开）；监听 ContextRefreshedEvent 不防重（父子容器多次触发）
- **架构师水平**：给任意一段"就绪后逻辑"30 秒内判定挂点；讲清"预热跑在端口开放前还是后"的发布窗口含义
- **补足方向**：把选型表抄进笔记；在问诊系统里审查全部 @PostConstruct，列出迁移到 Runner 的清单

### 差距2.4：推断构造器机制空白
> Day2发现

- **现状**：不知道多构造器时 Spring 怎么选、@Autowired 构造器优先级、5.0+ 单构造器自动推断；"为什么推荐构造器注入"答不出源码级理由
- **架构师水平**：讲清单构造器零注解即可推断的设计动机；对"构造器注入 vs 字段注入"给出不可变性/测试性/依赖显性化三连论据
- **补足方向**：读 determineConstructorsFromBeanPostProcessors 与 autowireConstructor

### 差距2.5：销毁阶段知识几乎空白
> Day2发现

- **现状**：说不全 @PreDestroy → destroy() → destroy-method 顺序；不知道 SmartLifecycle.stop 先于 Bean 销毁、销毁按依赖反向图逆序、Boot 自动注册 shutdown hook、destroyMethod 自动推测 close/shutdown；prototype 不管销毁的连带风险没概念
- **架构师水平**：画出优雅停机全时序（SIGTERM → 事件 → Lifecycle 停 → 逆序销毁 → JVM 退出），并对到 K8s 的 preStop/terminationGracePeriodSeconds 上
- **补足方向**：读 AbstractApplicationContext.doClose 与 DisposableBeanAdapter；对着问诊系统发布流程画一遍停机时序图

### 差距2.6：@PostConstruct 滥用没有纪律——启动事故的高发源头
> Day2发现，延续 Day01 差距1.5（启动耗时治理）

- **现状**：自己就在 @PostConstruct 里写过建连/预热代码；不知道"重活放 Runner、轻活放 @PostConstruct"的界线；强依赖顺序必须显式表达（@DependsOn/构造器注入）而不是赌定义顺序
- **架构师水平**：把三条纪律 + 反模式集变成团队的 code review checklist
- **补足方向**：审查问诊系统全部 @PostConstruct（IDEA Structural Search），产出整改清单

### 差距2.7：BPP 的两个 Order 分不清
> Day2发现

- **现状**：写 BPP/切面时分不清"BPP 的 Ordered（决定代理外壳套几层）"与"Advisor 的 @Order（决定同一代理内拦截链顺序）"——切面治理混乱的头号来源
- **架构师水平**：讲清两个轴的区别并给出"脱敏在事务之后执行"这类需求的正确落点
- **补足方向**：写一个含两个 Advisor 的 demo，断点观察 ReflectiveMethodInvocation 拦截链顺序

### 差距2.8：生命周期没有上升到"多阶段构造范式"
> Day2发现

- **现状**：把生命周期当 Spring 特有八股，看不到与 Servlet/Netty Channel/K8s Pod 的同构——"读源码学设计"停留在"读源码背流程"
- **架构师水平**：用"阶段化构造+钩子协议+单向推进+失败分阶段语义"四要素分析任意带生命周期的系统，并在自研组件（渠道连接管理器）里复用
- **补足方向**：把同构表内化；给问诊系统的渠道连接管理器写一页"生命周期设计 ADR"

## 三、循环依赖与三级缓存（Day03）

### 差距3.1：三级缓存数据结构说不全，"一级 CHM、二三级 HashMap"的锁设计不知道
> Day3发现

- **现状**：只背得出三个 Map 名字；不知道二三级是 HashMap 且被 singletonObjects 的锁整体保护——"锁 scope 覆盖非线程安全结构"的设计手法没识别
- **架构师水平**：讲清三个 Map 的访问模式差异（运行期热读 vs 启动期受控写）与锁的不变量设计
- **补足方向**：读 DefaultSingletonBeanRegistry 的三个字段声明与 getSingleton/addSingletonFactory/addSingleton 三个同步方法

### 差距3.2：完整时序走不下来——第 13 步一致性核对完全空白
> Day3发现，Day7深挖补全（见差距7.2）

- **现状**：A↔B 时序讲到"B 拿到 A 的引用"就断了；getSingleton(name, false) 的语义、exposedObject == bean 的判断、最终暴露对象为什么可能变成"二级里那个"全部没概念
- **架构师水平**：白板默写 14 步时序，指出两个灵魂考点（谁先完工、一致性核对在防什么）
- **补足方向**：对照 Day03 第 3 问时序抄写一遍；断点跑一个 AOP + 循环依赖的 demo 观察一致性核对

### 差距3.3："为什么不能两级"答不到点上——没有 AOP 延迟决策的推理
> Day3发现

- **现状**：只会说"为了效率/为了代理"，推不出"直接放壳 → B 拿到原始对象事务失效 / 提前代理 → 全量 Bean 买单"的两难，以及工厂如何解开两难
- **架构师水平**：用反证法三段论作答，并给出"第三级存的是还没做的决定"这句话
- **补足方向**：把反证法抄成笔记并给自己讲一遍；延伸对照 TLS 0-RTT 的同构表

### 差距3.4：可解域的第一性原理讲不出——"依赖需求时点 vs 可暴露时点"
> Day3发现

- **现状**：背"setter 能解构造器不能"，说不出"构造器的依赖需求发生在实例化之中、暴露点在实例化之后"这个时序本质
- **架构师水平**：用"可解当且仅当依赖需求时点晚于可暴露时点"一句话统一全部形态（含 prototype 为什么连暂存点都没有）
- **补足方向**：重读 Day03 第 1 问 + 第 5 问，把三个"为什么不能"都归约到同一原理

### 差距3.5：@Lazy 剪环的机制模糊
> Day3发现，Day7深挖补全（见差距7.4）

- **现状**：知道"@Lazy 能解决循环依赖"，说不出注入的是 LazyResolutionProxy、首次调用才 getBean——"创建期依赖松弛成运行期依赖"的本质没抓住
- **架构师水平**：讲清代理剪环的机制，并区分"过渡手段（存量代码）"与"目标手段（抽中介/事件解耦）"的使用边界
- **补足方向**：写一个构造器循环 + @Lazy 的 demo，断点看 getLazyResolutionProxyIfNecessary

### 差距3.6：Boot 2.6 禁止循环依赖的"矛盾题"没准备
> Day3发现

- **现状**：不知道 allow-circular-references 默认值变更；"一边解决一边禁止"的架构叙事（兼容能力 vs 设计态度）答不出；治理只有"加 @Lazy"一招，没有四步路线图
- **架构师水平**：给出摸底（CI 试跑/ArchUnit）→ 归因三类 → 过渡（@Lazy 留 TODO）→ 熔断（规则+闸门）的治理方案
- **补足方向**：给问诊系统跑一次 ArchUnit 循环检测；把四步路线抄进治理手册

### 差距3.7：循环依赖报错的判别力为零
> Day3发现，Day7 出四形态判别表（见差距7.5）

- **现状**：分不清 BeanCurrentlyInCreationException 的两种语义（构造器环 vs @Async 提前暴露不一致）、BeanNotOfRequiredTypeException（早期引用是壳导致）——报错出来只能瞎猜
- **架构师水平**：拿报错栈 30 秒定位环的位置与形态
- **补足方向**：Day07 的 4.5 判别表 + "三问定位法"内化

### 差距3.8：TLS 证书链验证与前向保密讲不清
> Day3发现

- **现状**：只会"HTTPS = http + ssl"；证书链逐级验证的四个要素（签名/有效期/吊销/域名）说不全；RSA 密钥交换为什么没有前向保密、ECDHE 为什么有没概念
- **架构师水平**：讲清混合加密的理由、证书信任锚的供应链本质、PFS 的"私钥用完即弃"机制——医疗数据传输合规叙事的地基
- **补足方向**：重读 Day03 热身题 1；对照医保数字证书对接经历梳理一遍证书校验清单

## 四、AOP 与动态代理（Day04）

### 差距4.1：Spring AOP 实现链路讲不出——从注解到代理对象是黑盒
> Day4发现

- **现状**：知道"@EnableAspectJAutoProxy 开启 AOP"，说不出它 Import 的 Registrar 注册了什么、AnnotationAwareAspectJAutoProxyCreator 是 BPP、wrapIfNecessary 的三步（找候选/匹配/建代理）、@Aspect 方法怎么变成 Advisor
- **架构师水平**：白板默写"注解→后置处理器→Advisor 翻译→Pointcut 匹配→ProxyFactory→拦截链"全链路，并标出 getEarlyBeanReference 挂在哪
- **补足方向**：读 AbstractAutoProxyCreator.wrapIfNecessary 与 AnnotationAwareAspectJAutoProxyCreator.findCandidateAdvisors

### 差距4.2：拦截链执行机制模糊——proceed 递归与 Order 排序
> Day4发现，延续 Day02 差距2.7（两个 Order）

- **现状**：不知道 Advisor 链按 Method 缓存、ReflectiveMethodInvocation.proceed 是递归推进索引、@Around 不调 proceed 会吞链；Order 数值与内外层的关系说不清
- **架构师水平**：讲洋葱模型执行序；解释"两个 Order"的区别（代理外壳层 vs 拦截链内层）
- **补足方向**：断点跟一次 ReflectiveMethodInvocation.proceed；写两个 @Around 切面打印前后日志验证嵌套序

### 差距4.3：失效场景只会背自调用，没有"三大族"的结构化地图
> Day4发现

- **现状**：@Transactional 失效只会答"自调用失效"；rollbackFor 默认值、多线程 ThreadLocal 断链、MyISAM 这些散点答不全，更没有族级归纳
- **架构师水平**：30 秒讲四族失效地图（代理/作用域/顺序/循环依赖），每族统一根因+统一检测；把散落八股收敛成机制推论
- **补足方向**：默写失效全图；在问诊系统代码里找三个失效隐患

### 差距4.4："this 是原始对象"的内存图画不出——第一性原理没建立
> Day4发现

- **现状**：知道自调用失效，讲不出"代理持 target 引用、方法体内 this 永远是 target"这条语言级事实；也就推不出"为什么 AspectJ 没有这个问题"
