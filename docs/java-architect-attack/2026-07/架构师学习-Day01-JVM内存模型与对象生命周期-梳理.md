## 一、架构师视角下的 JVM 内存模型

### 1.1 不只是"面试题"，是"架构决策的基础"

很多工程师把 JVM 内存模型当成面试题背诵，背完就忘。架构师视角下，JVM 内存模型是**技术选型与容量规划的决策基础**：

| 架构决策 | 受 JVM 内存模型约束的具体点 |
|---------|----------------------------|
| 选 Netty 还是 Tomcat 作长连接网关 | Netty 用直接内存，单机 10w 长连接仅需 8GB 直接内存；Tomcat 用堆内存 BIO，单机 1w 连接已是极限 |
| 缓存用 Caffeine 还是 Redis | Caffeine 在 JVM 堆内，受堆大小限制（GB 级）；Redis 独立进程，单机可放 100GB+ |
| SFU 服务单独部署还是混部 | SFU 高对象创建率需要大新生代，与业务服务的老年代主导内存画像冲突 |
| 堆设多大、用 G1 还是 ZGC | 堆 > 32GB 指针压缩失效，G1 在 16-32GB 表现最佳；ZGC 在 16GB-16TB 都能保持 &lt; 10ms 停顿 |
| 类加载用 CGLIB 还是 JDK Proxy | CGLIB 动态生成类，元空间压力大；JDK Proxy 不生成类，元空间稳定 |

如果不懂 JVM 内存模型，做技术选型就像"蒙着眼睛选路"，踩坑只是时间问题。

### 1.2 内存区域划分的本质：生命周期与共享范围

JVM 把内存划分为 6 个区域，本质是按**对象生命周期**与**线程共享范围**做的分类：

```
                       线程私有                  线程共享
                  ┌──────────────────┬──────────────────────────┐
                  │                  │                          │
   生命周期短      │  程序计数器      │                          │
                  │  虚拟机栈帧      │                          │
                  │  本地方法栈帧    │                          │
                  │                  │  堆（Eden/Survivor）    │
                  ├──────────────────┤  方法区/元空间           │
   生命周期中      │                  │  直接内存                │
                  │                  │                          │
                  │                  │  堆（Old）               │
   生命周期长      │                  │  方法区/元空间           │
                  │                  │                          │
                  └──────────────────┴──────────────────────────┘
```

这个划分对应三种 GC 策略：

1. **栈帧随方法调用结束自动销毁** - 无需 GC
2. **新生代对象朝生夕死** - Minor GC 频繁但快速
3. **老年代对象长期存活** - Full GC 罕见但耗时

架构师做容量规划时，关键是**估算每类对象的规模与生命周期**，再据此配置 JVM 参数。

### 1.3 元空间替换永久代的架构哲学

JDK 8 把永久代改为元空间，表面是"换个地方存类元数据"，本质是**架构边界的重新划分**：

| 维度 | 永久代（JDK 7-） | 元空间（JDK 8+） |
|------|------------------|------------------|
| 物理位置 | JVM 堆的一部分 | 本地内存（C Heap） |
| 大小限制 | 固定（默认 64MB） | 仅受物理内存限制 |
| GC 触发 | 与 Old 代绑定（Full GC） | 独立 GC（类卸载时） |
| OOM 影响 | 影响 JVM 堆 | 不影响 JVM 堆 |

这个变化背后的设计哲学是 **"把可变的东西放可变的地方"**：

- 类元数据的数量是**运行时动态变化**的（动态代理、JSP、Groovy 脚本都在动态生成类）
- 把动态变化的数据放在固定大小的容器里（永久代），必然会 OOM
- 把动态变化的数据放在动态扩展的容器里（本地内存），更符合数据本质

类似哲学在分布式系统也常见：
- 服务注册中心用临时实例（动态）vs 永久实例（静态）
- 配置中心把动态配置与静态配置分开
- K8s 把声明式 API（动态调谐）vs 命令式 API（静态执行）分开

### 1.4 TLAB 与分布式系统的"本地化优化"

TLAB（Thread Local Allocation Buffer）的设计思路是**"用本地化避免共享竞争"**：

- 堆是共享的，多线程分配对象会竞争指针
- 给每个线程预分配一块私有区域（TLAB），线程在 TLAB 内分配无需同步
- TLAB 用完才去共享区 CAS 申请新 TLAB

这种思路在分布式系统无处不在：

| JVM 层 | 分布式系统层 |
|--------|-------------|
| TLAB | 本地缓存（如 Caffeine） |
| 共享堆 | 远程缓存（如 Redis） |
| CAS 申请 TLAB | 缓存失效后回源 |
| TLAB 浪费比例 1% | 缓存命中率 99% |

架构师做系统设计时，"本地化优化"是核心模式：
- 写缓冲：先写本地内存（如 Netty ChannelBuffer），批量 flush 到网络
- 批量提交：先攒本地队列，批量发送到 MQ
- 读写分离：本地读副本，远程写主库

### 1.5 三色标记与并发算法的"快照"思想

三色标记算法解决的核心问题是 **"并发标记期间业务线程还在修改引用，如何不漏标"**。两种解决方案体现了两种思想：

**增量更新（CMS 选择）**：关注"新增的引用"
- 黑色对象新增引用时，重新标灰
- 思路：跟踪"新增"的变化

**SATB（G1 选择）**：关注"删除的引用"
- 删除引用前，把被删引用记录到队列
- 思路：在 GC 开始时拍"快照"，标记期间删除的对象仍按"开始时存活"处理

SATB 的"快照"思想在分布式系统也有体现：

| JVM GC | 分布式系统 |
|--------|-----------|
| SATB 快照 | 分布式事务的 MVCC 快照隔离 |
| 写屏障记录引用变化 | 数据库的 undo log |
| GC 结束时处理 SATB 队列 | 事务提交时处理 undo log |

架构师理解 SATB 后，对 G1 的调优就不再是"调参试错"，而是"理解算法后的精准调优"。

## 二、JVM 内存模型与在线问诊系统的结合点

### 2.1 三大 JVM 重灾区的内存画像

在线问诊系统的三大 JVM 重灾区，每个都有独特的内存画像：

**IM 长连接网关**（直接内存主导）：

| 内存区域 | 占比 | 主要对象 |
|---------|------|---------|
| 直接内存 | 60% | Netty ByteBuf、Socket Buffer |
| 堆 - 新生代 | 15% | 消息对象、Channel 临时对象 |
| 堆 - 老年代 | 20% | 长连接 Channel、用户会话 |
| 元空间 | 5% | Netty 类、业务类 |

调优重点：直接内存上限、ByteBuf 池化、长连接对象晋升老年代速度。

**视频问诊 SFU**（高对象创建率）：

| 内存区域 | 占比 | 主要对象 |
|---------|------|---------|
| 直接内存 | 30% | RTP 包 ByteBuf、SRTP 加密缓冲 |
| 堆 - 新生代 | 50% | RTP 包解析的临时对象（每秒百万级） |
| 堆 - 老年代 | 15% | 房间状态、录制分片元数据 |
| 元空间 | 5% | mediasoup 代理类 |

调优重点：新生代大小、Minor GC 频率、低延迟收集器选择（ZGC）。

**业务服务（Consult / Rx / Regulator）**（老年代主导）：

| 内存区域 | 占比 | 主要对象 |
|---------|------|---------|
| 直接内存 | 5% | DB 连接 ByteBuf、HTTP 客户端 |
| 堆 - 新生代 | 20% | 短生命周期业务对象 |
| 堆 - 老年代 | 70% | Caffeine 缓存、连接池、医师资质库 |
| 元空间 | 5% | Spring AOP 代理、MyBatis Mapper 代理 |

调优重点：老年代大小、缓存淘汰策略、连接池上限。

### 2.2 容量规划方法论

架构师做容量规划的标准流程：

```
1. 业务规模估算
   │  - 日均问诊订单 5.2w，峰值 8.1w
   │  - 单订单对象 552 字节 + 关联对象（事件、消息）约 5KB
   │  - 峰值对象创建速率：8.1w × 5KB / 8h / 3600s = 14MB/s
   │
   ▼
2. 内存画像建模
   │  - 新生代：5 秒内创建对象 + 20% 余量 = 70MB × 5 = 350MB
   │  - 老年代：缓存（10w 订单 × 552B = 55MB）+ 连接池（500MB）= 600MB
   │  - 直接内存：DB 连接 + HTTP + NIO = 1GB
   │  - 元空间：类数量 × 5KB = 200MB
   │
   ▼
3. JVM 参数推算
   │  - 堆：新生代 500MB + 老年代 1.5GB = 2GB
   │  - 直接内存：2GB（堆 1 倍）
   │  - 元空间：256MB-512MB
   │
   ▼
4. 实例数规划
   │  - 单实例 4GB 内存（堆 2GB + 直接 2GB + 元 0.5GB + OS 0.5GB）
   │  - 峰值 QPS 3500，单实例 800 QPS，需要 6 实例
   │  - 总内存：6 × 4GB = 24GB
   │
   ▼
5. 压测验证
   │  - JMeter 全链路压测 1.5 倍峰值
   │  - JFR 录制，分析 GC 行为、对象分配热点
   │  - 调整参数（如新生代从 500MB 调到 800MB）
```

### 2.3 与简历项目的呼应

Day01 的内容直接呼应简历项目的多处技术亮点：

**简历项目技术亮点 1：IM 消息必达**
- 客户端 seq 补齐机制：依赖 Netty ByteBuf 的内存管理
- 服务端重发补偿：依赖堆内消息对象的内存控制
- 端到端加密：依赖直接内存的零拷贝特性

**简历项目技术亮点 2：视频问诊录制存档**
- SFU 录制分片：每 30s 一片，依赖新生代对象管理避免 GC 压力
- SHA256 实时计算：依赖堆外 ByteBuf 的流式处理
- 录制文件加密：依赖 KMS 的 DEK 在 JVM 堆内短暂驻留

**简历项目技术亮点 3：监管上报 24h 必达**
- 本地消息表：依赖堆内 Map 的内存控制
- 重试队列：依赖 DelayQueue 的内存估算
- 全量对账：依赖游标式查询避免 OOM

第 2 周 Day05 会专门做"在线问诊系统 JVM 实战"，把 Day01 学到的内存模型知识应用到简历项目的具体场景。

## 三、与往周专题的呼应

### 3.1 JVM 内存模型 vs MySQL InnoDB 缓冲池（6月第1周）

| 维度 | JVM 堆 | InnoDB 缓冲池 |
|------|--------|--------------|
| 物理位置 | JVM 进程内 | MySQL 进程内 |
| 内存来源 | JVM 堆（用户态） | OS 内存（用户态） |
| 管理方式 | GC 自动回收 | LRU 自动淘汰 |
| 大小限制 | -Xmx | innodb_buffer_pool_size |
| 数据特征 | 业务对象 | 数据页（16KB） |

两者协同：业务对象在 JVM 堆，数据库页在缓冲池，JVM 通过 JDBC 拉取数据页解析为业务对象。如果业务对象大（如 MongoDB 大文档），JVM 堆压力大；如果查询频繁，缓冲池压力大。

### 3.2 JVM GC STW vs Redis 单线程（6月第2周）

| 维度 | JVM GC STW | Redis 单线程 |
|------|-----------|-------------|
| 停顿原因 | GC 标记/整理时业务线程暂停 | 单线程处理所有请求，无并发 |
| 停顿时长 | G1 100ms，ZGC 10ms | 无停顿（每条命令微秒级） |
| 影响范围 | 所有业务线程暂停 | 后续请求排队 |
| 优化方向 | 选择低延迟收集器、调小堆 | 拆分大 key、避免 KEYS |

两者协同：JVM GC STW 时，Redis 客户端连接会积压，触发连接池等待。架构师设计高 QPS 系统时，必须考虑 GC STW 对下游的影响。

### 3.3 JVM 直接内存 vs ES Lucene MMAP（6月第3周）

| 维度 | JVM 直接内存 | ES MMAP |
|------|-------------|---------|
| 物理位置 | OS 内存 | OS 内存 |
| 访问方式 | NIO ByteBuffer | mmap 系统调用 |
| 管理方式 | JVM 显式释放或 GC 触发 | OS 页缓存管理 |
| 适用场景 | 网络IO、文件IO | 大文件随机读 |

两者协同：ES 用 MMAP 把索引文件映射到内存，JVM 通过 ByteBuf 读取 ES 返回的数据。架构师做 ES + JVM 集成时，要同时关注 JVM 直接内存与 OS 页缓存。

### 3.4 JVM GC 停顿 vs Sentinel 限流误判（6月第4周）

JVM GC STW 会引发请求堆积，触发 Sentinel 限流误判：

- 单实例 GC STW 100ms，请求堆积 100ms × 800 QPS = 80 个请求
- Sentinel 检测到 RT 飙升，触发限流
- 实际是 GC 误判，不是下游故障

架构师设计限流时要考虑：
- RT 阈值留足 GC STW 余量（如 200ms，考虑 100ms GC）
- 单实例异常不算集群故障（多实例 A/B/C 测试）
- 与 JVM 监控联动（GC 期间不触发限流）

### 3.5 JVM 容器化 vs K8s cgroup（7月第3周 Day05）

JVM 在 K8s 容器中的内存管理有特殊坑：

| 维度 | 物理机 JVM | 容器化 JVM |
|------|-----------|-----------|
| 内存感知 | 物理机总内存 | 容器 cgroup 限制（JDK 8u191+ 才完整支持） |
| 堆大小 | -Xmx4g | -XX:+UseContainerSupport -XX:MaxRAMPercentage=75 |
| 直接内存 | 受 -XX:MaxDirectMemorySize 限制 | 受 cgroup memory.limit 限制 |
| OOM 处理 | JVM 抛 OutOfMemoryError | cgroup OOM Killer 杀进程 |

JVM 容器化的关键配置：

```bash
-XX:+UseContainerSupport                # JDK 8u191+ 默认开启
-XX:MaxRAMPercentage=75.0               # 堆最多占容器内存 75%
-XX:InitialRAMPercentage=50.0           # 初始堆占 50%
-XX:MaxDirectMemorySize=1g              # 直接内存上限（容器内存的子集）
-XX:MaxMetaspaceSize=256m               # 元空间上限
```

**陷阱**：cgroup memory.limit 包含堆 + 直接内存 + 元空间 + JVM 内部 + Native 内存。如果堆设 75%，直接内存设 1g，元空间设 256m，JVM 内部约 500MB，那么容器至少需要 (4g × 75% + 1g + 256m + 500m) / 0.75 ≈ 6g。

## 五、Day01 核心架构师命题

**Day01 的核心架构师命题**：理解 JVM 内存模型不是"背诵 6 个区域 + 5 种 GC Roots"，而是建立**"对象生命周期 + 内存画像 + 容量规划"三位一体**的架构能力。

具体三层能力：

**第一层：原理层**
- 理解 JVM 内存区域的物理位置与生命周期
- 理解对象创建到回收的全流程
- 理解三色标记、SATB、逃逸分析的算法原理

**第二层：工程层**
- 能根据业务对象特征估算内存占用
- 能根据业务规模规划 JVM 参数
- 能根据 GC 行为判断系统健康度

**第三层：架构层**
- 能把 JVM 内存模型融入系统设计（如 Netty 选型、缓存选型）
- 能做跨系统的容量规划（如 JVM + OS + K8s 三层内存协同）
- 能根据业务场景选择 GC 收集器与调优方向

Day02 进入 GC 算法与分代收集理论，Day03 讲 GC 收集器全谱系，逐步建立完整 JVM 架构能力。
