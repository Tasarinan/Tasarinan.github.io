## 一、模块定位与业务背景

### 1.1 模块定位

医保对接 Insurance 是互联网医院的**资金流出口模块**--处方开具后的药品费用，需要与医保系统结算，决定患者实际支付金额。这个模块的本质是**平台与医保局的资金契约**：

1. **目录契约**：平台药品库与医保目录的映射，决定哪些药能报、报多少
2. **结算契约**：每张处方的医保报销金额，与医保局系统的实时交互
3. **对账契约**：日终对账，确保平台记录与医保局记录一致

```
处方开具（已审核通过）
   ↓
医保预结算（开方时估算报销金额）
   ↓
医保实时结算（支付时调用医保局接口）
   ↓
患者自付支付（医保报销后的自付部分）
   ↓
日终对账（平台 vs 医保局）
   ↓
差错处理（短款补扣 / 长款退回）
```

### 1.3 合规要求

1. **医保定点资质**：执业挂靠医院必须是医保定点医疗机构
2. **目录同步**：医保目录更新后 24 小时内同步到平台
3. **结算实时性**：患者支付前必须完成医保实时结算
4. **数据上报**：结算数据实时上报医保局，禁止延迟
5. **资金安全**：医保报销金额由医保局直接结算给医院，平台不参与资金流转
6. **隐私保护**：医保结算涉及患者身份证号、医保卡号，需加密存储
7. **对账必达**：每日对账，差异必须 24 小时内处理

**关键设计**：

- `ceiling_price` 医保限价，超出部分患者自付
- `restriction` 使用限制 JSON（适应症、人群、疗程等）
- 全量同步到 ES，便于快速检索

## 三、核心业务流程

### 3.1 医保结算完整链路

```
处方审核通过 -> RxReviewedPassed 事件 -> Insurance服务
                                          │
                                          ├─ 1. 查询患者医保资质（医保局接口）
                                          ├─ 2. 查询医保目录（本地 ES）
                                          ├─ 3. 计算预结算金额
                                          │     ├─ 遍历处方药品
                                          │     ├─ 查医保目录（按省份）
                                          │     ├─ 计算每项报销金额
                                          │     └─ 汇总医保报销 + 自付金额
                                          ├─ 4. 保存预结算记录（status=0预结算）
                                          └─ 5. 推送给患者"去支付"

患者点击支付 -> Pay服务 -> Insurance服务（实时结算）
                                │
                                ├─ 6. 调用医保局实时结算接口
                                │     ├─ 入参：处方信息 + 患者医保信息 + 预结算金额
                                │     ├─ medicare_req_no 幂等控制
                                │     ├─ 超时 3 秒，重试 2 次
                                │     └─ 返回：medicare_resp_no + 实际报销金额
                                ├─ 7. 校验返回金额与预结算金额
                                │     ├─ 差异 < 1 元：接受，更新结算单
                                │     └─ 差异 >= 1 元：拒绝支付，提示患者重新预结算
                                ├─ 8. 更新结算单（status=1已结算）
                                └─ 9. 通知 Pay 服务实际自付金额

患者支付自付部分 -> Pay服务 -> Insurance服务
                                  │
                                  ├─ 10. 更新结算单（关联支付流水）
                                  └─ 11. 触发药品配送

日终对账（T+1 02:00）-> Insurance服务
                          │
                          ├─ 12. 拉取医保局当日结算流水
                          ├─ 13. 与本地结算单逐笔比对
                          ├─ 14. 生成对账记录（无差异 / 短款 / 长款 / 缺失 / 多余）
                          ├─ 15. 差异记录进入待处理队列
                          └─ 16. 监控告警：差异率 > 0.1% 触发 P1
```

### 3.2 医保预结算算法

```java
// 伪代码：医保预结算
public PreSettleResult preSettle(Rx rx, Patient patient) {
    // 1. 查询患者医保资质
    MedicareEligibility eligibility = medicareProviderService.queryEligibility(
        patient.getIdCard(), patient.getProvinceCode());
    if (!eligibility.isEligible()) {
        return PreSettleResult.notEligible();
    }
    
    // 2. 遍历处方药品，计算报销
    BigDecimal totalAmount = BigDecimal.ZERO;
    BigDecimal medicareAmount = BigDecimal.ZERO;
    List<SettleItem> items = new ArrayList<>();
    
    for (DrugItem drug : rx.getDrugItems()) {
        // 查医保目录（按省份）
        MedicareCatalog catalog = medicareCatalogService.findByDrugAndProvince(
            drug.getDrugCode(), patient.getProvinceCode());
        
        if (catalog == null) {
            // 不在医保目录，患者全自付
            items.add(SettleItem.fullSelfPay(drug));
        } else {
            // 计算超限价部分
            BigDecimal overCeiling = calculateOverCeiling(drug, catalog);
            // 计算医保报销金额
            BigDecimal medicarePay = calculateMedicarePay(drug, catalog, overCeiling);
            // 计算自付金额
            BigDecimal selfPay = drug.getTotalPrice().subtract(medicarePay);
            
            items.add(SettleItem.of(drug, catalog, medicarePay, selfPay, overCeiling));
            medicareAmount = medicareAmount.add(medicarePay);
        }
        totalAmount = totalAmount.add(drug.getTotalPrice());
    }
    
    // 3. 计算起付线与封顶线
    BigDecimal afterDeductible = applyDeductible(medicareAmount, eligibility);
    BigDecimal afterCap = applyCap(afterDeductible, eligibility);
    
    return PreSettleResult.builder()
        .totalAmount(totalAmount)
        .medicareAmount(afterCap)
        .selfPayAmount(totalAmount.subtract(afterCap))
        .items(items)
        .build();
}

// 超限价计算
private BigDecimal calculateOverCeiling(DrugItem drug, MedicareCatalog catalog) {
    BigDecimal overUnit = drug.getUnitPrice()
        .subtract(catalog.getCeilingPrice())
        .max(BigDecimal.ZERO);
    return overUnit.multiply(BigDecimal.valueOf(drug.getQuantity()));
}

// 医保报销计算
private BigDecimal calculateMedicarePay(DrugItem drug, MedicareCatalog catalog, 
                                         BigDecimal overCeiling) {
    BigDecimal withinCeiling = drug.getTotalPrice().subtract(overCeiling);
    return withinCeiling.multiply(catalog.getPaymentRatio())
        .divide(BigDecimal.valueOf(100), 2, RoundingMode.HALF_UP);
}
```

## 四、关键技术挑战与方案

### 4.1 23 省级医保平台接口差异统一

**挑战**：
- 国家医保局没有统一接口规范，各省自建平台
- 接口协议不同：HTTP / WebService / MQ
- 加密算法不同：SM2 / RSA / MD5
- 数据格式不同：JSON / XML
- 业务规则不同：起付线 / 封顶线 / 报销比例

**方案**：适配器模式 + 策略模式

```
接口架构：

InsuranceService（业务层）
       │
       ▼
MedicareProviderRouter（路由层）
   ├─ 按 province_code 路由
   └─ 选择对应的 Provider 实现
       │
       ▼
MedicareProvider接口（抽象层）
   ├─ queryEligibility()
   ├─ preSettle()
   ├─ realtimeSettle()
   ├─ revokeSettle()
   └─ querySettlement()
       │
       ▼
具体实现（23 个）
   ├─ BeijingMedicareProvider
   ├─ ShanghaiMedicareProvider
   ├─ GuangdongMedicareProvider
   └─ ...
```

**统一抽象**：

### 4.2 医保局接口稳定性与降级

**挑战**：
- 医保局接口稳定性参差不齐，部分省份可用性 &lt; 99%
- 接口超时常见（3 秒以上）
- 维护窗口期（每月最后一个周末）
- 患者支付时如果医保局接口故障，影响业务

**方案**：多级降级 + 异步补偿

```
实时结算的降级策略：

Level 1（正常）：
   - 调用医保局接口，3 秒超时
   - 失败重试 2 次（间隔 500ms）
   - 成功率 > 99%

Level 2（医保局故障）：
   - 重试 2 次仍失败
   - 降级为"自费结算"（患者全自付，事后报销）
   - 提示患者："医保结算暂不可用，可选择自费支付，事后到医保局报销"
   - 记录"待补结算"状态，T+1 重试

Level 3（大面积故障）：
   - 单省份故障率 > 30%
   - 关闭该省份医保结算（MedicareProvider.enabled = 0）
   - 全部走自费结算
   - 监控告警 P1

Level 4（兜底）：
   - 患者可选择"暂不支付"
   - 处方保留 7 天有效期
   - 医保局恢复后再结算
```

**异步补偿**：

```
待补结算任务（每 30 分钟扫描）：
   SELECT * FROM medicare_settlement
   WHERE settle_status = 0  -- 预结算
     AND medicare_amount > 0  -- 有医保报销
     AND create_time < NOW() - INTERVAL 1 HOUR
     AND retry_count < 8

补偿流程：
1. 调用医保局接口补结算
2. 成功：更新结算单，通知患者"医保已补结算"
3. 失败：retry_count + 1，下次继续
4. 8 次仍失败：进入"待人工处理"
```

### 4.3 结算幂等与防重复扣款

**挑战**：
- 患者可能重复点击支付（网络抖动、APP 重启）
- 医保局接口超时但实际已扣款
- 必须保证同一笔处方只结算一次

**方案**：多层幂等

```
幂等三层防护：

Layer 1：前端
   - 支付按钮点击后立即禁用（防抖）
   - 客户端生成 clientRequestNo

Layer 2：业务层
   - medicare_settlement 表 uk_rx 唯一索引（一张处方只能有一笔结算）
   - medicare_req_no 唯一索引（同一请求号重复调用返回相同结果）

Layer 3：医保局接口
   - medicare_req_no 传给医保局
   - 医保局接口要求带 clientRequestNo，重复返回相同结果

幂等流程：
1. 患者点击支付
2. 生成 medicare_req_no = "MR" + rx_id + timestamp
3. 查询 medicare_settlement 表
   ├─ 已存在且 status=1（已结算）：直接返回结算结果
   └─ 不存在或 status=0：调用医保局
4. 调用医保局接口（带 medicare_req_no）
   ├─ 成功：更新结算单
   ├─ 超时：查询医保局流水
   │   ├─ 已结算：补偿更新本地结算单
   │   └─ 未结算：重试
   └─ 失败：返回错误，患者重试
```

### 4.4 对账系统与差错处理

**挑战**：
- 每日 4.2w 笔结算，对账必须 100% 准确
- 平台与医保局记录可能存在金额差异、记录缺失、记录多余
- 差异必须 24 小时内处理

**方案**：四阶段对账

```
阶段 1：数据准备（T+1 02:00）
   - 平台侧：导出当日所有 settle_status=1 的结算单
   - 医保侧：调用医保局接口拉取当日结算流水
   - 双方数据写入 reconcile_record 表（diff_type=0）

阶段 2：逐笔比对（T+1 03:00）
   - 按 settle_id 匹配双方记录
   - 匹配成功：比对金额
     ├─ 金额一致：diff_type=0（无差异）
     ├─ 平台 > 医保局：diff_type=1（短款，平台少收）
     └─ 平台 < 医保局：diff_type=2（长款，平台多收）
   - 匹配失败：
     ├─ 平台有，医保局无：diff_type=3（缺失）
     └─ 医保局有，平台无：diff_type=4（多余）

阶段 3：差异处理（T+1 04:00）
   - 短款（平台少收）：
     ├─ 差异 < 1 元：挂账，月终汇总处理
     └─ 差异 >= 1 元：调用医保局补扣款接口
   - 长款（平台多收）：
     ├─ 差异 < 1 元：挂账
     └─ 差异 >= 1 元：调用医保局退款接口
   - 缺失：重新调用医保局结算接口
   - 多余：标记为"医保局多结算"，联系医保局处理

阶段 4：报告与监控（T+1 06:00）
   - 生成对账报告
   - 差异率 = 差异笔数 / 总笔数
   - 差异率 > 0.1% 触发 P1 告警
   - 差异金额 > 1000 元触发 P0 告警
```

**对账算法**：

```java
public void reconcile(LocalDate date) {
    // 1. 拉取双方数据
    List<SettleRecord> localRecords = settleRepository.findByDate(date);
    List<SettleRecord> medicareRecords = medicareProvider.querySettlements(date);
    
    // 2. 构建Map（key=settle_id）
    Map<String, SettleRecord> localMap = localRecords.stream()
        .collect(toMap(SettleRecord::getSettleId, r -> r));
    Map<String, SettleRecord> medicareMap = medicareRecords.stream()
        .collect(toMap(SettleRecord::getSettleId, r -> r));
    
    // 3. 逐笔比对
    Set<String> allKeys = new HashSet<>();
    allKeys.addAll(localMap.keySet());
    allKeys.addAll(medicareMap.keySet());
    
    for (String settleId : allKeys) {
        SettleRecord local = localMap.get(settleId);
        SettleRecord medicare = medicareMap.get(settleId);
        
        ReconcileRecord record = new ReconcileRecord();
        record.setSettleId(settleId);
        
        if (local == null) {
            // 平台无，医保局有
            record.setDiffType(4);  // 多余
            record.setDiffAmount(medicare.getMedicareAmount());
        } else if (medicare == null) {
            // 平台有，医保局无
            record.setDiffType(3);  // 缺失
            record.setDiffAmount(local.getMedicareAmount());
        } else {
            // 双方都有，比对金额
            BigDecimal diff = local.getMedicareAmount()
                .subtract(medicare.getMedicareAmount());
            if (diff.compareTo(BigDecimal.ZERO) == 0) {
                record.setDiffType(0);  // 无差异
            } else if (diff.compareTo(BigDecimal.ZERO) > 0) {
                record.setDiffType(1);  // 短款
            } else {
                record.setDiffType(2);  // 长款
            }
            record.setDiffAmount(diff.abs());
        }
        
        reconcileRepository.save(record);
    }
}
```

### 4.6 跨地区医保结算

- 不同省份报销政策不同

## 七、面试追问点

### Q1：医保对接最难的是什么？

**核心答案**：23 个省级医保平台的接口差异统一。
- 接口协议不同（HTTP / WebService / MQ）
- 加密算法不同（SM2 / RSA / MD5）
- 数据格式不同（JSON / XML）
- 业务规则不同（起付线 / 封顶线 / 报销比例）
- 解决方案：适配器模式 + 策略模式，定义 MedicareProvider 接口，每个省份一个实现

### Q2：医保局接口故障怎么办？业务怎么降级？

**核心答案**：多级降级 + 异步补偿
- Level 1（正常）：3 秒超时，重试 2 次
- Level 2（医保局故障）：降级为"自费结算"，事后报销
- Level 3（大面积故障）：关闭该省份医保结算，全部走自费
- Level 4（兜底）：患者可选择"暂不支付"，处方保留 7 天有效期
- 异步补偿：每 30 分钟扫描"待补结算"任务，重试 8 次

### Q3：对账系统怎么设计的？差异怎么处理？

**核心答案**：四阶段对账
- 阶段 1：数据准备（T+1 02:00），拉取双方数据
- 阶段 2：逐笔比对（T+1 03:00），按 settle_id 匹配，识别差异类型
- 阶段 3：差异处理（T+1 04:00），短款补扣 / 长款退款 / 缺失补结算 / 多余联系医保局
- 阶段 4：报告与监控（T+1 06:00），差异率 > 0.1% 触发 P1
- 1 元以下差异挂账月终汇总，1 元以上立即处理

### Q4：医保结算怎么保证幂等？防止重复扣款？

**核心答案**：三层幂等防护
- Layer 1 前端：按钮防抖，生成 clientRequestNo
- Layer 2 业务层：medicare_settlement 表 uk_rx 唯一索引（一张处方只能有一笔结算），medicare_req_no 唯一索引
- Layer 3 医保局接口：medicare_req_no 传给医保局，重复返回相同结果
- 超时处理：查询医保局流水，已结算则补偿更新本地，未结算则重试

### Q5：医保目录怎么同步？12.6w 条数据怎么处理？

**核心答案**：全量 + 增量双策略
- 全量同步（每月 1 次）：拉取全量目录，写入新表，原子切换（RENAME TABLE）
- 增量同步（每日 02:00）：调用医保局增量接口，直接 UPDATE
- ES 同步：Canal 监听 MySQL binlog，实时同步到 ES
- 查询走 ES，&lt; 10ms
- 24 小时内同步保障：失败重试 3 次，告警监控

### Q6：异地就医怎么处理？

**核心答案**：备案 + 就诊地结算
- 患者先在参保地备案，备案信息上传到国家医保平台
- 平台调用国家医保平台查询备案信息
- 调用就诊地医保目录计算报销
- 实时结算时调用就诊地医保局接口
- 资金由就诊地医保局垫付，参保地医保局事后清算
- 对账时区分本地结算和异地结算

### Q7：医保结算和处方开具、支付的关系是什么？

**核心答案**：
- 处方开具（Rx 模块）产出处方，触发医保预结算
- 医保预结算计算医保报销金额 + 患者自付金额
- 患者点击支付时，调用医保实时结算接口（确认报销）
- 实时结算成功后，患者支付自付部分（Pay 服务）
- 支付成功后触发药品配送
- T+1 对账确保平台与医保局记录一致

### Q8：医保数据涉及患者隐私，怎么保护？

**核心答案**：
- 医保卡号 AES-256 加密存储，密钥由 KMS 托管
- 身份证号用 SHA256 哈希存储（patient_id_hash），用于查询
- 日志不打印明文医保卡号、身份证号
- 数据库审计日志，记录所有查询操作
- 等保三级要求：数据传输 mTLS，存储加密，访问审计

### Q9：医保结算的 SLA 怎么保障？

**核心答案**：
- 实时结算延迟 &lt; 2 秒：医保局接口 3 秒超时，重试 2 次
- 结算成功率 99.92%：医保局接口故障降级为自费结算
- 对账差异率 &lt; 0.05%：四阶段对账 + 自动差异处理
- 对账完成时间 T+1 06:00：并行处理 + 批量优化
- 监控告警：P0/P1/P2 三级告警，差异金额 > 1000 元立即电话通知

### Q10：如果让你重新设计这个模块，你会做什么不同？

**核心答案**：
1. **引入医保结算引擎**：用规则引擎（Drools）配置报销规则，减少代码硬编码
2. **支持更多医保场景**：门诊统筹、门诊慢病、住院结算（当前只支持门诊个人账户）
3. **医保智能问答**：基于医保目录 + LLM，回答患者"这个药能报多少"
4. **异地就医全流程**：当前需要患者先备案，未来对接国家医保平台自动备案
5. **医保欺诈检测**：基于历史数据 + ML，识别异常结算（如频繁开药、超量开药）

- **EMR 集成**：医保结算单需同步到执业挂靠医院 EMR
- **医保结算四防闭环**：防漏报 / 防错报 / 防重报 / 防延迟，本模块实现了四防

### 8.3 与分布式事务专题的呼应（5月第3周、第4周）

- **TCC 分布式事务**：医保结算 + 患者支付 + 药品配送是跨服务事务，用 TCC 保证最终一致
- **事务消息**：处方审核通过事件 -> 医保预结算，用 RocketMQ 事务消息
- **幂等消费**：下游服务消费事件需幂等（基于 medicare_req_no）
