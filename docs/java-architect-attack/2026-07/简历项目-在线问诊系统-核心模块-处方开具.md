## 一、模块定位与业务背景

### 1.1 模块定位

处方开具 Rx 是互联网医院的**核心交易凭证生产模块**--所有线上问诊的最终业务产物不是订单，而是**合规电子处方**。一张处方承载三重契约：

1. **医疗契约**：医师对患者病情的诊断结论与用药决策
2. **法律契约**：医师电子签章后，处方具备与纸质处方同等的法律效力
3. **流转契约**：处方向下游流转（审核 -> 配送 -> 医保 -> 用药跟踪）的唯一标识

```
问诊订单（交易契约）
   ↓
诊疗事件（临床记录）
   ↓
处方开具（法律凭证） ← 本模块
   ↓
处方审核 → 药品配送 → 医保结算 → 用药跟踪
```

### 1.2 业务规模与 SLA

| 指标 | 数值 | 说明 |
|------|------|------|
| 日均处方量 | 4.8w 张 | 占问诊订单的 92%（部分订单仅咨询不开方） |
| 峰值处方量 | 8.6w 张/日 | 冬春呼吸道疾病高发期 |
| 处方平均药品数 | 3.2 种 | 单张处方 1-12 种药品 |
| 处方平均金额 | 186 元 | 含西药、中成药、中药饮片 |
| 处方签章延迟 | &lt; 200ms | CA 签章接口 P99 |
| 处方流转延迟 | &lt; 5 秒 | 从签章完成到下游服务接收 |
| 处方合规率 | 99.97% | 监管中心抽检合格率 |
| 处方撤销率 | 0.8% | 药师审核不通过 / 患者取消 |

### 1.3 合规要求（互联网诊疗监管办法）

处方开具必须满足以下合规要求，否则无法通过监管审核：

1. **复诊认定前置**：必须是复诊患者（6 个月内有该科室线下就诊记录）才能在线开方
2. **医师资质核验**：医师须在该平台注册、与执业挂靠医院一致、具备该科室处方权
3. **电子签章合规**：使用 CA 机构颁发的证书，符合《电子签名法》
4. **处方格式合规**：符合《处方管理办法》规定的 11 项必填字段
5. **用药合理性**：超过极量、配伍禁忌、相互作用等需医师二次确认
6. **处方有效期**：最长 7 天，过期自动作废
7. **特殊药品限制**：麻醉药品、第一类精神药品不得在线开具
8. **保存期限**：处方保存 ≥ 15 年（医疗病历保存期限）

## 二、核心数据模型

### 2.1 处方主表 Prescription（MySQL）

```sql
CREATE TABLE `prescription` (
  `rx_id`             varchar(32)  NOT NULL COMMENT '处方号（业务规则生成）',
  `order_id`          bigint       NOT NULL COMMENT '问诊订单ID',
  `patient_id`        bigint       NOT NULL,
  `doctor_id`         bigint       NOT NULL,
  `hospital_id`       bigint       NOT NULL COMMENT '执业挂靠实体医院',
  `dept_code`         varchar(32)  NOT NULL,
  `rx_type`           tinyint      NOT NULL COMMENT '1西药 2中成药 3中药饮片',
  `status`            tinyint      NOT NULL COMMENT '0草稿 1待审核 2审核通过 3审核拒绝 4已作废 5已配送 6已完成',
  `icd10_codes`       json         DEFAULT NULL COMMENT '诊断ICD-10编码列表',
  `diagnosis_text`    varchar(512) NOT NULL COMMENT '诊断文本',
  `drug_items`        json         NOT NULL COMMENT '药品明细（见2.2）',
  `total_amount`      decimal(10,2) NOT NULL COMMENT '处方总金额',
  `valid_hours`       int          NOT NULL DEFAULT 168 COMMENT '有效期小时数（默认7天=168h）',
  `expire_time`       datetime     NOT NULL COMMENT '过期时间',
  `sign_time`         datetime     DEFAULT NULL COMMENT '医师签章时间',
  `ca_cert_id`        varchar(64)  DEFAULT NULL COMMENT 'CA证书ID',
  `signature`         varchar(2048) DEFAULT NULL COMMENT '电子签名值（Base64）',
  `signed_hash`       varchar(64)  DEFAULT NULL COMMENT '处方内容SHA256（签章对象）',
  `review_doctor_id`  bigint       DEFAULT NULL COMMENT '审核药师ID',
  `review_time`       datetime     DEFAULT NULL,
  `review_opinion`    varchar(512) DEFAULT NULL,
  `revoke_reason`     varchar(256) DEFAULT NULL COMMENT '作废原因',
  `version`           int          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  `create_time`       datetime     NOT NULL,
  `update_time`       datetime     NOT NULL,
  PRIMARY KEY (`rx_id`),
  UNIQUE KEY `uk_order_rx_seq` (`order_id`, `rx_seq`),
  KEY `idx_patient_status` (`patient_id`, `status`),
  KEY `idx_doctor_status_time` (`doctor_id`, `status`, `sign_time`),
  KEY `idx_expire_status` (`expire_time`, `status`)
) ENGINE=InnoDB COMMENT='处方主表';
```

**关键设计**：
- `rx_id` 是业务号（非自增），格式见 2.3
- `signed_hash` 锁定处方内容，签章后任何字段变更都会让签名失效
- `expire_time` 独立字段，便于过期任务扫描
- `rx_seq` 是同一订单内的处方序号（一次问诊可开多张处方）

**特殊药品标记**：

- `controlledLevel`：管制级别（精一 / 精二 / 麻醉）

### 2.3 处方号 rx_id 生成规则

```
格式：RX + 8位日期 + 2位医院代码 + 2位科室代码 + 6位序列号 + 1位校验位
示例：RX2025120123010400000173

┌────┬──────────┬──────┬──────┬──────────┬───┐
│ RX │ 20251201 │ 23   │ 01   │ 000001   │ 7 │
└────┴──────────┴──────┴──────┴──────────┴───┘
  前缀  日期      院码  科码   Redis序列   校验

生成逻辑：
1. 日期：取当前日期，便于按日期归档
2. 医院+科室：路由信息，便于按院按科统计
3. 序列号：Redis INCR 按日+院+科维度自增，每日 0 点重置
4. 校验位：Luhn 算法校验，防止录入错误
```

**为什么不用雪花算法**：
- 雪花算法生成的 ID 不可读，不利于处方号人工核对
- 处方号需要包含业务信息（日期、医院、科室），便于审计
- 序列号按"日+院+科"维度，便于按维度查询当天处方量

### 2.4 处方流转事件表 RxEvent（MongoDB）

```javascript
// 集合 rx_event（保存处方全生命周期事件，留存 15 年）
{
  "_id": "evt_xxx",
  "rxId": "RX2025120123010400000173",
  "orderId": "1234567890",
  "eventType": "SIGNED",         // CREATED/SIGNED/REVIEW_PASSED/REVIEW_REJECTED/DISPENSED/COMPLETED/REVOKED
  "eventTime": "2025-12-01T10:30:00Z",
  "operatorId": "12345",
  "operatorRole": "DOCTOR",
  "snapshot": {                   // 事件发生时处方快照
    "status": "1",
    "drugItems": [...],
    "signature": "BASE64..."
  },
  "traceId": "trace-xxx",         // 链路追踪ID
  "regulatorReportStatus": "REPORTED"  // 是否已上报监管
}
```

**事件溯源（Event Sourcing）设计**：
- 处方主表只存当前状态，所有变更记录在事件表
- 事件表不可变，便于审计与回溯
- 任何状态迁移都伴随事件发布到 RocketMQ

## 三、核心业务流程

### 3.1 处方开具完整链路

```
医师端提交处方 -> API网关 -> Rx服务
                            │
                            ├─ 1. 校验医师资质（Credential服务，本地缓存）
                            ├─ 2. 校验复诊认定（Revisit服务，已缓存）
                            ├─ 3. 校验问诊订单状态（必须是 INPROGRESS）
                            ├─ 4. 药品目录校验（医保目录 + 平台药品库）
                            ├─ 5. 用药合理性校验（剂量/配伍/相互作用）
                            ├─ 6. 生成处方号 + 计算金额 + 设置有效期
                            ├─ 7. 计算处方内容SHA256（signed_hash）
                            ├─ 8. 调用CA服务签名（异步，事务消息保证一致性）
                            │     ├─ CA服务返回签名值 + ca_cert_id
                            │     └─ 处方状态 0草稿 -> 1待审核
                            ├─ 9. 发布事件 RxSigned
                            │     ├─ RxReview服务 -> 药师审核（异步）
                            │     ├─ Regulator服务 -> 监管上报（异步，24h必达）
                            │     └─ IM服务 -> 推送给患者"处方已开具"
                            └─ 10. 返回处方号给医师端

药师审核 -> API网关 -> RxReview服务
                        │
                        ├─ 11. 药师查看处方详情
                        ├─ 12. 机审 + 人审双层
                        ├─ 13. 通过：处方状态 1 -> 2
                        │     └─ 发布事件 RxReviewedPassed
                        │         ├─ DrugShip服务 -> 触发配送
                        │         ├─ Insurance服务 -> 医保预结算
                        │         └─ IM服务 -> 推送"处方已审核通过"
                        └─ 14. 拒绝：处方状态 1 -> 3
                              └─ 发布事件 RxReviewedRejected
                                  ├─ IM服务 -> 通知医师修改
                                  └─ 等待医师重新开具
```

```
                         │ 医师签章

                    ┌──────────┐
                    │ 待审核   │

                    │   (1)    │     │ 药师拒绝
                    └────┬─────┘     ▼

                         │ 药师通过   │ 医师修改后重开
                         │            ▼
                         │       ┌──────────┐
                         │       │  草稿    │
                         │       │ DRAFT(0) │
                         │       └──────────┘
                         ▼
                    ┌──────────┐
                    │ 审核通过  │
                    │ REVIEWED │
                    │   (2)     │
                    └────┬─────┘
                         │ 触发配送
                         ▼
                    ┌──────────┐
                    │ 已配送   │
                    │DISPENSED │
                    │   (5)     │
                    └────┬─────┘
                         │ 患者签收
                         ▼
                    ┌──────────┐
                    │ 已完成   │
                    │COMPLETED │
                    │   (6)     │
                    └──────────┘

       任意状态（除已完成）均可作废
                    ↓
              ┌──────────┐
              │ 已作废   │
              │ REVOKED  │
              │  (4)     │
              └──────────┘
```

**关键约束**：
- `DRAFT -> REVIEWING` 必须同步（CA 签章是强一致性操作）
- `REVIEWING -> REVIEWED` 异步（药师审核可能耗时数分钟到数小时）
- `REVIEWED -> DISPENSED` 异步（事件驱动，配送服务订阅）
- 过期处方自动作废（定时任务扫描 `expire_time`）

## 四、关键技术挑战与方案

### 4.1 电子签章合规与性能

**挑战**：
- 合规要求：CA 签章必须用国密 SM2 算法，符合《电子签名法》
- 性能要求：签章延迟 &lt; 200ms（不能让医师等太久）
- 可靠性要求：签章失败不能让处方"半签章"状态
- 一致性要求：处方内容与签名必须严格一致

**方案**：

```
签章流程：
1. Rx服务计算处方内容 SHA256（signed_hash）
   ├─ 待签名内容：rx_id + patient_id + doctor_id + drug_items JSON + diagnosis + sign_time
   └─ SHA256(input) -> 32 字节哈希

2. 调用 CA 服务（独立微服务，对接 CFCA / 上海CA）
   ├─ 入参：signed_hash + 医师 ca_cert_id + 时间戳
   ├─ CA 服务用 SM2 私钥签名（HSM 硬件加密机）
   └─ 返回：signature(Base64) + ca_cert_id + sign_time

3. Rx服务更新处方表
   ├─ signature = Base64 签名值
   ├─ ca_cert_id = 证书ID
   ├─ sign_time = 签章时间
   ├─ status = 1 待审核
   └─ 用乐观锁 version 校验

4. 签章验证（任何人可验证）
   ├─ 用 CA 公钥（CA 证书）验证 signature
   ├─ 验证签名对象是否为 signed_hash
   └─ 验证 signed_hash 是否与当前处方内容一致
```

**性能优化**：
- CA 服务本地缓存医师证书（Redis），避免每次查库
- 签章使用 HSM 硬件加密机，单次签名 &lt; 50ms
- 网络往返 &lt; 100ms（同机房部署）
- 总延迟 &lt; 200ms

**一致性保障**：
- 处方表 + 签章记录表（CA 服务）跨服务，用事务消息保证最终一致
- 签章失败：处方回滚到 DRAFT 状态
- 签章成功但 DB 更新失败：CA 服务有签章记录，下次补偿

### 4.2 处方号生成的高并发与唯一性

**挑战**：
- 峰值 8.6w 张/日，但集中在 9:00-11:00、14:00-16:00，峰值 QPS 约 200
- 处方号必须全局唯一、可读、含业务信息
- 序列号按"日+院+科"维度自增

**方案**：

```
Redis INCR + Lua 脚本：
   key = "rx:seq:{date}:{hospitalCode}:{deptCode}"
   value = INCR key
   EXPIRE key 86400  # 1天过期

生成序列号：
   seq = Redis INCR
   if seq > 999999: 报错（单日单院单科不超过 100w 张）
   seq_str = String.format("%06d", seq)

校验位（Luhn 算法）：
   full_rx_id = "RX" + date + hospital + dept + seq_str
   check_digit = luhn(full_rx_id)
   rx_id = full_rx_id + check_digit
```

**Redis 故障降级**：
- Redis 集群故障时，降级到 MySQL 序列表
- MySQL 表：`rx_seq(date, hospital, dept, seq)`，用 `SELECT ... FOR UPDATE` 加锁
- 性能从 200 QPS 降到 50 QPS，但保证唯一性

**为什么不用 UUID**：
- 不可读，无法人工核对
- 不含业务信息
- 索引性能差（随机字符串）

### 4.3 用药合理性审核

**挑战**：
- 必须在医师提交处方时**同步**完成机审（&lt; 500ms）
- 审核规则复杂：剂量、配伍、相互作用、特殊人群
- 规则库频繁更新（新药上市、新指南发布）

**方案**：双层机审 + 人审

```
机审（同步，< 500ms）：
├─ 1. 单药剂量校验
│   ├─ 单次剂量是否超过极量
│   ├─ 日剂量是否超过极量
│   └─ 疗程是否超过限制
├─ 2. 配伍禁忌校验
│   ├─ 药品两两组合查禁忌表
│   └─ 命中即拒绝
├─ 3. 相互作用校验
│   ├─ 查药品相互作用库
│   └─ 严重相互作用拒绝，中度警告
├─ 4. 特殊人群校验
│   ├─ 妊娠期 / 哺乳期禁忌
│   ├─ 儿童禁忌
│   ├─ 老年人禁忌
│   └─ 肝肾功能不全禁忌
└─ 5. 抗生素专项校验
    ├─ 是否有抗生素使用指征
    ├─ 抗生素分级管理（非限制 / 限制 / 特殊使用）
    └─ 特殊使用级需主任医师签章

规则引擎：Drools
├─ 规则库：~5000 条规则
├─ 知识库：国家药品不良反应监测中心数据
└─ 更新频率：每月 1 次

人审（异步，药师审核）：
├─ 机审通过后进入待审核队列
├─ 药师在工作台审核
├─ 审核时限：普通处方 30 分钟，特殊处方 2 小时
└─ 药师可拒绝 / 通过 / 退回医师修改
```

### 4.4 处方内容与签名的一致性

**挑战**：
- 处方签章后，任何字段变更都应让签名失效
- 但业务可能需要修改处方（如药师退回医师修改）
- 如何区分"已签章不可改"与"可修改"

**方案**：不可变快照 + 重新签章

```
签章后处方不可变：
- status = REVIEWING 及以后状态，drug_items / diagnosis 等字段不可修改
- 任何修改尝试都会让 signed_hash 与内容不匹配
- 验证签章时发现不一致，拒绝

修改流程：
1. 医师"作废"当前处方（status = REVOKED）
2. 复制原处方内容到新处方（status = DRAFT）
3. 医师修改新处方
4. 重新签章（生成新 rx_id）
5. 老处方保留作废记录，新处方走完整流程

数据库约束：
- trigger: UPDATE prescription SET drug_items = ... WHERE status >= 1 -> 报错
- 应用层校验：status >= REVIEWING 时禁止修改关键字段
```

### 4.5 处方有效期管理与过期作废

**挑战**：
- 处方有效期最长 7 天（168 小时）
- 不同药品有效期不同（如麻醉药品 1 天）
- 过期处方必须自动作废，不能配送

**方案**：

```
定时任务（每 10 分钟扫描一次）：
   SELECT rx_id FROM prescription
   WHERE status IN (1, 2)  -- 待审核或已审核未配送
     AND expire_time < NOW()

作废流程：
1. 扫描过期处方
2. 状态迁移到 REVOKED(4)
3. revoke_reason = '已过期'
4. 发布事件 RxExpired
   ├─ IM服务 -> 通知患者"处方已过期，请重新问诊"
   ├─ RxReview服务 -> 从审核队列移除
   └─ Regulator服务 -> 上报作废事件

为什么 10 分钟：
- 太短（如 1 分钟）：扫描频繁，DB 压力大
- 太长（如 1 小时）：过期处方可能在窗口期内被配送
- 10 分钟是业务容忍与 DB 压力的平衡
```

### 4.6 与下游服务的事件驱动衔接

**挑战**：
- 处方签章后需触发药师审核、配送、医保、监管上报等多个下游
- 任何下游故障不能影响处方开具主流程
- 必须保证事件最终送达

**方案**：RocketMQ 事务消息

```java
// 伪代码：处方签章 + 事件发布
@Transactional
public void signPrescription(SignRequest req) {
    // 1. 更新处方状态（本地事务）
    Prescription rx = rxRepository.findById(req.getRxId());
    rx.sign(req.getSignature(), req.getCaCertId());
    rxRepository.save(rx);
    
    // 2. 发送事务消息（半消息）
    rocketMQTemplate.sendMessageInTransaction(
        "RxSignedTopic",
        RxSignedEvent.builder()
            .rxId(rx.getRxId())
            .orderId(rx.getOrderId())
            .doctorId(rx.getDoctorId())
            .build(),
        rx.getRxId()  // 业务参数
    );
}

// 事务回查（broker 半消息超时未确认时调用）
@Transactional
public void checkLocalTransaction(String rxId) {
    Prescription rx = rxRepository.findById(rxId);
    if (rx.getStatus() >= REVIEWING) {
        return CommitMessage;
    } else {
        return RollbackMessage;
    }
}

// 下游服务订阅
@RocketMQMessageListener(topic = "RxSignedTopic")
public class RxReviewSubscriber {
    public void onMessage(RxSignedEvent event) {
        // 药师审核服务：加入审核队列
        reviewQueue.add(event.getRxId());
    }
}
```

**事务消息的优势**：
- 本地事务与消息发送的原子性
- 半消息机制避免消息丢失
- 事务回查保证最终一致

## 七、面试追问点

### Q1：处方开具的电子签章是怎么实现的？为什么用 SM2 不用 RSA？

**核心答案**：
- 使用 CFCA 颁发的医师个人证书，签名算法用国密 SM2
- 选 SM2 的原因：1) 国家法规要求（医疗行业等保三级）；2) SM2 比 RSA 更短（256 位 vs 2048 位），签名值更小；3) 性能更好（签名速度比 RSA-2048 快 3-5 倍）
- 签名流程：处方内容 SHA256 -> CA 服务 SM2 签名 -> 返回签名值 + 证书 ID
- 验证流程：CA 公钥验签 + 内容哈希比对

### Q2：处方号为什么不用雪花算法？怎么保证唯一性？

**核心答案**：
- 雪花算法不可读，不含业务信息，无法人工核对
- 处方号格式：RX + 日期 + 院码 + 科码 + 6位序列 + 校验位
- 唯一性保证：Redis INCR 按"日+院+科"维度自增，序列号 6 位（单日单院单科最多 100w 张）
- Redis 故障降级：MySQL 序列表 + FOR UPDATE 加锁
- 校验位：Luhn 算法，防止录入错误

### Q3：处方签章后医师发现开错了怎么办？

**核心答案**：
- 签章后处方不可变（status >= REVIEWING 时禁止修改关键字段）
- 修改流程：作废当前处方（status = REVOKED） -> 复制内容到新处方 -> 医师修改 -> 重新签章
- 老处方保留作废记录，新处方走完整流程
- 监管上报：作废事件也要上报（24h 内必达）

### Q4：处方开具和药师审核是同步还是异步？为什么？

**核心答案**：
- 处方开具（含签章）同步，药师审核异步
- 同步原因：医师提交后需要立即拿到处方号，签章是强一致性操作
- 异步原因：药师审核可能耗时数分钟到数小时，不能让医师等待
- 实现：RocketMQ 事务消息保证签章与事件发布的原子性，下游服务异步订阅

### Q5：处方有效期管理怎么做的？过期处方怎么处理？

**核心答案**：
- 处方有效期最长 7 天（168 小时），不同药品有效期不同
- 定时任务每 10 分钟扫描过期处方（status IN 待审核/已审核未配送 AND expire_time &lt; NOW()）
- 作废流程：状态迁移到 REVOKED + 发布事件 RxExpired + 通知患者/药师/监管
- 10 分钟是业务容忍与 DB 压力的平衡（太短 DB 压力大，太长过期处方可能被配送）

### Q6：用药合理性审核怎么做的？规则库怎么更新？

**核心答案**：
- 双层机审 + 人审
- 机审（同步 &lt; 500ms）：单药剂量 / 配伍禁忌 / 相互作用 / 特殊人群 / 抗生素专项
- 规则引擎用 Drools，规则库 ~5000 条
- 规则库更新：每月 1 次，从国家药品不良反应监测中心同步数据
- 人审：药师在工作台审核，普通处方 30 分钟，特殊处方 2 小时

### Q7：处方数据要保存 15 年，存储怎么规划？

**核心答案**：
- MySQL 分库分表：按 patient_id 分片，64 库 × 16 表 = 1024 表
- 15 年单表数据量 ~460w 条，索引优化后查询 &lt; 50ms
- 冷热分离：3 年内数据在 MySQL，3 年前归档到 MongoDB + OSS
- MongoDB 存事件流（rx_event），便于审计回溯
- OSS 存处方 PDF（带电子签章），便于法律取证

### Q8：如果 CA 服务挂了怎么办？处方开具还能继续吗？

**核心答案**：
- CA 服务是处方开具的强依赖，挂了无法签章
- 降级策略：1) CA 服务多机房部署，故障切换；2) 本地缓存医师证书，短暂可用本地签章（事后补偿）；3) 处方可暂存为 DRAFT 状态，CA 恢复后批量签章
- 业务影响：处方开具延迟，但不会丢失（DRAFT 状态保留）
- 监控告警：CA 服务延迟 P99 > 500ms 立即告警

### Q9：处方开具的高并发怎么支撑？峰值 200 QPS 怎么实现？

**核心答案**：
- 200 QPS 不算高，主要瓶颈在 CA 签章（外部服务调用）
- 优化点：1) CA 服务本地缓存医师证书；2) 签章使用 HSM 硬件加密机；3) CA 服务同机房部署
- 数据库：MySQL 分库分表，单表 QPS &lt; 50
- Redis：处方号生成用 INCR，单 Redis 节点 10w+ QPS
- 业务层：无状态，K8s HPA 自动伸缩

### Q10：处方与问诊订单、诊疗事件的关系是什么？

**核心答案**：
- 一次问诊订单可产生多张处方（如医师先开主药，后补开辅助药）
- 处方属于诊疗事件的一部分（诊疗事件包含诊断 + 处方 + 检查检验）
- 数据归属：订单归平台，诊疗事件（含处方）归执业挂靠医院 EMR
- 保存期限：订单 5 年，处方 15 年
- 处方号 rx_id 关联 order_id，便于双向查询
