## 难点一：医患 IM 消息必达与合规存档

### 1.1 问题背景

在线问诊的 IM 与普通聊天 IM 有本质差异：

| 维度 | 普通 IM（微信/钉钉） | 医患 IM |
|------|---------------------|---------|
| 消息丢失容忍 | 百万分之一可接受 | **零容忍**（医疗纠纷证据） |
| 撤回消息 | 撤回即删除 | **撤回仍需保留合规副本**（监管要求保存 15 年） |
| 敏感词 | 提示用户即可 | **命中后人工审核**（涉及用药指导、危重症状） |
| 隐私 | 端到端加密 | 端到端加密 + **患者图片 OCR 脱敏**（身份证、化验单） |
| 消息检索 | 用户本地检索 | **服务端全文检索**（医师调阅历史问诊） |
| 留痕 | 可不留痕 | **每条消息全生命周期留痕**（发送、投递、已读、撤回、审核） |

业务规模：日均 210w 消息，峰值 360w/s，单会话最大消息数 500+，跨网络场景（医院内网 / 4G / 家庭 Wi-Fi / 弱网）。

### 1.2 技术挑战

1. **消息必达**：网络抖动、客户端离线、长连接断开、服务重启等场景下，消息不能丢
2. **严格有序**：会话内消息必须按发送顺序展示（医疗场景错序可能引发误诊）
3. **撤回与合规的矛盾**：用户撤回的消息，对端不可见，但监管可查
4. **敏感词实时性**：危重症状（如"胸闷、剧烈头痛"）需秒级触发医师提醒，用药指导类敏感词需 30s 内人工审核
5. **海量消息存储与检索**：年新增 7.6 亿条消息，需支持按患者/医师/时间/关键词快速检索

### 1.3 方案选型对比

#### 1.3.1 消息投递可靠性方案对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| **方案 A：发件箱模式（Outbox）** | 消息表与业务数据本地事务，保证不丢 | 性能瓶颈在数据库 | 部分采用（关键消息） |
| **方案 B：RocketMQ 事务消息** | 高性能，与业务解耦 | 实现复杂，需要回查接口 | **核心采用** |
| 方案 C：直接发送 MQ | 简单 | 业务失败/网络抖动会丢消息 | 不采用 |
| 方案 D：客户端 ACK + 重发 | 简单 | 服务端无主动权，依赖客户端 | **辅助采用** |

最终方案：**RocketMQ 事务消息 + 客户端 seq 补齐 + 服务端重发补偿**三层保障。

#### 1.3.2 消息存档方案对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 方案 A：MySQL 分库分表 | 强一致性 | 写入瓶颈，schema 不灵活 | 不采用 |
| 方案 B：HBase | 海量写入、便宜 | 检索能力弱 | 不采用 |
| **方案 C：MongoDB** | 写入密集、schema 灵活、分片方便 | 强一致性弱于 MySQL | **核心采用** |
| 方案 D：TiDB | 兼容 MySQL、水平扩展 | 成本高 | 不采用 |

最终方案：**MongoDB 分片集群**（按 sessionId 哈希分片）+ **冷热分离**（6 个月内热数据 MongoDB，6 个月后归档 OSS + Hive）。

### 1.4 核心实现

#### 1.4.1 消息投递三层保障

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：RocketMQ 事务消息（保证消息从业务到 MQ 不丢）       │
│                                                             │
│  发送消息 -> 半消息 -> 执行本地事务（写 MongoDB）-> 提交     │
│                   ↓                                         │
│              本地事务失败 -> 回查接口 -> 回滚                │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  第二层：客户端 seq 补齐（保证客户端不丢）                   │
│                                                             │
│  - 服务端按 sessionId 维护严格递增 seq（Redis INCR）         │
│  - 客户端本地维护 maxSeq                                     │
│  - 客户端重连后调用 pullMessage(sessionId, maxSeq+1, ...)    │
│  - 服务端按 seq 范围返回缺失消息                            │
└─────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────┐
│  第三层：服务端重发补偿（保证 ACK 不丢）                     │
│                                                             │
│  - 消息发送后写入"待ACK"表（带 TTL 30s）                    │
│  - 30s 未 ACK -> 进入重发队列（指数退避 3 次：30s/1min/3min）│
│  - 3 次仍未 ACK -> 走离线推送（APNs/FCM/小米/华为）         │
│  - 离线推送失败 -> 标记"投递失败"，每日对账补偿              │
└─────────────────────────────────────────────────────────────┘
```

#### 1.4.3 敏感词双层过滤

```
消息发送 -> IM服务
            │
            ├─ 第一层：实时正则匹配（DFA 算法，10w+ 词库）
            │   ├─ 命中"危重症状"（胸闷/剧烈头痛/呼吸困难）-> 立即推送医师高亮提醒
            │   ├─ 命中"用药指导类"（具体药品用法）-> 标记待审核，但仍投递
            │   └─ 命中"违禁词"（涉政涉黄）-> 拦截，不投递，记录日志
            │
            └─ 第二层：异步语义分析（自研 NLP 模型）
                ├─ 识别隐含敏感意图（如"那个药"代指违禁药）
                └─ 命中后人工审核工单
```

**危重症状关键词触发**：医患 IM 中患者发送"胸闷、胸痛、呼吸困难、剧烈头痛、意识模糊"等关键词时，系统秒级给医师端推送红色高亮提醒，并触发自动问诊升级（建议转电话/视频问诊或线下急诊）。

### 1.5 量化收益

- 端到端投递成功率从 99.91% 提升到 **99.995%**（年丢失消息从 70w 条降到 1w 条以内）
- 客户端 seq 补齐机制使重连后消息丢失率从 0.3% 降到 **0**
- 撤回消息合规副本设计通过等保三级测评，零监管处罚
- 危重症状秒级触发医师提醒，年触发 1200+ 次早期干预

### 1.6 面试追问点

- **Q：为什么不用 HBase 存消息？**
  A：HBase 检索能力弱，而医患 IM 需要按患者/医师/时间/关键词多维检索，MongoDB 的索引能力更适合。HBase 更适合纯时序数据。

- **Q：seq 用 Redis INCR，Redis 挂了怎么办？**
  A：Redis Cluster 高可用，单节点故障不影响。极端情况 Redis 整集群故障，降级到 MongoDB 的 `findAndModify` 原子操作取 maxSeq+1，性能下降但功能不丢。

- **Q：合规副本会不会被反查篡改？**
  A：合规副本的 `originContentHash` 在撤回时计算并上链（联盟链），监管审计时可对比链上 hash 与副本内容，确保未被篡改。

- **Q：消息加密怎么做的？**
  A：信封加密。消息内容用 AES-256（DEK）加密，DEK 用 KMS 托管的 KEK 包装，KEK 由 HSM 保护。医师/患者调阅时通过 KMS 临时获取 DEK，DEK 不落盘。

## 难点二：视频问诊 WebRTC 信令与录制存档

### 2.1 问题背景

视频问诊是互联网医院最高规格的服务，监管要求：
- 视频全程录制存档，保存 ≥ 15 年
- 录制文件完整性可验证（防篡改）
- 录制文件加密存储，访问需审计
- 视频中断率 &lt; 5%，呼叫准时率 ≥ 98%

业务规模：日均 3200 路视频问诊，峰值 5800 路，平均时长 15 min，最长 30 min。每路视频双向录制，单路带宽 1.5Mbps。

### 2.2 技术挑战

1. **多网络场景下的 ICE 重协商**：医师 PC（医院内网）-> PAD（4G）-> 手机（家庭 Wi-Fi）切换时不能中断通话
2. **录制完整性**：录制过程中任何分片丢失都可能导致法律证据失效
3. **录制加密与密钥管理**：录制文件含敏感医疗信息，加密密钥必须独立管理
4. **SFU 节点分配**：跨地域分配，避免长延时；故障切换不能中断通话
5. **合规审计**：录制文件的访问、调阅、下载需全链路审计

### 2.3 方案选型对比

#### 2.3.1 视频媒体方案对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 方案 A：商用 SDK（声网/即构） | 接入快、稳定 | 成本高（年费 480w+）、数据出域合规风险 | 不采用 |
| 方案 B：纯 P2P（WebRTC） | 无中转成本 | 跨网络场景 P2P 失败率 30%+ | 不采用 |
| **方案 C：自研 SFU + TURN** | 可控、合规、成本低 | 研发投入大 | **采用** |
| 方案 D：开源 SFU（Janus/mediasoup） | 研发投入小 | 二次开发量大、医疗场景定制能力弱 | 部分参考 |

最终方案：**基于 mediasoup 二次开发自研 SFU**，部署 TURN 中继作为兜底。

#### 2.3.2 录制方案对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 方案 A：客户端录制 | 服务端无压力 | 易被篡改，不可信 | 不采用 |
| **方案 B：SFU 服务端录制** | 不可篡改、可控 | 服务端压力大 | **采用** |
| 方案 C：独立录制服务 | 解耦 | 架构复杂 | 不采用 |

#### 2.4.2 ICE 重协商的多端切换处理

```java
// 伪代码：医师端切换设备时的 ICE 重协商
public class VideoSessionManager {

    /**
     * 医师多端切换：保持 roomId 不变，重新协商 ICE
     */
    public void handleDoctorSwitchDevice(String roomId, String newDeviceId,
                                         String oldDeviceId, String newSdpOffer) {
        VideoSession session = videoSessionRepository.findById(roomId);

        // 1. 校验切换合法性（同一医师、同会话、时间窗内）
        if (!session.getDoctorId().equals(currentDoctorId)
            || !session.isActive()) {
            throw new BizException("非法切换");
        }

        // 2. 旧设备优雅退出（不断开媒体流）
        sfuService.gracefulDisconnectDevice(roomId, oldDeviceId);

        // 3. 新设备加入同一房间
        SdpAnswer newAnswer = sfuService.negotiate(roomId, newDeviceId, newSdpOffer);

        // 4. 推送给新设备
        signalingGateway.pushToClient(newDeviceId, newAnswer);

        // 5. 录制流不中断（SFU 保持录制进程）
        // 录制文件继续写入同一路径，最终合并

        // 6. 记录切换事件（合规审计）
        auditService.logDeviceSwitch(roomId, oldDeviceId, newDeviceId);
    }
}
```

**关键设计**：
- roomId 全程不变，录制流不中断
- 旧设备优雅断开（不立即销毁媒体流），等待新设备协商成功后再清理
- 切换事件入审计日志，监管可查

#### 2.4.3 录制完整性保障

```
录制流程（分片 + 实时哈希）：
   │
   ├─ 1. SFU 启动录制，每 30s 切一个分片
   │     └─ 分片文件：record_{roomId}_{seq}_{timestamp}.webm
   │
   ├─ 2. 每个分片实时计算 SHA256
   │     └─ sha256:abc123...
   │
   ├─ 3. 分片上传 MinIO（加密）
   │     └─ AES-256 加密，DEK 由 KMS 托管
   │
   ├─ 4. 分片元数据写入 MySQL
   │     └─ {roomId, seq, sha256, uploadTime, kmsKeyId}
   │
   ├─ 5. 通话结束时合并分片
   │     ├─ 计算整体 SHA256（所有分片哈希串联再哈希）
   │     ├─ 整体 SHA256 上链（联盟链）
   │     └─ 生成录制清单 manifest.json
   │
   └─ 6. 调阅时校验
         ├─ 拉取 manifest.json
         ├─ 按分片拉取并计算 SHA256
         ├─ 与元数据 SHA256 比对
         └─ 与链上 SHA256 比对（最终态）
```

**关键设计**：
- 分片粒度 30s：平衡录制连续性与故障恢复（SFU 故障最多丢 30s，但有最后一片哈希可验证）
- 实时哈希：分片上传时即计算 SHA256，避免录制结束后批量计算延迟
- 链上存证：整体 SHA256 上链（仅 hash，不含内容），防篡改
- 调阅校验：调阅时三层校验（分片 SHA256 -> manifest -> 链上 hash）

#### 2.4.4 SFU 节点分配与故障切换

```java
public class SfuRouter {

    /**
     * 分配 SFU 节点
     * 策略：地域就近 + 负载均衡 + 容量阈值
     */
    public SfuNode allocate(String patientRegion, String doctorRegion) {
        // 1. 计算最优地域
        String preferredRegion = regionMatcher.match(patientRegion, doctorRegion);

        // 2. 该地域内 SFU 节点按负载排序
        List<SfuNode> candidates = sfuRegistry.getByRegion(preferredRegion).stream()
            .filter(node -> node.getActiveRooms() < node.getMaxRooms() * 0.8)
            .sorted(Comparator.comparingInt(SfuNode::getActiveRooms))
            .collect(Collectors.toList());

        if (candidates.isEmpty()) {
            // 3. 跨地域兜底
            candidates = sfuRegistry.getAllHealthy().stream()
                .filter(node -> node.getActiveRooms() < node.getMaxRooms() * 0.7)
                .sorted(Comparator.comparingInt(SfuNode::getActiveRooms))
                .collect(Collectors.toList());
        }

        return candidates.get(0);
    }

    /**
     * SFU 故障切换
     * 触发条件：心跳丢失 3 次（15s）
     */
    public void failover(String roomId, String failedNode) {
        // 1. 标记原节点不可用
        sfuRegistry.markUnhealthy(failedNode);

        // 2. 分配新节点
        SfuNode newNode = allocate(...);

        // 3. 通知医患双端重新协商 ICE（保持 roomId）
        signalingGateway.pushIceRestart(roomId);

        // 4. 录制流不中断：新 SFU 接管录制，分片继续写入
        // 录制清单记录 SFU 切换点，调阅时按片段拼接
    }
}
```

### 2.5 量化收益

- 视频问诊呼叫准时率 **98.7%**（项目前 92.3%）
- 通话中断率从 8.2% 降到 **3.1%**（含网络抖动）
- 录制完整性 **100%**（零篡改、零丢失）
- 自研 SFU 替换商用 SDK，年节省 **480w** 通信费用
- SFU 故障切换 RTO &lt; 30s，对医患透明

### 2.6 面试追问点

- **Q：为什么不用商用 SDK（声网/即构）？**
  A：三方面考虑：成本（年费 480w+）、数据出域合规风险（医疗数据不允许出域）、定制能力（医疗场景需录制上链、密钥管理、合规审计，商用 SDK 难以深度定制）。

- **Q：录制分片为什么是 30s？**
  A：权衡。分片太短（如 5s）元数据膨胀、上传开销大；分片太长（如 5min）故障恢复时丢失数据多。30s 是经过压测的最优值，单分片约 5MB，上传 &lt; 1s。

- **Q：链上存证为什么用联盟链而不是公链？**
  A：医疗数据合规要求，联盟链节点由监管机构、医院、平台三方组成，写入需多方共识，公链无法满足准入要求。

- **Q：SFU 故障切换时录制怎么续上？**
  A：原 SFU 录制分片已上传（每 30s 一片），新 SFU 接管后从下一个 30s 分片开始录制。录制清单记录切换点，调阅时按分片顺序拼接，切换点可能有 &lt; 1s 的视频断点（音频连续）。

## 难点三：问诊订单状态机与跨服务一致性

### 3.1 问题背景

问诊订单生命周期涉及 9 个状态、5 个跨服务调用点（IM、Schedule、Rx、Regulator、Pay），每个状态迁移都伴随多个下游事件。难点在于：

- 状态机本身要正确（不可逆状态、并发迁移、异常状态）
- 跨服务的数据最终一致（订单状态 vs IM会话 vs 号源 vs 处方）
- 异常恢复（服务宕机、网络抖动、消息重复）

### 3.2 技术挑战

1. **状态机正确性**：并发请求下不能出现状态回退、跳跃
2. **跨服务一致性**：订单状态变更后，下游事件必须全部最终成功
3. **幂等性**：消息重复投递不能导致重复处理
4. **异常补偿**：下游失败时订单状态如何回滚或推进
5. **长期未决订单处理**：超时未支付、超时未接诊等场景

### 3.3 方案选型对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| **方案 A：状态机 + 事务消息** | 解耦、可扩展 | 实现复杂 | **采用** |
| 方案 B：Seata AT 强一致 | 简单 | 性能差、跨服务长事务 | 仅支付场景采用 |
| 方案 C：TCC | 强一致 | 开发成本高、补偿逻辑复杂 | 不采用 |
| 方案 D： Saga | 长事务友好 | 实现复杂 | 不采用 |

最终方案：**核心链路用 RocketMQ 事务消息保证订单与消息一致，下游服务幂等消费；支付场景用 Seata AT；问诊结束触发的多下游用 Saga 思想 + 补偿任务**。

```java
@EnableStateMachineFactory
public class ConsultOrderStateMachineConfig extends StateMachineConfigurerAdapter<ConsultStatus, ConsultEvent> {

    @Override
    public void configure(StateMachineStateConfigurer<ConsultStatus, ConsultEvent> states) {
        states
            .withStates()
            .initial(ConsultStatus.UNPAID)
            .states(EnumSet.allOf(ConsultStatus.class))
            .end(ConsultStatus.CLOSED)
            .end(ConsultStatus.REFUNDED);
    }

    @Override
    public void configure(StateMachineTransitionConfigurer<ConsultStatus, ConsultEvent> transitions) {
        transitions
            // UNPAID -> PENDING（支付成功）
            .withExternal()
                .source(UNPAID).target(PENDING)
                .event(PAY_SUCCESS)
                .action(paySuccessAction())
                .guard(paySuccessGuard())
            .and()
            // PENDING -> INPROGRESS（医师接诊）
            .withExternal()
                .source(PENDING).target(INPROGRESS)
                .event(DOCTOR_ACCEPT)
                .action(doctorAcceptAction())
                .guard(doctorAcceptGuard())
            .and()
            // INPROGRESS -> CLOSED（医师结束问诊）
            .withExternal()
                .source(INPROGRESS).target(ENDING)
                .event(DOCTOR_END)
                .guard(doctorEndGuard())  // 校验诊疗事件已补全
            .and()
            .withExternal()
                .source(ENDING).target(CLOSED)
                .event(ASYNC_COMPLETE)
                .action(asyncCompleteAction());
    }

    /**
     * 接诊 Guard：校验号源、复诊认定、医师资质
     */
    private Guard<ConsultStatus, ConsultEvent> doctorAcceptGuard() {
        return ctx -> {
            Long orderId = (Long) ctx.getMessageHeader("orderId");
            ConsultOrder order = orderRepository.findById(orderId);

            // 1. 校验医师资质（本地缓存 + 异步刷新）

                return false;
            }

            // 2. 校验号源未过期
            if (!scheduleService.checkSlotValid(order.getDoctorId(), orderId)) {
                return false;
            }

            // 3. 复诊认定已通过（异步任务完成）
            if (!revisitService.checkCompleted(orderId)) {
                return false;
            }

            return true;
        };
```

### 3.6 面试追问点

- **Q：为什么不用 TCC？**
  A：TCC 适合强一致短事务，但问诊结束触发的多下游（开方、上报、随访）是异步长流程，TCC 的 Try-Confirm-Cancel 模型不适用。事务消息更适合这种"主流程已结束，后续异步通知"的场景。

- **Q：事务消息的回查会不会一直 UNKNOWN？**
  A：不会。回查有最大次数限制（默认 15 次），超过后消息进入死信队列。我们监控死信队列，触发 P1 告警，人工介入。线上半年发生 2 次，均为数据库主从切换瞬间。

- **Q：幂等表会不会膨胀？**
  A：会。我们设计了 7 天 TTL，过期记录归档到 OSS。同时幂等表按月分表，避免单表过大。

- **Q：状态机选 Spring StateMachine 还是自研？**
  A：Spring StateMachine 适合中等复杂度（10 个状态以内），我们的场景（9 个状态、20+ 迁移）正好合适。如果状态超过 20 个，自研状态机更可控。

## 难点四：医师接诊调度与 SLA 保障

### 4.1 问题背景

医师接诊 SLA 是互联网医院的核心体验指标：图文问诊 P95 ≤ 30 min，超时则自动退款 + 影响医师评级。但医师资源稀缺，且不在线 7×24，调度难点在于：

- **号源管理**：医师排班时段精确到 30 min，号源有限
- **接诊时延**：从患者下单到医师首次回复的时延控制
- **超时重派**：医师超时未接诊时，自动转派给同科室其他医师
- **公平性**：避免某些医师"挑单"，避免某些患者被反复重派

### 4.2 技术挑战

1. **号源并发控制**：热门医师号源秒杀场景，防止超卖
2. **接诊时延监控**：实时检测超时未接诊订单
3. **重派策略**：避免重派风暴（同一订单被多次重派）
4. **医师画像**：基于接诊率、平均时延、患者评分做智能路由

### 4.3 方案选型对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 方案 A：FIFO 队列 | 简单公平 | 不考虑医师负载 | 不采用 |
| 方案 B：医师抢单 | 简单 | 冷启动慢、SLA 不可控 | 不采用 |
| **方案 C：调度引擎 + 抢单兜底** | 智能调度 + 兜底 | 实现复杂 | **采用** |
| 方案 D：纯智能路由 | 最优 | 误判影响大 | 部分采用 |

最终方案：**调度引擎优先派单 + 5 min 未接诊开放抢单 + 10 min 自动重派**。

### 4.4 核心实现

#### 4.4.1 号源并发控制（防超卖）

```java
// Redis + Lua 保证原子性
public class ScheduleService {

    private static final String LOCK_SCRIPT =
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del', KEYS[1]) " +
        "else " +
        "  return 0 " +
        "end";

    private static final String DECR_SCRIPT =
        "local current = redis.call('get', KEYS[1]) " +
        "if not current or tonumber(current) <= 0 then " +
        "  return 0 " +
        "end " +
        "redis.call('decr', KEYS[1]) " +
        "return 1";

    /**
     * 锁定号源（防超卖）
     */
    public boolean lockSlot(Long doctorId, String slotTime, Long orderId) {
        String key = "schedule:slot:" + doctorId + ":" + slotTime;
        String lockKey = "schedule:lock:" + doctorId + ":" + slotTime;

        // 1. 分布式锁（防止并发修改号源计数）
        String lockValue = UUID.randomUUID().toString();
        Boolean locked = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
        if (Boolean.FALSE.equals(locked)) {
            return false;
        }

        try {
            // 2. Lua 脚本原子扣减号源
            Long result = redisTemplate.execute(
                new DefaultRedisScript<>(DECR_SCRIPT, Long.class),
                Collections.singletonList(key)
            );
            return result != null && result == 1;
        } finally {
            // 3. 释放锁（Lua 校验 value）
            redisTemplate.execute(
                new DefaultRedisScript<>(LOCK_SCRIPT, Long.class),
                Collections.singletonList(lockKey),
                lockValue
            );
        }
    }
}
```

**优化**：单医师号源秒杀场景用 Redis Lua，整体性能 5000+ QPS。极端热门医师（如知名专家）号源预热到本地缓存，限流 100 QPS。

```java
public class SmartDispatchService {

    /**
     * 智能选择医师
     * 综合考虑：科室匹配、在线状态、当前负载、接诊率、平均时延、患者评分
     */
    public Long selectDoctor(ConsultOrder order) {
        // 1. 候选医师池：同科室 + 在线 + 当前负载 < 阈值
        List<DoctorProfile> candidates = doctorRepository.findCandidates(
            order.getDeptCode(),
            order.getHospitalId(),
            DispatchConstants.MAX_LOAD_PER_DOCTOR
        );

        if (candidates.isEmpty()) {
            // 兜底：跨医院同科室
            candidates = doctorRepository.findCrossHospitalCandidates(order.getDeptCode());
        }

        // 2. 综合评分
        return candidates.stream()
            .mapToDouble(doc -> calculateScore(doc, order))
            .max();
    }

    /**
     * 评分公式（加权）
     * - 接诊率（30%）：历史接诊率越高越优
     * - 平均时延（25%）：历史平均接诊时延越短越优
     * - 当前负载（20%）：当前未接诊订单数越少越优
     * - 患者评分（15%）：历史患者评分越高越优
     * - 既往关系（10%）：患者与医师既往问诊关系（提升连续性）
     */
    private double calculateScore(DoctorProfile doc, ConsultOrder order) {
        double acceptRate = doc.getAcceptRate();
        double avgLatency = 1.0 / (doc.getAvgAcceptLatencyMin() + 1);
        double loadScore = 1.0 - (double) doc.getCurrentLoad() / DispatchConstants.MAX_LOAD_PER_DOCTOR;
        double ratingScore = doc.getRating() / 5.0;
        double relationshipScore = hasPriorConsult(order.getPatientId(), doc.getId()) ? 1.0 : 0.5;

        return acceptRate * 0.30 + avgLatency * 0.25 + loadScore * 0.20
             + ratingScore * 0.15 + relationshipScore * 0.10;
    }
}
```

### 4.6 面试追问点

- **Q：为什么用延迟消息而不是定时任务？**
  A：定时任务扫描有延迟（最坏 1 min 才能发现超时），延迟消息精准到秒。且延迟消息天然分布式，避免定时任务的单点问题。

- **Q：号源秒杀场景为什么不用 ZK 分布式锁？**
  A：ZK 锁性能差（写入需半数节点确认），Redis Lua 性能高且足够。医疗号源场景冲突率低，Redis 完全够用。

- **Q：智能路由会不会误判？**
  A：会。所以我们用"调度优先 + 抢单兜底"，调度派单后医师 5 min 未接诊才开放抢单。极端情况（如某科室所有医师都不在线），调度派单失败，转人工客服介入。

- **Q：评分公式怎么调参？**
  A：基于历史数据离线训练，A/B 测试验证。我们用了 3 个月数据训练，最后定下 30/25/20/15/10 的权重。每月重新评估一次。

## 难点五：监管上报幂等与 24h 必达

### 5.1 问题背景

国家互联网诊疗监管中心要求：所有问诊记录、处方、医师执业信息、患者身份信息必须在 24h 内上报，否则吊销互联网医院资质。监管中心接口特点：

- 接口稳定性差：高峰期限流、偶发性 5xx
- 接口要求 `clientRequestNo` 幂等
- 上报数据格式严格（JSON Schema 校验）
- 上报失败需重试，但 24h 内必须成功

业务规模：日均 13w 上报，峰值 22w/s，年累计 4750w 条。

### 5.2 技术挑战

1. **24h 必达**：网络抖动、接口故障、限流等场景下必须保证 24h 内最终成功
2. **幂等性**：重试不能导致重复上报
3. **数据格式校验**：上报前必须校验，否则被监管中心拒绝
4. **批量上报**：单条上报效率低，需支持批量
5. **对账**：定期与监管中心拉取已收报文，发现遗漏立即补报

### 5.3 方案选型对比

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 方案 A：同步上报 | 简单 | 阻塞业务、接口故障影响大 | 不采用 |
| 方案 B：异步队列 + 重试 | 解耦 | 重试策略需精细设计 | **核心采用** |
| 方案 C：批量上报 | 高效 | 失败需重新批量重试 | 部分采用（处方） |
| 方案 D：本地消息表 | 强一致 | 性能瓶颈 | 关键场景采用 |

最终方案：**RocketMQ 异步队列 + 本地消息表（关键场景） + 指数退避重试 + 每日对账**。

### 5.4 核心实现

#### 5.4.1 上报流程

```
领域事件 -> RocketMQ -> Regulator服务
                          │
                          ├─ 1. 事件标准化（映射监管中心报文格式）
                          │     └─ JSON Schema 校验
                          │
                          ├─ 2. 幂等表校验（clientRequestNo）
                          │     └─ 已上报 -> 直接返回成功
                          │
                          ├─ 3. 写入"待上报"表（本地消息表）
                          │
                          ├─ 4. 调用监管中心接口
                          │     ├─ 成功 -> 更新状态为"已上报"
                          │     └─ 失败 -> 进入重试队列
                          │
                          ├─ 5. 重试策略（指数退避，覆盖 24h）
                          │     ├─ 1 min, 5 min, 15 min, 30 min, 1h, 2h, 4h, 8h
                          │     ├─ 8 次后改每 2h 一次
                          │     └─ 24h 仍未成功 -> P0 告警 + 人工介入
                          │
                          └─ 6. 每日 02:00 全量对账
                                ├─ 拉取监管中心已收报文（按日期）
                                ├─ 与本地上报记录比对
                                └─ 缺失项立即补报
```

#### 5.4.2 幂等设计

```java
@Service
public class RegulatorReportService {

    /**
     * 上报（幂等）
     */
    @Transactional
    public void report(RegulatorEvent event) {
        String clientRequestNo = generateClientRequestNo(event);

        // 1. 幂等表校验
        Optional<RegulatorRecord> existing = recordRepository
            .findByClientRequestNo(clientRequestNo);
        if (existing.isPresent() && existing.get().isSuccess()) {
            return;  // 已成功上报
        }

        // 2. 写入本地消息表（事务）
        RegulatorRecord record = new RegulatorRecord();
        record.setClientRequestNo(clientRequestNo);
        record.setEventType(event.getType());
        record.setPayload(JSON.toJSONString(event));
        record.setStatus(ReportStatus.PENDING);
        record.setRetryCount(0);
        record.setNextRetryTime(Instant.now());
        recordRepository.save(record);

        // 3. 异步调用监管中心
        asyncCallRegulator(record);
    }

    /**
     * clientRequestNo 生成规则
     * 格式：{eventType}_{eventId}_{yyyy-MM-dd}
     * 同一事件同一天的重试都用同一 clientRequestNo
     */
    private String generateClientRequestNo(RegulatorEvent event) {
        return event.getType().name() + "_" + event.getEventId() + "_"
             + LocalDate.now().format(DateTimeFormatter.ISO_DATE);
    }
}
```

**幂等三层保障**：
- **clientRequestNo**：监管中心接口要求，同一 clientRequestNo 重复上报返回相同结果
- **本地幂等表**：`(event_type, event_id)` 唯一索引，防止应用层重复处理
- **状态校验**：已成功的上报不重试

#### 5.4.3 重试策略

```java
public class RegulatorRetryScheduler {

    // 重试间隔（秒）：1, 5, 15, 30, 60, 120, 240, 480, 然后每 7200 一次
    private static final long[] RETRY_INTERVALS = {
        60, 300, 900, 1800, 3600, 7200, 14400, 28800
    };

    @Scheduled(cron = "0 * * * * ?")  // 每分钟扫描
    public void scanAndRetry() {
        List<RegulatorRecord> pending = recordRepository.findPending(Instant.now(), 1000);
        for (RegulatorRecord record : pending) {
            try {
                callRegulator(record);
                record.setStatus(SUCCESS);
                record.setReportTime(Instant.now());
            } catch (Exception e) {
                handleRetryFailure(record, e);
            }
        }
    }

    private void handleRetryFailure(RegulatorRecord record, Exception e) {
        int retryCount = record.getRetryCount();
        record.setLastError(e.getMessage());

        if (retryCount < RETRY_INTERVALS.length) {
            // 指数退避
            record.setNextRetryTime(Instant.now().plusSeconds(RETRY_INTERVALS[retryCount]));
            record.setRetryCount(retryCount + 1);
        } else {
            // 超过 8 次，改每 2h 一次
            record.setNextRetryTime(Instant.now().plusSeconds(7200));

            // 检查是否超过 24h
            if (Duration.between(record.getCreateTime(), Instant.now()).toHours() >= 24) {
                alertService.sendP0("监管上报 24h 未达: " + record.getClientRequestNo());
            }
        }

        recordRepository.save(record);
    }
}
```

#### 5.4.4 每日对账

```java
@Scheduled(cron = "0 0 2 * * ?")  // 每日 02:00
public void dailyReconcile() {
    LocalDate yesterday = LocalDate.now().minusDays(1);

    // 1. 拉取监管中心已收报文（按日期分页）
    List<String> remoteClientRequestNos = regulatorClient
        .fetchReceivedReports(yesterday);

    // 2. 拉取本地"应上报"记录
    List<RegulatorRecord> localRecords = recordRepository
        .findByCreateDate(yesterday);

    // 3. 比对：本地有但远程没有的，立即补报
    Set<String> remoteSet = new HashSet<>(remoteClientRequestNos);
    List<RegulatorRecord> missing = localRecords.stream()
        .filter(r -> !remoteSet.contains(r.getClientRequestNo()))
        .collect(Collectors.toList());

    log.info("对账结果: 应报 {}, 实报 {}, 缺失 {}", localRecords.size(),
             remoteClientRequestNos.size(), missing.size());

    for (RegulatorRecord record : missing) {
        // 立即补报（高优先级）
        record.setNextRetryTime(Instant.now());
        record.setPriority(9);  // 最高优先级
        recordRepository.save(record);
    }

    // 4. 缺失率 > 0.1% 触发告警
    double missingRate = (double) missing.size() / localRecords.size();
    if (missingRate > 0.001) {
        alertService.sendP1("监管上报缺失率超阈值: " + missingRate);
    }
}
```

#### 5.4.5 批量上报优化（处方场景）

```java
/**
 * 处方批量上报
 * 监管中心支持单次 100 条处方批量上报接口
 */
public class PrescriptionBatchReporter {

    @Scheduled(cron = "0 */5 * * * ?")  // 每 5 min
    public void batchReport() {
        // 1. 拉取待上报处方（最多 100 条）
        List<RegulatorRecord> pending = recordRepository
            .findPendingByType(EventType.PRESCRIPTION, 100);

        if (pending.isEmpty()) return;

        // 2. 组装批量报文
        BatchReportRequest request = new BatchReportRequest();
        request.setReports(pending.stream()
            .map(this::convertToReport)
            .collect(Collectors.toList()));

        // 3. 调用批量接口
        BatchReportResponse response = regulatorClient.batchReport(request);

        // 4. 处理结果（部分成功部分失败）
        for (BatchReportResult result : response.getResults()) {
            RegulatorRecord record = findRecord(pending, result.getClientRequestNo());
            if (result.isSuccess()) {
                record.setStatus(SUCCESS);
            } else {
                record.setLastError(result.getError());
                // 进入单条重试流程
                record.setNextRetryTime(Instant.now().plusSeconds(60));
            }
        }
    }
}
```

### 5.6 面试追问点

- **Q：监管中心接口故障 24h 怎么办？**
  A：第一，重试策略覆盖 24h（8 次指数退避 + 每 2h 兜底）。第二，每日对账发现缺失立即补报。第三，监管中心接口长时间故障（>4h）时，启用本地缓存队列，接口恢复后批量补报。第四，若 24h 仍未达，P0 告警 + 人工上报（电话/邮件向监管中心报备）。

- **Q：幂等表会无限增长吗？**
  A：不会。已成功上报的记录 7 天后归档到 OSS + Hive，仅保留近 30 天热数据。归档数据用于长期对账与审计。

- **Q：批量上报失败怎么处理？**
  A：批量接口返回每条记录的结果（部分成功部分失败），失败的进入单条重试流程。不会因为批量失败而全部重试。

- **Q：为什么 clientRequestNo 加日期？**
  A：监管中心要求 clientRequestNo 全局唯一，但我们的 eventId 跨天可能重复（极小概率），加日期确保唯一。同一天内同一事件的重试用同一 clientRequestNo，监管中心返回已收。

## 总结：5 个难点的共性方法论

| 难点 | 共性方法论 |
|------|-----------|
| IM 消息必达 | 多层保障（事务消息 + seq 补齐 + 重发补偿）+ 离线兜底 |
| 视频录制存档 | 分片 + 实时哈希 + 链上存证 + 调阅校验 |
| 订单状态机一致性 | 状态机 + 事务消息 + 幂等表 + 补偿任务 |
| 医师接诊调度 | 智能路由 + 多级超时（5/10/30 min）+ 公平性保障 |
| 监管上报 | 异步队列 + 指数退避 + 全量对账 + 批量优化 |

**架构师视角的共性**：
1. **分层防御**：任何单点都不足以保证可靠性，必须多层兜底
2. **幂等设计**：分布式系统下重复是常态，幂等是基础
3. **可观测**：所有关键链路必须有指标、日志、追踪
4. **可恢复**：异常不是 if 而是 when，设计时就要考虑恢复策略
5. **可对账**：关键业务必须有对账机制，发现遗漏立即补
