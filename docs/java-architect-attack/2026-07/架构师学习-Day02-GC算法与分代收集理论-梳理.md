## 一、架构师视角下的 GC 算法

### 1.1 不只是"面试题"，是"GC 调优的内功"

很多开发者把 GC 算法当成面试题来背：标记清除、复制、标记整理，三种算法的优缺点倒背如流。但架构师视角下，GC 算法是**调优决策的底层依据**：

- **为什么 Survivor 太小导致 Full GC 频繁？** -- 动态年龄规则触发过早晋升，Old 代膨胀
- **为什么 CMS 用着用着退化成 Serial Old？** -- 标记-清除碎片化 + Concurrent Mode Failure
- **为什么 G1 的 SATB 写屏障开销大但能预测停顿？** -- 快照语义让 Mixed GC 可控
- **为什么大对象直接进 Old 代？** -- 复制算法在大对象上开销不可控

理解算法本身只是起点，理解算法在**特定业务场景下的表现**才是架构师的核心能力。

### 1.2 三种基础算法的本质：处理"标记后怎么办"

GC 的核心是两步：**找出存活对象（标记）** + **回收死亡对象的内存（清理）**。三种算法的差异只在"清理"阶段：

| 算法 | 标记阶段 | 清理阶段 | 是否移动对象 |
|------|---------|---------|------------|
| 标记-清除 | 同 | 直接释放死亡对象的内存 | 否 |
| 复制 | 同 | 把存活对象复制到另一块区域，清空原区域 | 是（复制） |
| 标记-整理 | 同 | 把存活对象向一端移动，清理边界外 | 是（移动） |

**为什么不只用一种算法？** 因为每种算法都有致命缺陷：

- **标记-清除**：碎片化（无法分配大对象）
- **复制**：浪费一半内存（无法承受 Old 代 50% 浪费）
- **标记-整理**：移动开销大（无法承受新生代频繁整理）

**分代收集的精髓**：根据对象生命周期特征选择算法，扬长避短。

```
新生代（90% 对象朝生夕死）：
  - 存活少 -> 复制开销小
  - 频繁分配 -> 需要无碎片（指针碰撞）
  -> 选复制算法

老年代（存活率高）：
  - 存活多 -> 复制开销大
  - 偶尔分配 -> 容忍空闲列表
  -> 选标记-整理（无碎片）或标记-清除（低停顿）
```

### 1.3 分代假说与晋升规则的工程权衡

**分代假说**：绝大多数对象朝生夕死，熬过越多次 GC 越难回收。这是经验观察，不是定理。但基于这个假说，JVM 设计了一系列工程机制：

1. **Eden : Survivor = 8 : 1 : 1**：基于"新生代 90% 对象死亡"的假设，10% 的存活空间够用
2. **MaxTenuringThreshold = 15**：让对象在 Survivor 中熬 15 次 Minor GC，确认是"长期存活"才晋升
3. **动态年龄规则**：如果某年龄对象总和超过 Survivor 50%，年龄 >= 该年龄的对象全部晋升--避免 Survivor 溢出

**动态年龄规则是过早晋升的根因**：

```
假设 Survivor 100MB，对象创建速率 50MB/秒，Minor GC 间隔 1 秒

每次 Minor GC 存活 50MB（10% 存活率）
   - 年龄 1: 50MB
   - 年龄 1 + 年龄 2 = 100MB（达到 Survivor 50% 阈值）
   - 触发动态年龄规则：年龄 >= 2 的对象全部晋升

结果：对象只熬了 2 次 Minor GC 就晋升 Old 代
      Old 代快速膨胀，触发 Full GC
```

**架构师视角**：调优 SurvivorRatio 不是简单的"调大或调小"，要根据对象存活时间分布。如果业务对象存活 5-10 秒（如 IM 心跳、视频 RTP），Survivor 要够大让对象自然死亡，不能过早晋升。

### 1.4 跨代引用的本质：分代的代价

**分代收集的代价**就是跨代引用。如果只有新生代，就没有跨代引用问题。但分代带来的收益（Minor GC 只扫新生代）远大于代价，所以问题转化为"如何低成本处理跨代引用"。

**三种方案的精度-性能权衡**：

```
全堆扫描         |-------|-------|-------|  精度 100%，性能最差
Remembered Set   |---X---|---X---|---X---|  精度 100%，性能好，内存大
Card Table       |XXX----|----XXX|--X----|  精度粗（卡片级），性能好，内存小

Card Table 的设计哲学：
  - 用"卡片级精度"换"内存与性能"
  - 1 字节记录 512B（约 8-16 个对象）
  - 牺牲的精度 = 扫描卡片内所有对象的成本
  - 这是工程上"足够好"的权衡
```

**架构师视角**：Card Table 是"精度换性能"的经典案例。架构设计中类似权衡无处不在：

- **Sentinel 滑动窗口**：用 60 个 Bucket 记录 1 分钟数据，精度 1 秒（6月第4周）
- **ES 倒排索引的 Posting List**：用 Frame of Reference 压缩，精度换内存（6月第3周）
- **MySQL InnoDB 的 Change Buffer**：批量合并二级索引更新，延迟换吞吐（6月第1周）

### 1.5 写屏障与并发标记的"快照"思想

**并发标记的根本矛盾**：GC 标记对象图时，应用线程在改对象图。要么不允许改（STW，违背并发目标），要么记录改动（写屏障）。

**两种"记录改动"的思路**：

1. **增量更新**：记录"新增的引用"（post-write barrier）
   - 思路：黑色对象新增到白色引用时，黑色变灰，重新扫描
   - 缺点：重新扫描黑色对象的开销大

2. **SATB**：记录"删除的引用"（pre-write barrier）
   - 思路：拍快照时刻存活的，都标记为存活
   - 缺点：浮动垃圾（标记期间死亡的对象不回收）

**SATB 的"快照"思想**在分布式系统中也有体现：

- **MVCC**：数据库的快照隔离，读时看到的是某个时间点的一致性视图
- **Raft 日志复制**：Leader 的日志是"快照"，Follower 基于快照追赶（5月第3周）
- **ES Near Real-Time**：Segment 是某个时间点的快照，新数据在内存中等待刷新（6月第3周）

**架构师视角**：SATB 是"用内存换一致性"的设计--多标一些对象（浮动垃圾），换取标记阶段的并发性能。这种"容忍暂时不一致换性能"的设计在分布式系统中是常态。

### 1.6 Safepoint 与 Safe Region：JVM 与线程的协作机制

**Safepoint 的本质**：JVM 与应用线程的"协商点"--应用线程说"我现在状态确定，可以暂停"，JVM 说"好，我暂停你做 GC"。

**为什么不能强制暂停线程？** 因为线程执行中间状态不确定：
- 寄存器中的对象引用可能没写回栈
- 即将执行的字节码可能涉及对象分配
- TLAB 中的对象可能没初始化完成

**轮询机制的实现**：

```
JIT 编译后的代码：
  ... 业务代码 ...
  test [polling_page] 0  // 单字节轮询指令
  ... 业务代码 ...
  
GC 触发时：
  1. JVM 把 polling_page 标记为"不可读"
  2. 线程执行 test 指令时触发 SegFault
  3. JVM 信号处理器捕获，把线程阻塞在 Safepoint

为什么用轮询而不是中断：
  - 中断代价高（CPU 上下文切换）
  - 轮询代价低（1 个时钟周期的 test 指令）
  - 频率可控（JIT 在合适位置插入）
```

**Counted Loop 陷阱**：

```java
// int 计数循环，JIT 不插入轮询
for (int i = 0; i < Integer.MAX_VALUE; i++) {
    sum += i;
}
// GC 触发时，这个循环会卡住所有线程，STW 时间可能数秒

// long 计数循环，JIT 会插入轮询
for (long i = 0; i < Integer.MAX_VALUE; i++) {
    sum += i;
}
```

**为什么 int 循环不插入轮询**：JIT 认为 int 循环次数有限（&lt; 2^31），不需要轮询。但如果循环体内有方法调用或对象分配，本身就会触发 Safepoint 检查。空循环 + int 计数才是陷阱。

**Safe Region 是 Safepoint 的扩展**：

```
线程状态               能到 Safepoint?    解决方案
--------------------------------------------------
执行 Java 字节码       能                 轮询点
执行 JIT 编译代码      能                 轮询点
执行 Native (JNI)      不能               Safe Region
Sleep / Wait / Blocked 不能               Safe Region
分配 TLAB              能                 分配前轮询
```

**架构师视角**：Safepoint 是 JVM 的"全局暂停原语"。理解 Safepoint 的工程实现，能解释很多生产问题：

- **服务延迟毛刺**：可能是 Safepoint 等待时间长（Counted Loop 陷阱）
- **GC 时间长但堆不大**：可能是 Safepoint 同步时间长
- **JNI 性能差**：可能是 Safe Region 切换开销

## 二、GC 算法与在线问诊系统的结合点

### 2.1 在线问诊系统的 GC 重灾区画像

| 场景 | 对象特征 | GC 影响 | 关键算法 |
|------|---------|---------|---------|
| IM 心跳包 | 高频小对象，存活 &lt; 1 秒 | Eden 快速填满，Minor GC 频繁 | 复制算法 |
| IM 长连接 | Channel + Pipeline + ByteBuf，长期存活 | 直接内存为主，堆内 Old 代 | 跨代引用处理 |
| 视频问诊 RTP 包 | 高频小对象，被 Session 引用 | 跨代引用频繁，Card Table 开销 | 跨代引用处理 |
| 视频问诊 Session | 长生命周期，引用大量短生命周期对象 | Old 代对象，触发跨代扫描 | 跨代引用处理 |
| 问诊订单缓存 | 100w 对象 × 1KB，TTL 30 分钟 | Old 代占用 1GB，碎片化 | 标记-整理 |
| MongoDB 大文档读取 | 5-10MB 临时对象 | Humongous Region | G1 大对象处理 |
| 问诊日志事件 | 高频小对象，异步落库 | 异步队列堆积，Old 代 | 复制 + 标记-整理 |

### 2.2 容量规划方法论

**Step 1：估算对象创建速率**

```
IM 网关：
- 日均 5.2w 订单，假设每订单 10 条消息，共 52w 消息
- 日均 12w 长连接，每连接每 30 秒 1 次心跳 -> 12w × 2880 = 3.5 亿次心跳/日
- 峰值 5w 心跳/秒
- 每心跳 5 个对象 × 350B = 17.5MB/秒

视频问诊：
- 峰值 5800 路并发
- 每路 750 包/秒 × 64B = 48KB/秒
- 总计 5800 × 48KB = 278MB/秒

问诊订单缓存：
- 100w 订单 × 1KB = 1GB（Old 代）

MongoDB 大文档：
- 假设每秒 10 次大文档读取，每次 5MB
- 临时对象分配 50MB/秒
```

**Step 2：规划新生代大小**

```
新生代大小 = 每秒对象创建速率 × 期望 Minor GC 间隔 / 0.8（Eden 占比）

IM 网关：
- 期望 Minor GC 间隔 60 秒
- 新生代 = 17.5MB × 60 / 0.8 = 1.3GB
- 实际配置：-Xmn2g（留余量）

视频问诊 SFU：
- 期望 Minor GC 间隔 10 秒（视频实时性要求高）
- 新生代 = 278MB × 10 / 0.8 = 3.5GB
- 实际配置：-Xmn4g
```

**Step 3：规划老年代大小**

```
老年代 = 长期存活对象 + 本地缓存 + 预留空间

IM 网关：
- 长连接对象：12w × 7KB = 840MB
- 业务缓存：500MB
- 预留 30%：~600MB
- 老年代总大小：2GB
- 实际堆大小：新生代 2GB + 老年代 2GB = 4GB

视频问诊 SFU：
- Session 对象：5800 × 10KB = 58MB
- 视频缓冲：5800 × 100KB = 580MB
- 预留 30%：~200MB
- 老年代总大小：1GB
- 实际堆大小：新生代 4GB + 老年代 1GB = 5GB
- 但 SFU 通常配 16GB 堆，留余量给突发流量
```

**Step 4：选择 GC 收集器**

| 场景 | 推荐收集器 | 原因 |
|------|----------|------|
| IM 网关 | G1 | 低停顿（100ms 目标），无碎片 |
| 视频问诊 SFU | G1 / ZGC | 极低停顿（20ms 目标） |
| 业务服务（订单） | G1 | 均衡，可预测停顿 |
| MongoDB 大文档服务 | G1 | Humongous Region 处理 |
| 内部管理后台 | Parallel | 吞吐优先，停顿不敏感 |

## 三、与往周专题的呼应

### 3.1 GC 标记-清除 vs MySQL InnoDB 脏页刷新（6月第1周）

**相似点**：都是"找出脏数据 + 清理"。

**差异点**：
| 维度 | InnoDB 脏页刷新 | GC 标记-清除 |
|------|---------------|-------------|
| 触发时机 | Buffer Pool 满 / LSN 阈值 | Eden / Old 代满 |
| 范围 | 单页级别 | 整堆或分代 |
| 是否阻塞 | 否（异步刷新） | 是（STW，CMS 除外） |
| 内存整理 | 原地更新 | 标记-清除不整理，标记-整理会移动 |

**架构师视角**：InnoDB 是"原地更新"，因为磁盘随机 IO 慢，移动数据代价大。JVM 是"移动对象"，因为内存移动代价小（指针更新），但收益大（无碎片）。

### 3.2 GC 分代假说 vs Redis 惰性删除（6月第2周）

**相似点**：都是"利用对象生命周期特征做优化"。

**差异点**：
| 维度 | Redis 惰性删除 | GC 分代假说 |
|------|--------------|------------|
| 假设 | 大部分 key 不会被访问 | 大部分对象朝生夕死 |
| 实现 | 访问时检查 TTL | 分代 + 不同算法 |
| 回收时机 | 被访问时 | 主动触发（GC） |
| 主动性 | 被动 + 定期删除 | 主动（GC 线程） |

**架构师视角**：两者都是"经验驱动"的设计--基于观察到的对象生命周期分布，选择最合适的回收策略。

### 3.3 GC Mark-Compact vs ES Lucene Segment Merge（6月第3周）

**相似点**：都是"碎片整理"。

**差异点**：
| 维度 | ES Segment Merge | GC Mark-Compact |
|------|-----------------|-----------------|
| 触发时机 | Segment 数量阈值 | GC 时 |
| 整理对象 | Segment（文件） | Java 对象（内存） |
| 是否阻塞 | 后台线程，不阻塞查询 | STW（G1 Region 间复制减低阻塞） |
| 整理后 | 多个 Segment 合并为一个 | 对象向一端移动 |

**架构师视角**：两者都是"用整理开销换后续访问性能"。ES 用后台线程避免阻塞，JVM 用 G1 Region 模型减少 STW。

### 3.4 GC Card Table vs Sentinel 滑动窗口（6月第4周）

**相似点**：都是"用粗粒度数据结构降低精度换性能"。

**差异点**：
| 维度 | Sentinel 滑动窗口 | GC Card Table |
|------|-----------------|--------------|
| 数据结构 | Bucket 数组 | Card 字节数组 |
| 粒度 | 1 秒 | 512 字节 |
| 写入 | 每请求写入对应 Bucket | 每次引用写入标脏对应 Card |
| 读取 | 滑动窗口聚合 | Minor GC 时扫描脏 Card |

**架构师视角**：两者都是"批量处理"的思想--用粗粒度数据结构降低单次操作开销，代价是精度损失。

### 3.5 JVM 分代隔离 vs K8s Pod 反亲和（7月第3周）

**相似点**：都是"按生命周期/特征分离以减少干扰"。

**差异点**：
| 维度 | K8s Pod 反亲和 | JVM 分代隔离 |
|------|--------------|-------------|
| 分离维度 | 节点级别 | 堆内区域 |
| 依据 | 业务重要性 / 资源需求 | 对象生命周期 |
| 目标 | 故障隔离 / 资源隔离 | 算法选择优化 |

**架构师视角**：两者都是"分类治理"--根据对象特征选择不同的处理策略，避免"一刀切"的低效。

## 四、能力差距与补足方向

### 差距 1：分代假说与晋升规则的工程理解不深
> Day2发现

- **现状**：知道新生代用复制、老年代用标记整理，但动态年龄规则、过早晋升、Survivor 大小调优等工程细节模糊
- **架构师水平**：能根据对象创建速率、存活时间精确规划新生代大小、SurvivorRatio、MaxTenuringThreshold；能用 `-XX:+PrintAdaptiveSizePolicy` 验证 JVM 的动态调整
- **补足方向**：精读《深入理解 Java 虚拟机》第 3 章分代收集；用 JMH 实测不同 SurvivorRatio 下的晋升速率；阅读 HotSpot `ageTable.cpp` 源码

### 差距 2：Card Table 与 Remembered Set 的精度权衡不熟
> Day2发现

- **现状**：知道 Card Table 是 512B 卡片，但精度选择、多精度 Card Table、G1 的 Region 级 RS 设计不深
- **架构师水平**：能讲清 Card Table 的 3 种精度、G1 的 RS 哈希表实现、为什么 G1 不用全堆 Card Table
- **补足方向**：阅读 HotSpot `cardTableRS.cpp`、`g1RemSet.cpp` 源码；对比 CMS 全堆 Card Table 与 G1 Region 级 RS 的实测开销

### 差距 3：写屏障的两种实现细节不清
> Day2发现

- **现状**：知道 CMS 用增量更新、G1 用 SATB，但 pre-write barrier 与 post-write barrier 的具体执行流程、SATB 队列处理时机不深
- **架构师水平**：能讲清 SATB 写屏障的代码级实现、SATB 队列在 Remark 阶段的处理、为什么 SATB 不能用于移动对象
- **补足方向**：阅读 G1 论文《Garbage-First Garbage Collection》；阅读 OpenJDK `g1SATBCardTableModRefBS.cpp`；Day07 深挖 G1 时深入

### 差距 4：Safepoint 的实现机制与陷阱不熟

## 五、Day02 核心架构师命题

### 命题 1：为什么 G1 用 SATB 而不用增量更新？

**核心答案**：SATB 让 G1 的 Mixed GC 可预测停顿。

**详细推理**：
1. G1 的核心目标是"可预测停顿"（MaxGCPauseMillis）
2. 可预测停顿要求 GC 回收的 Region 集合可控
3. Region 集合选择依赖于"标记准确"--要知道每个 Region 的存活对象大小
4. 增量更新（CMS）的重新标记要扫描所有标脏黑色对象，开销不可控
5. SATB 拍快照后，标记结果与开始时刻一致，可以准确计算 Region 存活对象
6. 所以 G1 选 SATB，承担浮动垃圾的代价，换取 Mixed GC 的可控性

**架构师视角**：这是"准确性 vs 性能"的权衡。SATB 写屏障开销大（10-20%），但带来可预测停顿。CMS 追求极致低停顿，写屏障要轻，所以选增量更新。

### 命题 2：为什么 Survivor 太小会导致 Full GC 频繁？

**核心答案**：动态年龄规则触发过早晋升，Old 代快速膨胀。

**详细推理**：
1. Survivor 小，放不下多个 Minor GC 的存活对象
2. JVM 检测到 Survivor 中年龄 N 的对象总和超过 50%
3. 触发动态年龄规则：年龄 >= N 的对象全部晋升
4. 大量"本应再存活几秒"的对象被晋升到 Old 代
5. Old 代快速膨胀
6. Old 代占用率达到 IHOP 阈值（默认 45%），触发并发标记
7. Mixed GC 来不及回收，Old 代继续涨
8. 最终触发 Full GC

**架构师视角**：SurvivorRatio 不是"越大越好"或"越小越好"，要根据对象存活时间分布。IM 心跳对象存活 &lt; 1 秒，Survivor 要够大让对象在 1 个 Minor GC 间隔内死亡。

### 命题 3：为什么 CMS 会"Concurrent Mode Failure"？

**核心答案**：Old 代碎片化 + 晋升速率过快，并发收集跟不上。

**详细推理**：
1. CMS 用标记-清除，不整理，产生碎片
2. 碎片导致大对象分配失败（无连续空间）
3. 晋升对象无法放入 Old 代，触发 Concurrent Mode Failure
4. CMS 退化为 Serial Old 单线程 Full GC，整理全堆
5. STW 时间可达数秒

**架构师视角**：CMS 的设计有内在矛盾--追求低停顿用标记-清除，但碎片化最终导致长 STW。G1 用 Region 间复制解决这个矛盾。

### 命题 4：为什么大对象直接进 Old 代（或 Humongous Region）？

**核心答案**：复制算法在大对象上开销不可控。

**详细推理**：
1. 新生代用复制算法
2. 大对象（如 5MB）在新生代复制开销大（5MB 内存拷贝）
3. 大对象还可能放不进 Eden（Eden 通常 1GB 以内），触发提前 GC
4. 直接进 Old 代（或 G1 的 Humongous Region），避免复制
5. Old 代用标记-整理，大对象不频繁移动

**架构师视角**：大对象是 GC 的"特殊公民"。代码中应避免大对象创建（如大数组、大 JSON 字符串），改用流式处理。

### 命题 5：为什么 Safepoint 不能完全取消？

**核心答案**：对象移动仍需 Safepoint（或读屏障）。

**详细推理**：
1. JDK 12 引入并发栈扫描（JEP 376），GC 扫描栈无需 Safepoint
2. 但 GC 移动对象时，所有指向该对象的引用都要更新
3. 如果线程正在用对象引用（已加载到寄存器），更新会出错
4. 所以对象移动仍需 Safepoint
5. ZGC 用读屏障替代部分 Safepoint，但实现复杂，JDK 15 才稳定

**架构师视角**：Safepoint 是 JVM 的"全局一致性原语"。完全取消 Safepoint 需要"无锁并发对象移动"，ZGC / Shenandoah 通过读屏障实现，是 GC 的下一代设计。

## 六、Day03 预告：GC 收集器全谱系

Day02 讲了 GC 算法与分代收集理论，是"算法层面"。Day03 进入"工程层面"--具体的 GC 收集器：

- **Serial / Serial Old**：单线程，最简单，Client 模式默认
- **ParNew / Parallel Scavenge / Parallel Old**：多线程并行，吞吐优先
- **CMS**：并发收集，低停顿，但有碎片化问题
- **G1**：Region 模型，可预测停顿，JDK 9+ 默认
- **ZGC**：染色指针 + 读屏障，&lt; 10ms 停顿，JDK 15+ 生产可用
- **Shenandoah**：并发整理，Brooks 转发指针，RedHat 主导

Day03 会对比 7 种收集器的设计哲学、适用场景、调优参数，并在 Day07 深挖 G1 底层（Region 模型、SATB、Mixed GC）。

第 2 周进入调优实战与生产排查：
- Day01：JVM 调优参数全解
- Day02：监控诊断工具链
- Day03：OOM 与内存泄漏排查
- Day04：CPU 飙高与 Full GC 频繁排查
- Day05：在线问诊系统 JVM 实战
- Day06：串联 - 一次完整的 JVM 故障复盘
- Day07：架构深挖 - ZGC 与 Shenandoah

Day02 的核心收获：**GC 算法是调优的内功，分代假说是经验驱动的工程权衡，写屏障与并发标记是 GC 设计的精髓。**
