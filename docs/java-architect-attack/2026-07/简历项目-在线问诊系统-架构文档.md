## 一、项目背景与业务规模

### 1.1 项目定位

该系统是某互联网医院平台的**在线问诊核心交易子系统**，承担"患者-医师-药师"三方在线诊疗交易闭环。平台为**第三方平台型互联网医院**，依托 30+ 家合作实体医院执业，覆盖内、外、妇、儿、慢病管理等 12 个临床科室。

在线问诊子系统向上承接患者端（APP / H5 / 微信小程序）与医师端（PC 工作台 / PAD）的问诊请求，向下对接电子处方、药品配送、医保结算、监管上报等下游系统，是平台日均交易量最大、SLA 要求最严的子系统。

### 1.3 关键 SLA

- **医师接诊时延**：图文问诊 P95 ≤ 30 min，P99 ≤ 60 min；视频问诊准时呼叫率 ≥ 98%（预约时间 ±5 min）
- **问诊订单可用性**：核心交易链路 99.95%
- **IM 消息必达**：端到端投递成功率 99.99%，丢失补偿时延 ≤ 5 min
- **监管上报**：24 h 内必达，幂等率 100%
- **视频问诊录制存档**：录制完整性 100%，文件 SHA256 上链，保存 ≥ 15 年

### 2.2 模块职责边界

**问诊订单 Consult**：问诊订单全生命周期管理（创建、支付、排队、接诊、沟通、结束、退款）；状态机驱动；幂等控制；订单与诊疗事件的拆分。

**医患 IM**：图文问诊消息的可靠投递（必达、有序、幂等）；消息存档；撤回消息保留合规副本；敏感词过滤；患者图片 OCR 脱敏。

**视频问诊 Video**：视频问诊的预约、信令协商（WebRTC SDP/ICE）、媒体流转发（SFU）、录制存档、合规审计。

**医师排班 Schedule**：医师出诊排班、号源管理、接诊调度、超时重派、SLA 监控。

**处方开具 Rx**：处方开立、医师电子签章、处方号生成、与处方审核/配送/医保的异步衔接。

**复诊认定 Revisit**：调阅合作医院 HIS / 区域卫生信息平台，判断 6 个月内是否有该科室线下就诊记录。

**医师资质 Credential**：医师执业注册信息核验、多点执业管理、CA 证书管理、处方权限校验。

**监管上报 Regulator**：问诊记录、处方、医师执业信息、患者身份信息上报国家互联网诊疗监管中心；24 h 内必达；幂等。

### 2.3 核心设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 服务框架 | Spring Cloud Alibaba | 公司技术栈统一，Nacos/Sentinel 与 K8s 兼容性好 |
| RPC | Dubbo 3.x（Triple 协议） | 相比 Feign 性能更好，Triple 协议兼容 gRPC，方便对接异构客户端 |
| 消息中间件 | RocketMQ 5.x | 事务消息解决订单与消息的一致性；医疗场景对消息可靠性要求极高 |
| 数据库 | MySQL 8.0 + ShardingSphere | 问诊订单按 patientId 分库分表（64 库 × 16 表 = 1024 表） |
| 缓存 | Redis 7.x Cluster | 热点医师号源、问诊状态、IM 在线状态 |
| IM 长连接 | Netty 4.x + WebSocket | 单机长连接 10w+，与业务层解耦 |
| 视频媒体 | 自研 SFU + WebRTC | 商用 SFU（声网/即构）成本高，自研可控且合规 |
| 文档库 | MongoDB | IM 消息、诊疗事件，写入密集 + schema 灵活 |
| 检索 | ElasticSearch 8.x | IM 消息全文检索、诊疗事件检索、医师检索 |
| 对象存储 | MinIO（私有化）+ OSS（备份） | 患者图片、视频录制、电子签名文件 |
| Service Mesh | Istio 1.20 | mTLS 满足等保三级；流量治理支持蓝绿/金丝雀 |
| 容器编排 | K8s 1.28 + Argo CD | 多可用区部署，HPA 自动伸缩 |

## 三、核心数据模型

### 3.1 问诊订单 ConsultOrder（交易契约）

```sql
CREATE TABLE `consult_order` (
  `order_id`          bigint       NOT NULL COMMENT '订单ID（雪花算法）',
  `patient_id`        bigint       NOT NULL COMMENT '患者ID',
  `doctor_id`         bigint       NOT NULL COMMENT '医师ID',
  `hospital_id`       bigint       NOT NULL COMMENT '执业挂靠实体医院ID',
  `dept_code`         varchar(32)  NOT NULL COMMENT '科室代码',
  `consult_type`      tinyint      NOT NULL COMMENT '1图文 2电话 3视频',
  `status`            tinyint      NOT NULL COMMENT '0待支付 1待接诊 2问诊中 3已结束 4已退款',
  `sub_status`        tinyint      NOT NULL DEFAULT 0 COMMENT '子状态：视频问诊预约/呼叫状态',
  `amount`            decimal(10,2) NOT NULL COMMENT '订单金额',
  `pay_time`          datetime     DEFAULT NULL COMMENT '支付时间',
  `accept_time`       datetime     DEFAULT NULL COMMENT '接诊时间',
  `end_time`          datetime     DEFAULT NULL COMMENT '结束时间',
  `im_session_id`     varchar(64)  DEFAULT NULL COMMENT 'IM会话ID',
  `video_room_id`     varchar(64)  DEFAULT NULL COMMENT '视频房间ID',
  `revisit_token`     varchar(64)  DEFAULT NULL COMMENT '复诊认定凭证',
  `refund_status`     tinyint      NOT NULL DEFAULT 0 COMMENT '0无退款 1待退款 2已退款',
  `risk_level`        tinyint      NOT NULL DEFAULT 0 COMMENT '风险等级（用于路由）',
  `version`           int          NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
  `create_time`       datetime     NOT NULL,
  `update_time`       datetime     NOT NULL,
  PRIMARY KEY (`order_id`),
  UNIQUE KEY `uk_patient_doctor_type_status` (`patient_id`,`doctor_id`,`consult_type`,`status`),
  KEY `idx_doctor_status` (`doctor_id`,`status`),
  KEY `idx_hospital_status` (`hospital_id`,`status`,`create_time`)
) ENGINE=InnoDB COMMENT='问诊订单表';
```

**分库分表策略**：按 `patient_id % 1024` 路由到 1024 张物理表（64 库 × 16 表），患者维度查询走分片键；医师维度查询走 `idx_doctor_status` 广播索引 + 异步 ES 同步。

```sql
  ],
  "prescriptions": ["rx_xxx1", "rx_xxx2"],
  "doctorSign": {
    "signature": "BASE64...",
    "caCertId": "ca_xxx",
    "signTime": "2025-12-01T10:30:00Z"
  },
  "attachments": ["img_xxx", "video_record_xxx"],
  "eventTime": "2025-12-01T10:00:00Z",
  "archiveStatus": "ARCHIVED"

```

**订单与诊疗事件拆分的核心理由**：

1. **关注点分离**：订单管交易（金额/状态/退款），诊疗事件管临床（主诉/诊断/处方）。
2. **保存期限不同**：订单 5 年（电商交易存档要求），诊疗事件 ≥ 15 年（医疗病历保存期限）。
3. **数据归属不同**：订单归平台，诊疗事件归执业挂靠的实体医院 EMR。
4. **隐私等级不同**：订单可对账务/运营可见，诊疗事件仅医/药/患者本人可见。
5. **一对多关系**：一次问诊可能产生多个事件（接诊、修改诊断、补开处方），订单只有一个。

### 3.5 状态机：问诊订单生命周期

```
                  ┌────────────────────────────────────────────────┐
                  ▼                                                │
   ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐    │
   │ 待支付 │→│ 待接诊 │→│ 问诊中 │→│ 待结束 │→│ 已结束 │    │
   │ UNPAID │  │ PENDING│  │INPROG  │  │ENDING  │  │ CLOSED │    │
   └────────┘  └────────┘  └────────┘  └────────┘  └────────┘    │
        │           │            │                          │      │
        │           │            │ 异常                     │      │
        │           ▼            ▼                          ▼      │
        │      ┌────────┐  ┌────────┐                ┌────────┐  │
        │      │ 已退款 │  │ 异常中 │                │ 已退款 │  │
        │      │REFUNDED│  │ERROR   │                │REFUNDED│  │
        │      └────────┘  └────────┘                └────────┘  │
        │                      │                                   │
        │                      └─ 运维介入 ──────────────────────┘
        ▼
   ┌────────┐
   │ 已取消 │
   │CANCEL  │
   └────────┘
```

**状态机实现**：基于 Spring StateMachine + 持久化状态机上下文；每个状态迁移都伴随领域事件发布到 RocketMQ；下游服务订阅事件做异步处理。

**关键约束**：
- 只有 `UNPAID → PENDING` 必须同步（支付回调驱动）
- `PENDING → INPROGRESS` 由医师接诊动作触发，需校验号源、复诊认定、医师资质
- `INPROGRESS → CLOSED` 由医师"结束问诊"动作触发，需校验所有未读消息已读、诊疗事件已补全
- 异常状态 `ERROR` 由补偿任务驱动恢复，不允许业务直接迁移

## 四、核心业务链路

### 4.1 图文问诊创建链路（同步，RT &lt; 800ms）

```
患者端 → API网关 → Consult服务
                      │
                      ├─ 1. 校验患者身份与黑名单
                      ├─ 2. 校验医师资质（Credential服务，本地缓存 + 异步刷新）
                      ├─ 3. 复诊认定（Revisit服务，调HIS/区域平台，超时降级到患者自述）
                      ├─ 4. 锁定号源（Schedule服务，Redis分布式锁）
                      ├─ 5. 创建订单（MySQL，事务）
                      ├─ 6. 发起支付（Pay服务，事务消息保证订单-支付一致性）
                      └─ 7. 返回订单号（支付完成后再拉起IM会话）
                            
支付成功回调 → Consult服务
                │
                ├─ 8. 订单状态 UNPAID → PENDING
                ├─ 9. 发送 RocketMQ 事件 OrderPaid
                │     ├─ IM服务订阅 → 创建会话、推送患者首条消息
                │     ├─ Schedule服务订阅 → 占用号源
                │     └─ Regulator服务订阅 → 预上报（订单创建事件）
                └─ 10. 返回成功
```

**关键设计**：
- 步骤 1-7 同步链路 RT 控制在 800ms 内，超时降级（如复诊认定超时走患者自述，后台异步补全）
- 步骤 8-10 通过 RocketMQ 事务消息保证订单状态与下游事件最终一致
- 复诊认定走"先同步校验，失败异步补全"策略，避免 HIS 接口抖动影响下单

### 4.2 医师接诊与 IM 沟通链路（半同步 + 异步）

```
医师端 → API网关 → Consult服务
                    │
                    ├─ 1. 校验医师身份与排班
                    ├─ 2. 状态机迁移 PENDING → INPROGRESS（乐观锁）
                    ├─ 3. 发布事件 DoctorAccepted
                    │     ├─ IM服务 → 会话激活，推送"医师已接诊"系统消息
                    │     ├─ Regulator服务 → 上报接诊事件
                    │     └─ Schedule服务 → 释放号源占用，记录接诊时延
                    └─ 4. 返回医师端 IM 会话凭证

医师/患者发送消息 → IM长连接网关 → IM服务
                                  │
                                  ├─ 5. 生成会话内 seq（Redis INCR）
                                  ├─ 6. 持久化到 MongoDB
                                  ├─ 7. 敏感词机审（异步，不阻塞投递）
                                  ├─ 8. 推送给对端（在线走长连接，离线走推送）
                                  ├─ 9. 端到端加密（信封加密 + KMS）
                                  └─ 10. 客户端ACK → 更新deliveredTime
                                       └─ 若30s未ACK → 走离线推送 + 重发补偿
```

**消息必达三层保障**：
1. **客户端 seq 补齐**：客户端重连后按本地最大 seq 拉取服务端缺失消息
2. **服务端重发补偿**：30s 未 ACK 的消息进入重发队列，指数退避重试 3 次
3. **离线推送兜底**：重试失败走 APNs/FCM/小米/华为推送通道

### 4.3 视频问诊信令链路

```
预约时间到达 → Schedule服务 → 推送"呼叫提醒"给医患双端
                                  │
                                  ▼
患者端发起呼叫 → 视频信令网关 → Video服务
                                  │
                                  ├─ 1. 校验预约时间（±5 min 容忍）
                                  ├─ 2. 分配 SFU 节点（按地域 + 负载）
                                  ├─ 3. 创建房间，生成 roomId
                                  ├─ 4. 信令交换（offer/answer/candidate）
                                  │     ├─ 患者端 SDP offer → 转发医师端
                                  │     ├─ 医师端 SDP answer → 转发患者端
                                  │     └─ ICE candidate 双向交换
                                  ├─ 5. TURN 服务器分配（仅当 P2P 失败）
                                  ├─ 6. 通话开始，启动录制
                                  │     ├─ 录制流 → SFU 混流 → MinIO
                                  │     ├─ 录制元数据 → MySQL
                                  │     └─ 录制 SHA256 → 区块链存证
                                  └─ 7. 通话结束
                                        ├─ 计费（按时长）
                                        ├─ 触发诊疗事件补录
                                        └─ 监管上报
```

**WebRTC 在医疗场景的工程化要点**：
- **ICE 重协商**：医师多端切换（PC → PAD → 手机）时，需保持 roomId 不变，重新协商 ICE
- **TURN 中继部署**：医院内网 / 4G / 家庭 Wi-Fi 三场景，P2P 失败率约 30%，必须部署 TURN 中继
- **录制完整性**：录制流分片（每 30s 一片），SHA256 实时计算，结束时合并并上链存证
- **密钥管理**：录制文件用 KMS 托管的 DEK 加密，DEK 用 KEK 包装，KEK 由 HSM 保护

### 4.4 监管上报链路（异步，24h 内必达）

```
领域事件（订单创建/接诊/结束/处方开具）→ RocketMQ → Regulator服务
                                                      │
                                                      ├─ 1. 事件标准化（映射监管中心报文格式）
                                                      ├─ 2. 幂等表校验（事件ID + 上报类型）
                                                      ├─ 3. 调用监管中心接口（HTTPS + 国密SM2签名）
                                                      ├─ 4. 失败重试（指数退避，最多 8 次，覆盖 24h）
                                                      ├─ 5. 重试仍失败 → 落"待人工处理"表
                                                      └─ 6. 每日对账：拉取监管中心已收报文，与本地上报记录比对
```

**幂等设计**：上报记录表 `(event_id, report_type)` 唯一索引，监管中心接口要求带 `clientRequestNo`，重复上报返回相同结果。

**24h 必达保障**：
- 正常重试 8 次（1min、5min、15min、30min、1h、2h、4h、8h）
- 超过 8 次进入"待人工处理"，但**不停止重试**，改为每 2h 一次
- 每日 02:00 跑全量对账任务，发现未上报事件立即补报
- 监控告警：单日失败率 > 0.1% 触发 P1 告警

- **熔断限流**：Sentinel 配置核心接口 QPS 限流（如下单接口单实例 800 QPS），超过限流走排队
