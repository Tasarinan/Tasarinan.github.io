## 一、架构师视角下的 GC 收集器

### 1.1 不只是"选择题"，是"业务场景与 GC 设计哲学的匹配"

很多开发者把 GC 收集器当成"选择题"：G1 还是 ZGC？看个对比表就行。但架构师视角下，GC 选型是**业务场景与 GC 设计哲学的匹配**：

- **吞吐优先业务**（批处理、ETL）选 Parallel -- 因为 GC 设计目标是最大化业务时间占比
- **延迟敏感业务**（IM、视频）选 G1 / ZGC -- 因为 GC 设计目标是可预测停顿
- **大堆业务**（> 32GB）选 ZGC -- 因为 ZGC 停顿与堆大小无关
- **容器化业务**选 G1 -- 因为 G1 适配 cgroup 限制

理解每种 GC 的**设计哲学**，比记参数更重要。

### 1.2 GC 演进的 25 年：从单线程到并发

```
1999 (JDK 1.3)   Serial          单线程，Client 模式
2002 (JDK 1.4)   Parallel        多线程并行，吞吐优先
2004 (JDK 1.5)   CMS             并发标记，低停顿
2012 (JDK 1.7)   G1              Region 模型，可预测停顿
2018 (JDK 11)    ZGC             染色指针 + 读屏障，< 10ms 停顿
2019 (JDK 12)    Shenandoah      Brooks 转发指针，并发整理
2021 (JDK 17)    ZGC 生产可用     移除 Experimental
2023 (JDK 21)    分代 ZGC        重大改进，吞吐提升 20%+
```

**演进的核心主线**：从"STW 全程"到"并发全程"。

```
Serial         |████████████████|  全程 STW
Parallel       |████████░░░░░░░░|  并行 STW，时间缩短
CMS            |██░░░░░░░░░░░░░|  STW 短，并发标记 / 清除
G1             |██░░░░░░░░░░░░░|  STW 短，并发标记，Region 选择
ZGC            |█░░░░░░░░░░░░░░|  STW 极短，并发整理
Shenandoah     |█░░░░░░░░░░░░░░|  STW 极短，并发整理
```

**架构师视角**：GC 演进的每一步都是"工程权衡"--用更复杂的设计换更短的 STW。Serial 简单但停顿长，ZGC 停顿极短但设计复杂。架构师需要理解"复杂度的代价"是否值得。

### 1.3 7 种收集器的设计哲学

**1. Serial：简单优先**
- 设计哲学：单线程 GC，最简单，最稳定
- 适用：Client 模式、微服务启动期
- 优势：冷启动快，无并发开销
- 劣势：STW 时间长

**2. Parallel：吞吐优先**
- 设计哲学：最大化业务时间占比（GC 占比 &lt; 1%）
- 适用：批处理、后台计算
- 优势：吞吐最高
- 劣势：停顿长

**3. CMS：低停顿优先**
- 设计哲学：并发标记 + 标记-清除，STW &lt; 200ms
- 适用：互联网应用（已弃用）
- 优势：停顿可控
- 劣势：碎片化 + Concurrent Mode Failure + 浮动垃圾

**4. G1：可预测停顿优先**
- 设计哲学：Region 模型 + 选择性回收，MaxGCPauseMillis 可达
- 适用：通用场景（JDK 9+ 默认）
- 优势：可预测停顿 + 无碎片
- 劣势：写屏障开销大（SATB）

**5. ZGC：极致低延迟**
- 设计哲学：染色指针 + 读屏障，&lt; 10ms 停顿
- 适用：实时业务、大堆
- 优势：停顿与堆大小无关
- 劣势：吞吐损失 10-15%

**6. Shenandoah：并发整理**
- 设计哲学：Brooks 转发指针 + 读屏障，并发移动对象
- 适用：RedHat 系生态
- 优势：与 ZGC 类似
- 劣势：Brooks Pointer 内存开销

### 1.4 G1 的设计精髓：Region 模型 + 选择性回收

**Region 模型的核心思想**：

```
传统分代（CMS / Parallel）：
   堆 = [Young | Old]
   Young / Old 是连续的内存区域

G1 的 Region 模型：
   堆 = [Region 0][Region 1]...[Region 2048]
   每个 Region 动态切换 Eden / Survivor / Old / Humongous 角色
```

**Region 模型的优势**：

1. **局部回收**：只回收部分 Region，不是全堆
2. **可预测停顿**：根据 Region 的回收价值选择，控制总停顿
3. **无碎片**：Region 间复制实现整理
4. **大对象处理**：Humongous Region 独立处理大对象

**选择性回收的实现**：

```
G1 维护每个 Region 的：
- 存活对象量（live bytes）
- 预计回收时间（GC cost）

Mixed GC 时：
1. 按"回收价值"（live bytes / GC cost）排序所有 Old Region
2. 选择 Region，直到累计回收时间达到 MaxGCPauseMillis
3. 只回收选中的 Region
```

**架构师视角**：G1 的"选择性回收"是"贪心算法"在 GC 中的应用。每次 GC 选择"性价比最高"的 Region，最大化单次 GC 的回收量。

### 1.5 ZGC 的范式转移：染色指针 + 读屏障

**传统 GC 的局限**：

```
传统 GC：
   1. GC 移动对象
   2. 更新所有指向该对象的引用
   3. 必须在 STW 中完成（引用更新一致性）

无法并发整理的根因：
   - 应用线程访问旧地址，对象已被移动 -> 错误
   - 应用线程修改引用，GC 也要修改 -> 数据竞争
```

**ZGC 的解决方案**：

```
染色指针 + 多视图映射：
   1. 64 位指针中保留 4 位染色位
   2. 染色位标记指针的"状态"（Marked / Remapped / Finalizable）
   3. 同一物理地址有多个"染色视图"
   4. GC 移动对象后，修改染色位（不需修改对象）
   5. 读屏障检查染色位，必要时修正指针
```

**读屏障的作用**：

```
应用线程读取引用时：
   1. 检查指针染色位
   2. 如果指针"过期"（指向旧地址）
      -> 触发读屏障
      -> 通过多视图映射找到新地址
      -> 修正指针
   3. 返回新地址

关键：读屏障让"引用更新"可以并发进行
```

**架构师视角**：ZGC 是 GC 设计的范式转移。从"GC 移动对象 + STW 更新引用"到"GC 移动对象 + 读屏障按需更新引用"。这种"懒更新"思想在并发设计中常见：

- **MVCC 的快照隔离**：读时看到旧版本，按需更新
- **Copy-On-Write**：写时才复制，读时不阻塞
- **RCU（Read-Copy-Update）**：读不加锁，写时复制，旧版本等读者离开再释放

### 1.6 收集器选型决策树

```
是否单核或内存 < 100MB？
   └─ 是 -> Serial
   └─ 否
       |
是否对延迟极敏感（< 10ms）？
   └─ 是
   |   ├─ JDK 21+ -> 分代 ZGC
   |   ├─ JDK 15-20 -> ZGC
   |   ├─ JDK 12+ RedHat 系 -> Shenandoah
   |   └─ JDK 11 以下 -> G1（适当调小 Region）
   └─ 否
       |
是否吞吐优先（批处理 / 后台计算）？
   └─ 是 -> Parallel Scavenge + Parallel Old
   └─ 否
       |
堆大小？
   ├─ < 4GB -> Parallel 或 G1
   ├─ 4-32GB -> G1
   ├─ 32GB-16TB -> ZGC
   └─ > 16TB -> ZGC（JDK 17+）

容器化场景：
   - JDK 8u191+：-XX:+UseContainerSupport（默认）
   - JDK 10+：自动感知 cgroup
   - 推荐 G1（容器适配好）
```

## 二、GC 收集器与在线问诊系统的结合点

### 2.1 在线问诊各服务的 GC 选型矩阵

| 服务 | QPS | 延迟要求 | 堆大小 | JDK | 推荐 GC | 关键参数 |
|------|-----|---------|--------|-----|---------|---------|
| IM 网关 | 5w 心跳/秒 | &lt; 100ms | 8GB | 17 | G1 | MaxGCPauseMillis=100 |
| 视频问诊 SFU | 5800 路并发 | &lt; 20ms | 16GB | 21 | 分代 ZGC | ConcGCThreads=8 |
| 问诊订单服务 | 2000-5000 | &lt; 500ms | 4GB | 17 | G1 | MaxGCPauseMillis=200 |
| 处方服务 | 1000-2000 | &lt; 500ms | 4GB | 17 | G1 | MaxGCPauseMillis=200 |
| 医师服务 | 1000-3000 | &lt; 500ms | 4GB | 17 | G1 | MaxGCPauseMillis=200 |
| MongoDB 大文档服务 | 100-500 | &lt; 1s | 8GB | 17 | G1 | G1HeapRegionSize=16m |
| 内部管理后台 | 100-500 | &lt; 2s | 2GB | 17 | G1 | MaxGCPauseMillis=500 |
| 对账离线服务 | 批处理 | 不敏感 | 16GB | 17 | Parallel | GCTimeRatio=99 |

### 2.2 不同服务的 GC 调优重点

**IM 网关**：
- 重点：低停顿（100ms 目标）+ 长期稳定运行
- 难点：长连接对象长期存活，直接内存管理
- 调优：MaxGCPauseMillis=100，IHOP=45，UseStringDeduplication

**视频问诊 SFU**：
- 重点：极低停顿（&lt; 20ms）+ 高对象创建速率
- 难点：5800 路并发，每秒 435w 临时对象
- 调优：ZGC（JDK 21+ 分代），大堆 16GB

**业务服务**：
- 重点：均衡（吞吐 + 停顿）
- 难点：本地缓存 100w 订单进 Old 代
- 调优：G1，IHOP 调优，控制 Mixed GC 频率

**MongoDB 大文档服务**：
- 重点：避免 Humongous Region 滥用
- 难点：5MB 文档 + 16MB 文档混用
- 调优：G1HeapRegionSize=16m，流式解析

### 2.3 容量规划方法论

**Step 1：根据业务规模估算堆大小**

```
堆大小 = 新生代 + 老年代

新生代 = 每秒对象创建速率 × 期望 Minor GC 间隔 / 0.8
老年代 = 长期存活对象 + 缓存 + 预留 30%

示例（IM 网关）：
- 每秒对象创建：17.5MB
- Minor GC 间隔 60 秒
- 新生代 = 17.5 × 60 / 0.8 = 1.3GB
- 长连接对象：12w × 7KB = 840MB
- 业务缓存：500MB
- 预留 30%：~600MB
- 老年代 = 2GB
- 堆 = 1.3GB + 2GB = 3.3GB
- 实际配置 8GB（留余量）
```

**Step 2：根据延迟要求选 GC**

```
延迟要求 < 10ms  -> ZGC（JDK 21+）
延迟要求 < 50ms  -> G1（MaxGCPauseMillis=50）或 ZGC
延迟要求 < 200ms -> G1（MaxGCPauseMillis=200）
延迟要求 > 500ms -> G1 或 Parallel
```

**Step 3：根据 JDK 版本确认**

```
JDK 8  -> Parallel（默认）/ G1 / CMS（不推荐）
JDK 11 -> G1（默认）/ ZGC（实验）
JDK 17 -> G1（默认）/ ZGC（生产）
JDK 21 -> G1（默认）/ 分代 ZGC
```

1. **IM 网关的 G1 调优**：从 JDK 8 + CMS 升级到 JDK 17 + G1，停顿从 500ms 降到 100ms

## 三、与往周专题的呼应

### 3.1 GC 演进 vs MySQL 存储引擎演进（6月第1周）

**相似点**：都是从简单到复杂，从单线程到并发。

**差异点**：
| 维度 | MySQL 存储引擎 | JVM GC |
|------|--------------|--------|
| 演进动力 | 业务规模 + 事务需求 | 延迟需求 + 多核 CPU |
| 主要里程碑 | MyISAM -> InnoDB | Serial -> G1 -> ZGC |
| 并发策略 | MVCC + 锁 | 并发标记 + 读屏障 |
| 兼容性 | 多引擎共存 | JDK 版本绑定 |

**架构师视角**：两者都是"用复杂换性能"，但 MySQL 是"业务驱动"（事务、并发），JVM 是"硬件驱动"（多核、大内存）。

### 3.2 Serial vs Redis 单线程（6月第2周）

**相似点**：都是单线程简单设计。

**差异点**：
| 维度 | Redis 单线程 | Serial GC |
|------|------------|----------|
| 单线程范围 | 全请求处理 | 仅 GC |
| 单线程原因 | 避免锁竞争 + 内存访问 | 简单实现 |
| 性能瓶颈 | CPU 计算 | 堆大小 |
| 多线程演进 | Redis 6+ 多线程 IO | Parallel / G1 |

**架构师视角**：单线程不是"落后"，是"特定场景下的最优解"。Redis 单线程避免锁竞争，Serial GC 简化实现。多线程是"复杂换性能"，不是"先进"。

### 3.3 CMS 并发标记 vs ES Near Real-Time（6月第3周）

**相似点**：都是"后台并发处理，前台低延迟"。

**差异点**：
| 维度 | ES NRT | CMS 并发标记 |
|------|--------|------------|
| 后台任务 | Segment 刷新 | 标记对象 |
| 前台延迟 | &lt; 1 秒可见 | &lt; 200ms STW |
| 一致性 | 最终一致 | 最终一致 |
| 触发 | 时间周期（1 秒） | Old 代占用率 |

**架构师视角**：两者都是"容忍短暂不一致换低延迟"。ES 接受 1 秒延迟，CMS 接受浮动垃圾。

### 3.4 G1 Region 模型 vs Sentinel 滑动窗口（6月第4周）

**相似点**：都是"分片 + 局部处理"。

**差异点**：
| 维度 | Sentinel LeapArray | G1 Region |
|------|-------------------|----------|
| 分片维度 | 时间窗口 | 内存区域 |
| 局部处理 | 单窗口统计 | 单 Region 回收 |
| 选择策略 | 聚合多窗口 | 按回收价值排序 |
| 触发 | 请求时 | Eden 满 / Old 满 |

**架构师视角**：两者都是"分而治之"--把大问题分解为小问题，局部处理，再聚合。这是处理大规模数据/状态的通用方法。

### 3.5 JVM GC vs K8s 容器化（7月第3周）

**相似点**：都涉及资源限制与隔离。

**差异点**：
| 维度 | K8s 资源限制 | JVM GC |
|------|------------|--------|
| 资源 | CPU / 内存 | 堆内存 / 直接内存 |
| 隔离 | Pod 级别 | JVM 进级别 |
| 调度 | K8s 调度器 | GC 线程 |
| 配置 | requests / limits | -Xmx / -XX |

**协同问题**：
- JVM 堆 > K8s limit -> OOM Killed
- JVM 直接内存 + 堆 > limit -> OOM Killed
- GC 在容器中的行为：JDK 8u191+ 才正确感知 cgroup

**架构师视角**：JVM 与容器的协同是云原生时代的关键问题。Day05 第 2 周会深入。

## 四、能力差距与补足方向

- **架构师水平**：能讲清 ZGC 的染色位 4 位布局、多视图映射的 OS 层支持、读屏障在 JIT 中的实现、分代 ZGC（JDK 21）的改进

## 五、Day03 核心架构师命题

### 命题 1：为什么 G1 是 JDK 9+ 默认 GC？

**核心答案**：G1 是"通用场景下的最优解"。

**详细推理**：
1. **CMS 的内在矛盾**（碎片化 + Concurrent Mode Failure）无法解决
2. **Parallel 的停顿长**不满足现代互联网应用
3. **ZGC / Shenandoah** 在 JDK 9 时还不成熟
4. **G1 的可预测停顿 + 无碎片 + 通用性**是最佳平衡
5. **G1 调优简单**：只需设 MaxGCPauseMillis，无需精细调参
6. **G1 适合大堆**：6GB+ 堆表现优于 CMS

**架构师视角**：默认 GC 选择是"通用最优"而非"极致最优"。G1 不是最快的，但适合 80% 场景。ZGC / Shenandoah 是"特殊场景最优"，需要业务主动选。

### 命题 2：为什么 ZGC 能做到停顿与堆大小无关？

**核心答案**：染色指针 + 读屏障让"对象移动"与"堆大小"解耦。

**详细推理**：
1. 传统 GC 移动对象需要 STW，扫描整个堆更新引用
2. 堆越大，扫描越久，STW 越长
3. ZGC 用染色指针标记"指针状态"，不修改对象
4. 读屏障按需修正指针（懒更新）
5. GC 移动对象 + 修改染色位，与应用线程并发
6. STW 只在"初始标记 / 重新标记"（GC Roots 直接引用，与堆大小无关）

**架构师视角**：ZGC 是"用 CPU 换停顿"--读屏障开销 10-15%，但停顿始终 &lt; 10ms。这种"用资源换指标"的设计在大规模系统中常见。

### 命题 3：为什么 CMS 必然被 G1 替代？

**核心答案**：CMS 的设计有内在矛盾，无法修复。

**详细推理**：
1. CMS 用标记-清除追求低停顿
2. 标记-清除必然产生碎片
3. 碎片化最终触发 Concurrent Mode Failure
4. 失败后退化为 Serial Old Full GC，停顿数秒
5. 这是"低停顿"目标的彻底失败
6. G1 用 Region 间复制解决碎片问题，同时保持低停顿
7. CMS 的代码复杂度高，维护成本大
8. JDK 9 弃用，JDK 14 移除

**架构师视角**：CMS 是"局部最优"设计--单次 GC 停顿低，但长期运行必然退化。架构师要看"长期稳定性"，不能只看短期指标。

### 命题 4：为什么 SFU 适合 ZGC 而不是 G1？

**核心答案**：SFU 的延迟要求 &lt; 20ms，G1 难以达到。

**详细推理**：
1. SFU 每秒 435w 临时对象，新生代快速填满
2. G1 的 Young GC 停顿与 Region 数 + 存活对象相关
3. 5800 路并发，存活对象多，G1 停顿通常 30-80ms
4. 视频实时性要求 &lt; 20ms，G1 难以达到
5. ZGC 停顿 &lt; 10ms，与堆大小无关
6. SFU 堆 16GB，ZGC 表现稳定
7. JDK 21 分代 ZGC，吞吐损失降到 5-10%，可接受

**架构师视角**：GC 选型要"按需"，不是"越先进越好"。SFU 用 ZGC 是因为延迟要求，业务服务用 G1 是因为均衡。

### 命题 5：为什么大对象是 GC 的"特殊公民"？

**核心答案**：大对象在复制算法下开销不可控。

**详细推理**：
1. 新生代用复制算法
2. 大对象（如 5MB）复制开销大（5MB 内存拷贝）
3. 大对象可能放不进 Eden，触发提前 GC
4. 解决方案：大对象直接进 Old 代（CMS / Parallel）或 Humongous Region（G1）
5. 但 Old 代 / Humongous Region 也有问题（占用 Old 代配额、分配失败触发 Full GC）
6. 最佳实践：避免大对象创建，改用流式处理

**架构师视角**：大对象是"性能陷阱"--单次大对象分配可能触发 GC 雪崩。代码中应避免大数组、大字符串、大 JSON，改用流式 API。
