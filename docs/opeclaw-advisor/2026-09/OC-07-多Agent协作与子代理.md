# OC-多Agent协作与子代理

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

多 Agent 先协议后数量。子代理必须有交接字段和失败回收。没有协议的「再开一个助手」，通常只是把上下文污染复制成两份。

## 一、目标与边界

本篇回答：什么时候该拆 Agent、主会话与子代理如何交接、深度如何封顶。大多数个人场景一个 main Agent 足够；拆分的理由必须是职责、权限或人格冲突，而不是新鲜感。

该拆的信号：

- 上下文污染：写代码时仍装着投研技能说明。
- 人格冲突：严谨研报口吻与闲聊口吻互相伤害。
- 安全隔离：能跑 shell 的开发助手，不应处理陌生人的群消息。
- 路由需求：不同 Channel 或不同群需要不同技能集。

不该拆的信号：只是任务步骤多。步骤多用 Skill 编排或子代理一次任务，不新开常驻人格。常驻人格有记忆和权限寿命，成本按周付；工单型子代理成本按次付。选错了，账单和安全事件会同时提醒你。

Nanobot 这类轻量子 Agent 适合「单次任务、小窗口、低温度」，不适合当第二个拥有完整 MEMORY 的人格。它是工具化的运行时，不是第二个你。

## 二、结构 / 分层模型

单 Agent：所有消息进 main，加载全部技能。简单，但窗口和权限一起膨胀。

多 Agent：按通道或按职责路由。每个 Agent 有自己的工作区、SOUL、技能集和凭证。这是「多员工」。

子代理：main 仍是唯一对用户负责的人格，用 `sessions_spawn` 或脚本拉起一次性任务。这是「外包一个工单」。投研工作区更适合后者：主会话保持人格与风控，切片分析外包。

交接必须是结构化字段，而不是一段自然语言「你去看看」：

- 目标：本轮要产出什么文件或结论类型
- 输入：允许读取的路径或证据列表
- 禁止：不可调用的 Tool、不可读取的档案
- 预算：模型档位、max tokens、时限
- 回收：超时、空结果、异常时如何写回主会话

深度上限：子代理默认不得再 spawn 子代理。链路一深，失败无法归因，费用也无法封顶。

## 三、工程动作

1. 先写路由表：来源 Channel / 场景 → Agent 或子代理。没有命中则留在 main。
2. 主会话保留风控和对外发言权。子代理只写中间文件，不直接回用户通道。
3. 给子代理单独的工作目录和较小的 token 上限。共享整个 workspace 等于没有隔离。
4. 交接用同一张工单模板。缺字段不准 spawn。
5. 失败回收：超时杀进程、把错误码写回工单、主会话用降级策略（告诉用户哪一层失败），禁止假装成功。
6. 并发要有上限。同一标的的拆解任务串行或加锁，避免两份估值文件互相覆盖。
7. 定期问：这个常驻 Agent 本周有没有独立流量。没有流量就合并回 main，减少人格分叉。
8. 子代理产出必须是文件而不是聊天。主会话只引用路径。这样用户看到的是一条声音，磁盘上却能回放切片。
9. 权限随工单走：工单禁止读档案，则子代理进程环境里根本没有那条路径，而不是靠模型「请不要读」。

过关口径：一次切片任务结束后，用户通道上只有 main 的一则汇总；工作区多了一份带工单 id 的中间文件；子代理进程已退出。若通道上出现第二个人格，或中间文件无法对应工单，协作协议就还没落地。

## 四、常见失败模式

1. 为每个技能建一个 Agent，路由表比技能还多。对策：常驻 Agent 按权限和人格拆，流程用 Skill。
2. 子代理继承主会话完整记忆，把私人偏好写进工具日志。对策：子代理最小上下文。
3. 子代理直接对 Channel 发言，用户看到互相矛盾的两条回复。对策：只有 main 作出站。
4. 无深度上限的递归 spawn，一次「分析行业」变成费用事故。对策：spawn 层数 = 1。
5. FAQ：多 Agent 配了但消息仍进 main。常见是通道路由未绑定。对策：验收用一条指定通道的消息，看 Agent ID。

## 五、建议指标

协作一旦没有深度和越权这两项，成功率会把事故包装成交付。宁可少交付，不可无回收。回收失败的任务应视为系统失败，而不是模型失败。建议跟踪：

- 协作任务成功率（主会话最终交付）
- 子代理超时率、空结果率
- 平均链路深度（目标 = 1）
- 重复工作率（同一输入两份子结果）
- 子代理越权读取（触碰禁止路径）次数，目标 0
- 常驻 Agent 周活跃数（长期为 0 的应下线）

## 六、结论

协作机制做得好，能力是叠加；做不好，复杂性是叠加。能用 Skill 解决的不要拆人格，能用一次性子代理解决的不要造常驻员工。协议、交接、回收齐了，多 Agent 才值得存在。数量本身不是架构，能回收的工单才是。先把工单跑稳，再谈第二个常驻人格。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：子代理不许对用户通道发言。
2. 可以落到监控面板的指标：深度、超时、越权读取。
3. 能在下次项目里直接复用的流程模板：五字段工单。

后续继续学习时，我会优先补两块：
- 收集一次递归 spawn 的费用账单作为反面教材。
- 对比 nanobot 与同框架 sessions_spawn 在隔离程度上的真实差异。
