# OC-Gateway最小闭环与安装验收

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

安装完成不等于系统可用。OpenClaw 的最小闭环是：消息进得来、模型回得去、会话可复盘。只看到 CLI 打印 ready，并不能证明这三件事成立。

## 一、目标与边界

本篇定义「怎样算跑通」，不写各操作系统的包管理步骤。

最小闭环的验收对象是 Gateway，不是某一条安装命令。Gateway 是常驻守护进程：默认本机端口、持有 Token、管理 Channel 长连接、把请求交给 Agent Runtime。它挂了，所有通道一起静音。

明确不在本篇范围：

- 多模型路由和预算（见 OC-03）
- 生产级公网暴露（见 OC-08）
- 技能包和投研流程（见 OC-05 / OC-09）

硬件只作约束：Gateway 本身轻，内存主要吃在通道数量；若上本地模型，资源账要另开，不能和「助手进程」混报。

## 二、结构 / 分层模型

把故障域分成四层，出问题先定位层，再动手。跨层乱修是安装场景里最贵的习惯：模型超时却去重装 Node，通道掉线却去换默认模型。分层的价值就是让每一次失败只打开一个抽屉。

1. 运行时层：Node 版本、CLI 是否可执行。这一层失败，onboard 都进不去。
2. 控制层：Gateway 进程、端口、Token、TLS。`status` 必须是 running，且 PID 稳定。
3. 模型层：提供商可达、密钥可读、一次非空 completion。
4. 会话层：至少一条用户消息写入 Session 日志，回复能在同一 Channel 回来。

引导向导 `onboard` 的真正产物不是「聊上了」，而是三份资产：模型提供商、Gateway Token、（可选）daemon 自启。通道可以后加。第一次就把 WhatsApp 和 Telegram 全接上，会把通道故障和 Gateway 故障缠在一起。

数据流验收用一条合成消息：WebChat 或 CLI 发「ping」→ Gateway 路由到 main Agent → 模型返回 → 界面可见 → 磁盘上能找到本轮会话记录。缺任何一跳，都不算闭环。

## 三、工程动作

1. 先验收控制层。`openclaw status` 看 Gateway Status、Port、Agents。stopped 时只重启 Gateway，不要重装全家桶。
2. 确认监听地址是预期中的回环或内网，而不是 0.0.0.0 加空 Token。Token 存在但从未轮换，等于门没锁。
3. 用最小通道验证。优先本机 WebChat，再加一个即时通讯 Channel。两条通道都通，才说明路由不是「碰巧一个客户端能用」。
4. 做一次失败注入：拔掉模型密钥或改错模型名，系统应报模型层错误，而不是假成功空回复。空回复比报错更危险。
5. 检查落盘。工作区应出现会话日志或当日 memory 文件。只有屏幕滚动没有文件，下次重启就是失忆。
6. 把验收写成清单，而不是「感觉能聊」。清单至少包含：进程、端口、一次成功回复、一次可复现的失败提示、一条磁盘记录。
7. daemon 自启是加分项，不是闭环条件。自启失败时，先保证手动拉起可复现，再修服务单元。
8. 重启验收：杀掉 Gateway 再拉起，原会话仍可从磁盘续上。只能「重新聊一句」的，说明会话层没进闭环。
9. 记录一次完整的分层定位：现象、判定层、动作、结果。没有这条记录，团队会在重装和改模型之间反复横跳。

过关口径：不打开官方安装章节，只凭清单就能在另一台机器上判定「通 / 不通 / 卡在哪一层」。如果判定还依赖某一条复制粘贴命令是否跑过，说明验收绑在了安装步骤上，而不是绑在系统行为上。

## 四、常见失败模式

1. 把 onboard 成功输出当成生产就绪。向导默认值可能开了端口却没理解 Token 与 TLS 含义。对策：闭环清单里单独勾「谁持有 Token、Token 存在哪」。
2. Node 版本漂移。文档要求 Node 22+，用 18/20 能装上 CLI 但运行时怪错。对策：验收记录运行时版本，升级只改这一层。
3. 通道先于 Gateway 验收。扫码成功但 Gateway 不在，表现为「刚才还能聊」。对策：任何 Channel 操作前先看 status。
4. FAQ 高频：Gateway 起来了但浏览器打不开。常见是绑了 127.0.0.1 却在另一台机器访问，或反向代理没传 WebSocket。对策：先本机访问，再谈远程。
5. 重装癖。一次失败就 npm 重装，毁掉已有工作区。对策：工作区与 CLI 分离备份；修层不修世界。

## 五、建议指标

指标要能周度复盘，而不是写完就归档。缺主人的指标不要写上墙。建议至少看：

- Gateway 可用率：进程 running 的时间占比（目标 ≥ 99% 本机场景）
- 冷启动时延：从拉起到 status=running 的秒数
- 首轮对话成功率：新会话第一条非空回复比例
- 会话落盘率：有回复的会话中，磁盘可追溯的比例（目标 100%）
- 分层误报率：把模型错误当成通道错误的次数（应逐月下降）
- 错误可定位率：失败日志能归到上述四层之一的比例

## 六、结论

Gateway 最小闭环是 OpenClaw 的地基。先证明控制层活着、模型层可调用、会话层可审计，再叠加通道和技能。安装步骤可以变，验收清单不能变。清单不随操作系统分叉：Windows 和 Linux 的包管理不同，但「running + 非空回复 + 磁盘记录」这三件事相同。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：ready 文案不等于闭环。
2. 可以落到监控面板的指标：可用率、首轮成功率、落盘率。
3. 能在下次项目里直接复用的流程模板：四层故障域 + 七步验收。

后续继续学习时，我会优先补两块：
- 收集「空回复 / 假成功」的日志样本，做成对照表。
- 对比本机 WebChat 与远程 Channel 在闭环判定上的差异，避免只用最顺的通道当绿灯。
