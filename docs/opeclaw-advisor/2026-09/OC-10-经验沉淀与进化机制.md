# OC-经验沉淀与进化机制

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

经验必须结构化才能复用。进化是带度量的 A/B，不是改了 SOUL 就算进化。没有假设、没有对照、没有指标的「感觉更好」，只是另一次人格漂移。

## 一、目标与边界

本篇覆盖三块，且必须分开存放：

- 经验库：决策、教训、偏好、技巧。可检索、可过期、可关联。
- 进化：同一场景下的策略对照（例如按场景装载 vs 全量装载），用指标判胜负。
- 个性化：沟通与决策风格的参数，而不是又一份散文 SOUL。

非目标：自动把模型微调当成进化。工作区里的进化对象是装载策略、检索排序、回复风格，不是权重。

经验不是 MEMORY 的别名。MEMORY 是每次主会话可能装载的精选事实；经验库是按类型检索的案例。把所有教训追加进 MEMORY，窗口会先被历史压死。检索型经验允许「用时再取」；常驻记忆只保留几乎每次都要用的约束。

## 二、结构 / 分层模型

经验条目建议带前置元数据：id、type、category、tags、importance、时间、关联条目。正文写背景、动作、结果、可复用条件。类型至少四种：

- decision：当时做了什么选择、否决条件是什么
- lesson：失败或惊吓，下次禁止重复
- preference：稳定口味，可晋升到 USER
- tip：可复制的操作技巧

检索入口应是命令或技能，而不是「模型回忆一下」。工作区的 `experience-manager find` 按 type 与 category 过滤，这才是可测试的 API。

进化机制的最小闭环：假设 → 变体 A/B → 流量分配 → 指标 → 报告 → 只推广胜出配置。示例假设：「按场景加载能降低上下文体积并提高满意度」。对照必须同时跑，禁止先改生产再找感觉。

个性化参数（简洁度、正式度、保守度、自主性）应版本化。SOUL 负责不可谈判的红线；参数负责可 A/B 的风格。把幽默感写进 SOUL 长文，就无法做对照实验。

## 三、工程动作

1. 规定什么能进经验库：必须有日期、类型、可复用条件。没有结果的感想进日报，不进经验库。
2. 主会话在投研或复盘场景先检索相关 decision / lesson，再开口。检索为空也要记录，证明查过。
3. 同时只跑一个 A/B。多测试交叉会让指标无法归因。
4. 预先写指标：上下文体积、装载时延、任务完成率、用户显式反馈。缺指标的测试不准上线。
5. 胜出配置以文件或配置版本发布，而不是口头「以后都按 A 来」。回滚就是切回旧版本号。
6. 个性化变更走小步：一次只动一个维度。同时改简洁度和自主性，失败无法解释。
7. 过期策略：低 importance 且长期未检索的条目归档，防止经验库变成第二份 MEMORY。
8. 进化报告固定四段：假设、样本、指标、结论。没有样本数的结论视为无效，不允许改默认配置。
9. 经验被引用时记下 id。一周没人引用却天天增长的库，说明入库门槛太低，检索没有进入主会话习惯。

过关口径：能指出当前生产用的装载策略版本号，以及它赢过的对照版本。如果说不出对照，只说「我们改过 SOUL」，进化机制就不存在。个性化同理：能指出当前简洁度取值和上一次回滚点。

## 四、常见失败模式

1. 改 SOUL 一行就称为进化。无法对照、无法回滚。对策：SOUL 冻结红线，策略放配置。
2. 经验正文没有 type，检索只能全文碰词。对策：强制元数据，缺字段拒绝入库。
3. A/B 未结束就把变体 A 写进默认路径。对策：status=active 时禁止改默认。
4. 用「用户没骂」当满意度。对策：显式评分或可观察的返工次数。
5. 个性参数与 SOUL 双写，模型收到两套口吻。对策：单一来源，SOUL 只保留冲突时的红线。
6. FAQ 式问题：「为什么这周风格变了」。没有版本日志就只能猜。对策：每次进化写报告文件。

## 五、建议指标

进化没有进行中测试数这一项，就分不清「在实验」和「已发布」。默认配置必须能指向版本号。指不出版本，就不能声称系统在进化。建议跟踪：

- 经验检索命中后被引用的比例
- 入库条目的元数据完整率（目标 100%）
- 进行中的 A/B 数量（目标 ≤ 1）
- 上下文体积与装载时延在变体间的差值
- 任务完成率、返工率
- 个性化版本回滚次数与回滚原因分类

## 六、结论

可复用的助手不是靠更长的灵魂文件堆出来的。经验库让过去可检索，进化让策略可验证，个性化让口吻可调且可撤。三套机制都带着度量和版本时，OpenClaw 工作区才从「能跑」变成「能迭代」。没有版本号的改进，下一周还会被当成灵感再改回去。版本比灵感便宜，也比灵感可回滚。这一点要写进团队习惯。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：改 SOUL 不是进化。
2. 可以落到监控面板的指标：进行中测试数、体积差值、元数据完整率。
3. 能在下次项目里直接复用的流程模板：假设-对照-指标-版本。

后续继续学习时，我会优先补两块：
- 把一次真实的装载策略 A/B 报告写进附录，保留失败变体。
- 区分「偏好晋升到 USER」与「仍留在经验库」的规则，避免两处各写一套口味。
