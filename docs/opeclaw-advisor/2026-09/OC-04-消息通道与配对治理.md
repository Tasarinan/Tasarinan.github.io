# OC-消息通道与配对治理

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

Channel 既是入口 SLA，也是攻击面。DM Pairing 是授权动作，不是为了少扫一次码而存在的方便开关。通道一开，助手就拥有「能从外部被叫醒」的能力。

## 一、目标与边界

本篇管两件事：消息如何进出、谁有资格叫醒 Agent。不管具体平台的 BotFather 点击路径。

Channel 是双向管道。Telegram Bot、Discord Bot、WhatsApp 会话、WebChat 都是同级对象。Gateway 的卖点是「一个控制面连多个管道」，不是「每个管道一台机器人」。

配对针对的是发送者身份，不是通道进程。通道 connected 只说明管道活着；发送者 approved 才说明这个人可以驱动 Tool。把两者当成一回事，会在群聊和私聊里放出未授权执行。治理上宁可漏回复，不可漏执行：少回一句是体验问题，多跑一次工具是安全事件。

本篇不覆盖沙箱内部如何拦 `rm`（见 OC-08），但所有公网通道默认视为不可信入口。

## 二、结构 / 分层模型

通道生命周期：配置凭证 → 登录/链接 → 收发 → 移除。每一段都要能单独观察：`channels status`、`channels logs`、pairing 列表。

入站治理建议三段：

- 入口：Channel 是否 connected、凭证是否过期、WebSocket 是否还在。
- 授权：DM Pairing 是否通过；群聊是否要求 @提及或关键词；陌生人默认拒绝。
- 出站：回复回到来源 Channel，除非任务显式要求跨通道投递。跨通道是能力，也是事故源。

群聊与私聊必须分 Session。群里一人一句若共享主会话记忆，会把人格和私人档案泄漏进公共上下文。激活模式（提及、关键词）是群聊的刹车，不是装饰。群刹车失效时，预算和泄密会一起发生，所以群策略要当成安全控制，而不是体验开关。

配对状态按发送者存储。扫码成功只绑定设备通道；不自动等于「所有联系人已授权」。FAQ 里「配对成功但过一会儿断开」通常是通道会话过期，不要用 autoApprove 去「修好」它。过期应重连，授权应保持拒绝直到再次批准。

## 三、工程动作

1. 第一阶段只接一个 Channel。WebChat 或 Telegram 二选一。第二条通道要等配对流程跑顺。
2. 列出 pairing：待批准、已批准、已拒绝。新发送者进入待批准，不进模型。这是默认，不是可选插件。
3. 关闭自动批准。autoApprove 只适合完全私有的测试号。投顾或文件权限一旦接上，自动批准等于把 Tool 交给通讯录。
4. 群聊默认静默，除非被提及。机器人在群里「热心插话」会同时烧掉预算和信任。
5. 给每个 Channel 记 SLA：连接断开告警、消息积压长度、回错频道次数。通道问题先看通道日志，再怀疑模型。
6. 凭证轮换。Bot Token 泄漏的修复是轮换而不是重启 Gateway。轮换后旧通道应立即失效。
7. 跨通道投递写白名单：哪些任务允许「从 A 收、到 B 发」。默认禁止。
8. 新成员加入群时，默认沿用群的静默策略，不继承任何个人的已批准私聊权限。群身份和人身份分开记账。
9. 通道变更窗口：登录、换 Token、改群激活规则，一次只做一件，并写进变更日志。出事才能回放。

过关口径：用一个未配对账号发一条带工具倾向的指令（例如「读工作区并总结」），系统只应答「等待批准」，磁盘上不出现新的工具痕迹。只要工具跑过，通道治理就失败了，无论回复文案多么礼貌。

## 四、常见失败模式

1. 通道 connected 就让所有私聊进主 Agent。对策：未配对请求只回「等待管理员批准」，不跑 Skill。
2. 用 autoApprove 处理反复掉线。掉线是通道层，授权是身份层。对策：修重连和会话保活，不放开配对。
3. 群聊共享主会话。私人 MEMORY 被群消息带出。对策：群 Session 隔离，主会话记忆不对群加载。
4. 多通道同时接入，故障无法归因。对策：变更窗口一次只改一个 Channel。
5. FAQ：扫码后能收不能发，或只能发不能收。能力表因平台而异（群组、媒体、已读）。对策：先查 `channels capabilities`，再写业务假设。

## 五、建议指标

通道指标要分开看「管道」和「授权」，混在一起会把掉线当成安全事件。授权类指标优先于连接类指标。连接好但未授权放行，比断线更危险。建议至少看：

- Channel 连接可用率与重连次数
- 待批准队列停留时间（P95）
- 未授权请求拦截率（应接近 100% 的拦截，而不是 100% 放行）
- 群聊误触发率（未被提及却回复）
- 跨通道误投递次数（目标 0）
- 配对撤销后的生效时延

## 六、结论

通道治理的核心是把「管道活着」和「人被授权」拆开。Channel 负责传输与 SLA，Pairing 负责谁能驱动 Agent。这两件事做对了，后面的技能和投研才不会被陌生人的一句话点燃。拆开之后，运维可以分别告警，安全可以分别审计，不再用一次重连去掩盖一次误授权。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：connected ≠ approved。
2. 可以落到监控面板的指标：拦截率、误触发、误投递。
3. 能在下次项目里直接复用的流程模板：单通道先跑顺，再谈多通道。

后续继续学习时，我会优先补两块：
- 记录一次真实的配对滥用或群聊串话事件，写成时间线。
- 对比官方通道与 extension 通道在配对语义上是否一致，避免假定「所有 Channel 同一套授权」。
