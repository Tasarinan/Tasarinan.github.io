# OC-本地优先架构与角色边界

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

OpenClaw 的价值不在「又能聊天」，而在把私人助手跑在自己的控制面里：数据本地、通道可替换、角色可划界。角色一旦糊成一个全能 prompt，后面的技能、记忆和安全都会一起塌。

## 一、目标与边界

本篇只回答一件事：系统里有哪些对象，各自负责什么，什么不该进 SOUL。

必须先固定术语，否则安装、配模型和写技能会各说各话：

1. OpenClaw：本地优先的私人助手框架，不是云端客服平台。
2. Gateway：常驻控制平面，收消息、做路由、管会话、调 Agent。
3. Agent：一个独立助手实例，有自己的工作区、记忆、技能和人格。
4. Channel：消息进出的管道，一个 Telegram Bot 或一个 Web Chat 都是 Channel。
5. Skill：教 Agent 如何组合 Tool 完成任务的说明书，通常是 Markdown。
6. Tool：原子动作，读文件、发消息、跑命令。
7. Session：一次带上下文的对话；主会话和群聊会话要隔离。
8. Memory：跨会话要记住的信息，落在本地 Markdown，而不是模型权重里。

边界同样要写死：OpenClaw 不做可视化客服编排，也不替代企业 NLU 平台。它适合「个人或小团队、数据敏感、要多通道 + 多模型 + 工具」的场景。把投顾口吻、持仓偏好、沟通风格塞进同一个 SOUL 长文，看起来省事，实际是把角色、知识和流程焊死了。

## 二、结构 / 分层模型

官方自我定义接近「多通道 AI 网关」。落地时我按四层看：

- 通道层：WhatsApp、Telegram、Discord、飞书、WebChat 等，只负责统一消息进出。
- 控制层：Gateway。路由、会话队列、配对授权、WebSocket API、Cron。
- 运行时层：Agent Runtime。组装 prompt、调用模型、执行 Tool、流式回写。
- 模型层：云端或本地提供商，可替换，不绑定单一厂商。

一条消息的正确路径是：Channel 入站 → Gateway 判定 Agent 与授权 → 加载 Session / Memory / Skill → Runtime 循环（文本或 Tool）→ Channel 出站 → 会话落盘。

同会话必须串行。并行写同一份 MEMORY.md，会把「记住了什么」变成竞态。人格在 `SOUL.md` / `IDENTITY.md`，用户在 `USER.md`，任务流程在 Skill。这三份文件混写，是后续所有故障的根。

工作区里的真实用法也印证了这一点：身份可以是「个人助理 + 投研风格」，但风格不等于研究流程。风格留在 SOUL，研究流程必须是 Skill。

## 三、工程动作

1. 先画对象图，再装软件。一张图上只保留 Gateway、一个 main Agent、一个 Channel，确认数据都落在本机工作区。
2. 给 Agent 写职责一页纸：服务谁、擅长什么、明确不做什么（例如不对外冒充本人发言、不在群里主动扩权）。
3. 把 SOUL 限制在人格与沟通约束：直接、有观点、数据要有来源。禁止在 SOUL 里写完整分析流水线。
4. 给每个 Skill 规定触发词、输入字段、输出字段、允许调用的 Tool。Skill 之间不要共享一份「万能分析提示」。
5. 主会话与子任务会话分开。主会话读人格和用户档案；子任务只带任务说明书和最小证据。
6. 任何跨通道能力先当「同一 Gateway 上的多个管道」，不要理解成多个互不相干的机器人。出站通道必须显式指定，避免回错地方。
7. 做一次「职责越界」演练：让 Agent 处理明显不属于它的任务（例如投研助手去改生产代码）。期望是拒绝并指出该找谁，而不是硬扛。硬扛成功反而说明边界失败。
8. 评审 SOUL 的 diff。一周内若流程步骤频繁进出人格文件，说明分层还没站住。稳定的 SOUL 应该几乎只改口吻和红线。

过关口径：新人只看对象图和三份文件（SOUL / USER / 一个 Skill）就能说出「人格、用户、流程」分别在哪，而不用读完所有指南。说不清的，架构就还停留在能聊天。

## 四、常见失败模式

1. 用聊天机器人的心智装 OpenClaw，只测「能不能回一句」，不测文件是否本地可审计。对策：验收看工作区文件，不看聊天截图。
2. 一个 Agent 同时当程序员、日程秘书和投研。上下文被无关 Skill 污染，误触发升高。对策：按职责拆 Agent，或至少按场景装载 Skill。
3. SOUL 写成操作手册，一改流程就要改人格，版本无法 diff。对策：流程进 Skill，人格只保留稳定约束。
4. 把 Channel 当身份。换 Telegram 到 Discord 后，发现记忆和授权绑在了账号上。对策：身份在 Agent 工作区，Channel 只做传输。
5. FAQ 里最常见的「装上了但不知道自己在跟谁说话」：没有 IDENTITY，模型会演成通用助手。对策：IDENTITY 只放稳定身份字段，细节放 SOUL。

## 五、建议指标

- 角色文件完整率：SOUL / USER / IDENTITY 三者是否都存在且职责不重叠
- 主会话平均装载文件数（目标：场景相关，而不是全盘加载）
- Skill 误触发率：实际任务与被加载技能的不一致次数 / 总任务
- 本地可审计率：关键决策能否在工作区 Markdown 中回溯（目标 100%）
- 通道串话次数：回错 Channel 或回错群的次数（目标 0）

## 六、结论

本地优先架构的第一课是划界。Gateway 管进出，Agent 管人格与记忆，Skill 管流程，Tool 管动作。界线清楚之后，安装、模型和安全才有地方挂；界线不清楚，后面每篇笔记都在给一个全能 prompt 打补丁。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：SOUL 不写流程。
2. 可以落到监控面板的指标：装载文件数、误触发、串话。
3. 能在下次项目里直接复用的流程模板：四层对象图 + 职责一页纸。

后续继续学习时，我会优先补两块：
- 增加「一个 Agent 硬扛多职责」的失败样本，而不是只保留拆分后的成功路径。
- 对比个人助手与小团队共用 Gateway 时，角色边界会在哪一层先破裂。
