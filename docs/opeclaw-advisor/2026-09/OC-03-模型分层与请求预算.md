# OC-模型分层与请求预算

这篇是我基于项目实践与资料交叉阅读整理的学习笔记，目标不是复述概念，而是沉淀可直接复用的工程动作与判断标准。

多模型必须先分档再调用。默认旗舰模型，账单、时延和上下文膨胀会一起失控。OpenClaw 能接几十个提供商，这不是让每次请求都走最贵的那条路。

## 一、目标与边界

本篇解决：请求如何分级、如何设上限、主模型挂了怎么降级。不讨论某个厂商的注册页面，也不把 temperature 调参当成主业。

分档的输入是任务价值，不是模型品牌。同一句话「帮我看看」，在心跳场景是快速档，在投研综合场景是深度档。关键是请求必须带场景或被路由表打上标签；无标签不得猜测成高价值。

- 快速档：分类、摘要、格式转换、心跳类短回复。低成本、低时延。
- 标准档：日常分析、写技能草稿、常规检索后作答。质量与成本平衡。
- 深度档：长链路推理、多文件综合、高代价决策。默认关闭，显式升级。

提供商只是实现。云端 API、OpenRouter 聚合、Ollama 本地，都可以映射到这三档。本地模型省的是单价，不省上下文纪律。

## 二、结构 / 分层模型

配置落在 `openclaw.json` 的模型字段、提供商块、fallback 列表和 tokenLimits。我把它理解成三层策略，而不是一堆开关：

1. 路由层：按任务类型或显式指令选档。没有标签的请求进标准档，禁止隐式进深度档。
2. 限额层：单请求 maxInput / maxOutput / maxTotal，以及日/月费用上限、告警阈值。
3. 降级层：主模型超时或 429 时，按 fallback 列表走下一档，并标记「本轮已降级」。

工作区里的子代理实践也符合这套结构：轻量子 Agent 用更小的 max tokens 和更低 temperature，主会话才保留深度档权限。子任务默认深度档，是在用钱买噪声。

参数上只锁少数几个：投研与风控类 temperature 偏低；创意草稿可以略高。不要同时猛调 temperature 和 topP。maxTokens 先按档位封顶，再谈「模型最大能输出多少」。

## 三、工程动作

1. 写一张路由表，三行即可：任务类型 → 档位 → 模型 ID。贴在工作区，改模型只改表，不改 Skill。
2. 打开 usageTracking。没有日限额的助手，等于生产环境裸奔。告警阈值先设 80%，让人在打满前介入。
3. 给三档分别设 tokenLimits。快速档输出封到短回复；深度档才给长输出。禁止用旗舰模型的最大窗口当默认。
4. 配置 fallback：深度档失败降标准档，标准档失败降快速档或本地模型。降级必须可观测，不能静默换模型导致风格突变却无人知晓。
5. 密钥按提供商隔离，优先环境变量。配置文件里的明文 Key 一旦进备份仓库，后续所有安全篇都来不及救。
6. 每次改默认模型，跑三条探针：短指令、带工具的中等任务、超预算应被拒绝的长粘贴。第三条经常被漏测。
7. 记录「档位命中」。如果 80% 请求都打到深度档，是路由表失效，不是模型不够强。
8. 把「用户说再想想」映射为升级档，而不是默认深度档。升级必须可逆：下一轮没有同样指令就回到标准档。
9. 周报只看三列：档位占比、P95 token、降级次数。模型排行榜可以看，但不要当运营指标。

过关口径：关掉旗舰模型后，快速档和标准档任务仍能完成；只有标注为深度的任务失败或明显变差。如果一关旗舰全站瘫痪，说明路由从未真正分档，只是所有请求共用一个贵模型。

## 四、常见失败模式

1. onboard 选了最强模型后从未再看 `models status`。对策：周度对账，按任务类型看费用分布。
2. 用 OpenRouter 当「自动最便宜」，结果简单问答仍进推理模型。对策：聚合层仍要分档，不能把路由外包给黑盒。
3. 只设费用上限，不设 token 上限。超长粘贴会在费用触发前打满上下文。对策：两道闸门同时存在。
4. fallback 配了更贵的模型。主模型 429 时费用不降反升。对策：降级方向只能向更便宜或本地。
5. FAQ 常见：模型列表里有名字但调用 404。别名、下线、代理 baseUrl 不一致。对策：探针任务纳入发布检查，不靠记忆中的模型名。

## 五、建议指标

没有档位占比，费用上限只是心理安慰。建议跟踪：

- 各档请求占比（快速 / 标准 / 深度），深度档应是少数
- 请求平均 token 与 P95 token
- 超预算触发率、降级后可用率
- 日费用 / 月费用相对限额的使用率
- 主模型失败到 fallback 成功的中位时延
- 空回复率（含超时被当成成功的情况）

## 六、结论

模型能力是上限，预算路由是命门。先分档、再限额、再降级，OpenClaw 的多提供商优势才是资产而不是负债。默认高预算，系统会在你看见质量问题之前先看见账单。分档一旦写进路由表，日常运营就只调表，不再在聊天里口头指定模型。

## 学习者复盘

这轮整理里，我刻意保留了三类内容：
1. 真正会踩坑的决策点：没有标签的请求不得进深度档。
2. 可以落到监控面板的指标：档位占比、P95 token、降级可用率。
3. 能在下次项目里直接复用的流程模板：三行路由表 + 三条探针。

后续继续学习时，我会优先补两块：
- 用真实一周账单做一次档位复盘，而不是只写限额配置。
- 对比「同任务换模型」时质量是否真的随价格上升，避免深度档迷信。
